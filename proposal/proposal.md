## 1. 要解决的问题

**团队已经可以借助 AI 开发自己的工作台，但从“代码写出来”到“整个团队持续使用”，仍然缺少基层团队难以自行获得的公司级接入条件和运行资源。**

前期实践从分发 Agent、Skill、MCP 等套件开始。套件落到个人本地后，使用情况难以观察，改进留在个人环境，公共版本分发和兼容又形成额外管理动作。问题不是应该禁止个人分叉，而是团队缺少将个人优势汇合、共同使用和持续改进的载体。[S1][S3]

两个团队根据各自业务建设了工作台。由懂业务、懂 AI 的成员牵头，大家围绕同一个平台提出问题并改进，部分问题能够小时级兑现。用户观察到其中一个平台每周改版，持续融入团队的新想法。这些是实践观察，不是经过统计验证的提效倍数。[S3]

**组织提效需要共同改进的工作方式，但不必要求所有团队使用同一个业务应用。** 装备应提供共同的接入与运行条件，业务团队保留对页面、流程、产品知识和 Agent 使用方式的决定权。[S1][S3]

### 1.1 用户构建数字人的三大痛点

| 痛点 | 基层团队已经能做的事情 | 团队仍难以自行获得的条件 | 平台应提供的结果 |
|---|---|---|---|
| **认证鉴权难接入** | 写出页面和服务 | 公司已有身份体系的应用接入资格，以及数字人账号、运行身份和权限映射 | 在批准范围内接入公司身份，数字人有独立账号与受控权限 |
| **部署／运行资源难获得** | 编写业务服务与 Agent 逻辑 | CPU 服务部署资源、Agent 执行资源、代码环境、数据库和文件存储 | 声明需求后取得可用环境，能发布、运行、扩缩和保留数据 |
| **公司接口难访问** | 编写接口调用和业务组合逻辑 | 已受管控接口的授权、凭据、系统适配和事件接收能力 | 获得按服务授权的接口目录、实际代理调用和 Webhook 接入 |

不是重新建设公司已有的鉴权和接口管控体系，也不是绕过审批。平台承接这些体系的对接，并将已获批准的能力供给业务团队。

## 2. 产品定位：借鉴小程序的分工，而不是复制一个应用商店

**CrewStation 是面向团队的数字人构建、发布与运行平台。** 团队开发业务应用，平台提供身份、接口、计算和数据资源，并支持通过 Agent 对话持续修改应用。

“小程序”在这里是分工类比：公共平台统一，业务应用各自建设。不要求使用微信技术，不要求所有应用是移动页面，也不把完整数字人限制成一个短时函数。

| 参与方 | 负责什么 | 不负责什么 |
|---|---|---|
| 装备／平台维护者 | 对接公司体系，提供授权接口、运行与数据资源、部署升级、安全和基础运维 | 不承接所有团队的业务功能，不强制统一业务流程 |
| 业务团队 | 定义数字人意图、业务页面、产品知识、处理规则、检视点和使用效果 | 不从零申请和搭建每一套公共基础设施 |
| 数字人维护者 | 维护代码、版本、数据结构及业务质量，对正式发布负责 | 不能通过上传包或提示词自行扩大权限 |
| 意图创建与修改 Agent | 根据用户意图创建和修改数字人应用自身，完成页面、业务逻辑、测试与调试，并通过受控平台接口提交发布请求 | 不直接取得平台管理权限，不自行批准生产授权；发布仍遵循平台规则 |
| 业务执行 Agent | 由数字人业务服务按需调用，分析和处理具体业务对象，完成定位、检视、代码修改等任务并返回约定结果 | 不直接接管公司 Webhook，不替代必要人工审核，不因执行任务取得应用维护权限 |

**角色按工作对象区分，不按是否写代码区分。** 意图创建与修改 Agent 面向“创建和修改数字人应用”，业务执行 Agent 面向“完成数字人承接的业务任务”。例如，前者开发问题单处理系统的页面和流程；后者由该系统调用，定位问题单所涉及的产品代码缺陷。两者都可能编写代码，但不是同一个职责。[S3]

两类角色可以复用同一套底层 Agent 引擎、适配器和执行资源池；各自的实例、会话、工作区绑定与权限仍须分开。这里不要求增加两套独立的 Agent 平台。

“主 Agent、分析 Agent、编码 Agent、审核 Agent”描述任务内分工，不是另外四种平台产品。两类用途都可以在一个任务环境中组织这些角色。主 Agent 或业务程序决定下一步，普通程序实现的任务执行器负责排队和可靠执行；平台不强制每个流程都增加主 Agent。

与 Agent Workflow 的关系：本项目不以重新实现统一业务工作流为目标。Agent Workflow 或其他工作流工具可以作为某个业务应用的实现选择；平台提供其接入和运行条件，不强制所有数字人依赖同一套编排框架。

## 3. 已明确的产品原则

### 3.1 以数字人业务服务和 Agent 为中心

数字人不是只有聊天窗口，也不是只有底层沙箱。它可以有页面、API、事件处理、业务数据库、文件以及独立身份。架构与产品界面应首先让人看到业务服务和 Agent，沙箱用于表达它们的隔离与运行边界。

**一个服务运行单元承载一个业务服务；一个任务执行环境覆盖一项持续工作，关联一个或多个代码仓执行环境，并顺序运行多个 Agent 和命令子任务。** 不再要求一个任务环境在整个生命周期只能承载某一个 Agent。首版默认一个前台子任务在运行，共享可写工作区保持单写；任务执行器、预览等必要辅助进程可以存在。代码仓环境由平台关联管理，不要求嵌套创建容器。

子任务结束只结束该次执行；取消子任务、暂停环境、关闭任务是三个不同动作。任务级工作区、文件产物和执行记录持续保留，主 Agent 可在授权范围内直接读取真实文件、差异与日志。[S5]

### 3.2 公共条件统一，业务实现不统一

首个模板可以统一技术栈，但平台协议不应限定所有团队只能使用一种语言或 Agent。统一的是身份、资源、接口契约、发布与管理要求，不是每个团队的界面与工作步骤。

### 3.3 确定性动作程序化，Agent 最小化使用

获取问题单、拉代码、创建 MR、投递事件、管理发布等明确动作由程序完成。Agent 聚焦需要理解和判断的任务，执行输入输出要有契约。流水线全绿不等于修改正确，商用代码仍按要求审核。[S1]

### 3.4 体验即效率，开发与运行不能脱节

创建业务服务时自动在指定托管 Group 下创建 Project，写入初始源码，并分配稳定 URL。新建和已运行应用都能按需拉起意图创建与修改会话：准备任务环境、应用代码、获授权的数据绑定及真实预览，再运行所需 Agent 和命令。修改后的源码就是预览使用的源码；完成后自动入库，并按项目规则发布最终固定提交，不把开发进程改个标签当成正式服务。[S5][S6]

### 3.5 小时级业务改进不应被公共发布流程重新拖慢

在已经批准的身份、权限和资源范围内，团队可以自行构建、验证、发布和回退。新增敏感权限、扩大资源或执行破坏性数据变更，进入对应审核，不把所有日常改动都变成装备排期。

### 3.6 源码和数据长期存在，计算环境按需重建

每逻辑业务服务绑定一个公司托管 Project；preview/prod、运行副本和历次发布不重复建仓。仓库保存正式源码历史，工作区检查点补充尚未提交的修改，数据资源独立保留。重新修改应用不依赖某个旧 Agent 或容器仍在运行。已有应用默认以目标环境实际部署的提交为基线，另建修改分支和工作区；选择其他基线时明确展示差异。[S6]

数据库连接是修改环境的正式能力。开发读写、受控真实数据诊断和批准后的生产变更分别授权，不能用“有预览环境”代替数据接入，也不能将正式服务的全部权限默认交给 Agent。

## 4. 核心用户场景

### 场景 A：创建项目，通过对话开发数字人

用户输入名称、模板和业务意图。平台先记录项目、服务和稳定地址，再以受控身份在配置的公司 GitLab 兼容 Group 下自动创建 Project，提交模板初始代码并保存仓库绑定。仓库、URL、数据、预览和 Agent 的准备状态分别可见。

平台建立 DevSession 与长周期 TaskEnvironment，拉取应用仓库，按模板分配并绑定开发数据库和文件空间，启动真实 Demo。意图创建与修改 Agent 按需组织分析、编码、测试命令和审核等子任务。左侧显示对话、子任务、文件变化和检查结果，右侧预览读取同一工作区。

在用户或项目已有授权内，满足完成契约与检查条件后自动提交、推送并继续发布；需要额外批准时等待该节点，批准后自动续行。初始 Demo 不依赖第一轮模型成功；一个修改工作区默认一个写入者。

### 场景 B：上传 ZIP 即部署，并能继续开发

用户上传符合协议的源码包。新服务自动建仓并将导入源码写入初始历史；已有服务在原仓库创建受控变更，不新建重复仓库、不覆盖他人的工作区。原包与安全检查、源码提交、构建和发布分别记录。

ZIP、对话修改和编辑器改动共用“检查点／修改分支 → 远端确认提交 → 固定最终源码 → 干净构建验证 → 发布”的流程。授权和检查满足时自动推进；缺少托管权限、资源或必要批准时明确阻塞。首版不承诺任意 ZIP 或所有语言，静态产物包仍是后续模式，不冒充完整源码项目。

### 场景 C：服务只看到、也只能调用自己的公司接口

每个数字人服务在指定环境中绑定自己的服务账号。平台按操作和资源范围生成 OpenAPI 文档；Swagger 只显示该服务获准使用的接口及限制。代理实际调用时再次鉴权，凭据不下发到浏览器或用户镜像。看文档与以服务身份调试是两项不同权限。

### 场景 D：事件驱动的问题单数字人

公司 Webhook 进入接入代理，经过验签、去重和可靠投递后交给数字人业务服务。服务创建或找到对应业务任务的 TaskEnvironment，准备多个代码仓执行环境，在其中顺序运行分析 Agent、编码 Agent、编译测试命令、审核 Agent及必要修复。子任务共享任务现场，不默认共享全部模型对话。

主 Agent 或业务程序可以直接查看报告、文件、差异和命令结果，再决定后续步骤。业务服务取得代码与方案，按规则提交 MR，并处理流水线及检视事件。业务执行 Agent 不直接接收公司原始 Webhook或承担系统数据同步。外部反馈到达时，可恢复尚未关闭的任务，或基于保留记录建立明确关联的新任务。

### 场景 E：有状态数字人的日常更新

数字人使用独立业务数据库和文件空间。用户对运行中的应用发起“意图修改”时，平台读取该服务的仓库绑定、当前发布 SHA 和数据绑定，新建独立修改会话及任务环境，拉取指定代码、启动预览，并提供获授权的业务数据访问。

默认使用该应用的开发库或数据副本；需要真实数据诊断时可按批准范围连接业务库或只读副本；生产写操作和迁移使用专门授权及受控任务，不默认给修改环境生产写权。预览关闭生产定时任务、真实消息消费和通知等副作用。

修改完成后自动入库并按策略部署最终提交，正式服务在切换前继续运行。数据库迁移独立记录；独占文件状态按维护窗口发布。任务环境全部回收后，代码仓、业务数据和必要检查点仍在，下一次意图修改可以重新建立工作环境。

### 场景 F：空集群安装与公共平台升级

管理员向一个网络、DNS 和节点已正常的 Kubernetes 集群提供配置与发行包。安装器检查入口、存储、镜像、身份、公司代码托管 Group 与权限等前置条件，分阶段安装依赖与平台，执行自动建仓、数据库、文件、预览、顺序子任务、代码入库及发布的真实验收。公司权限仍需实际获得；未连接的能力明确标为待配置。

平台升级不要求所有业务数字人一起改版；Agent 环境升级默认作用于新任务，旧任务按既定版本结束。备份恢复、撤权和数据迁移不与普通镜像回退混为一谈。

## 5. 需求基线

| 编号 | 要求 | 完成判据摘要 |
|---|---|---|
| R01 | 平台与业务应用分工，三大痛点有实际供给 | 团队可获得接入、资源和接口，不只拿到文档 |
| R02 | 项目创建即分配稳定 URL，启动可编辑 Demo | 地址稳定，状态真实，Demo 来自项目源码 |
| R03 | 意图驱动、插件化构建与对话开发 | SDK／CLI／MCP／控制台调用同一能力，支持调试与发布 |
| R04 | 意图创建与修改 Agent 与业务执行 Agent 分离 | 创建／修改应用与执行具体业务的职责明确；工作对象、身份、会话、权限、生命周期可区分 |
| R05 | 一服务一运行单元；任务级环境复用、多仓关联 | 同一任务可顺序执行多个 Agent／命令，子任务结束不销毁环境；共享工作区保持单写 |
| R06 | ZIP 安全导入、入库与统一构建发布 | 新项目建仓、已有项目形成变更；最终源码固定，失败不覆盖旧版 |
| R07 | 业务服务独立发布、路由与版本管理 | 项目 URL 稳定，新旧版本可验证切换 |
| R08 | 网关负责流量，控制面不搬运全部业务数据 | 管理 API 重启不导致已部署应用重建 |
| R09 | 数字人账号、环境与运行身份绑定 | 不能靠自报请求头冒充服务 |
| R10 | 操作＋资源＋环境的接口授权 | 越权、跨项目、批量和列表旁路均被拒绝 |
| R11 | 权限化 OpenAPI 与 Swagger | 文档服务端裁剪，实际代理规则一致 |
| R12 | 公司 API 代理与事件接入 | 受控凭据、可靠投递，事件先到业务服务 |
| R13 | 调试与委托权限收窄 | 看文档不等于可执行，Agent 不继承全部生产权限 |
| R14 | Serverless 式资源管理与任务生命周期 | 任务上下文与计算租约分离，支持预热、暂停、恢复和关闭；子任务与环境分别管理 |
| R15 | 租户、代码、网络和供应链隔离 | 用户代码不能接触平台管理凭据或绕过受控接口 |
| R16 | 业务 PostgreSQL 资源供给 | 项目／环境独立数据库和账号，与平台库隔离 |
| R17 | 对象文件存储及必要持久卷供给 | 实际存储权限隔离，支持所声明的访问模式 |
| R18 | 数据资源、绑定与程序版本解耦 | 发布、暂停、删除旧版本不误删业务数据 |
| R19 | 有状态发布、迁移与可判定回退 | 兼容迁移，破坏性操作审批，不能回退时明确阻塞 |
| R20 | 执行分析与知识积累 | 记录有来源，候选经验经验证后发布并按权限召回 |
| R21 | 空集群一键安装、离线与可恢复安装 | 缺条件不伪成功，失败重试不重建或删除已有数据 |
| R22 | 平台、应用、环境、策略分别升级 | 版本边界、兼容矩阵与回退边界可验证 |
| R23 | 长任务、子任务与会话可靠性 | 断线、控制器重启、步骤失败、重复事件不误删现场或重复副作用 |
| R24 | 观测、审计、配额和容量验证 | 能定位运行、权限、资源和发布问题，不虚报性能 |
| R25 | 模板与运行后端可替换 | 首版单一实现，但不让业务协议绑死某个 Agent |
| R26 | 数据保留、备份和单项目恢复 | 真实恢复验证，不为恢复一个项目回退其他项目 |
| R27 | 预览与正式环境隔离 | 身份、数据、授权和发布状态分开 |
| R28 | 不可变产物和完整变更记录 | 仓库 Project ID、最终提交 SHA、镜像、配置、契约、任务与迁移版本可追溯 |
| R29 | 长周期任务执行环境及独立生命周期 | 顺序子任务共享任务现场；取消子任务、暂停环境、关闭任务分别可操作 |
| R30 | Agent 与命令两种子任务的统一执行管理 | 独立会话、输入输出契约、退出状态、重试和步骤预算；主 Agent 或程序可组织执行 |
| R31 | 主 Agent 读取真实环境文件与结果 | 经授权工具读取多仓文件、差异、报告和日志，区分实时视图与检查点，不依赖子 Agent 自述 |
| R32 | 一业务服务一托管 Project，创建时自动初始化 | 指定公司 Group 下幂等建仓；源码入库，绑定持久；权限不足、冲突和部分失败可恢复 |
| R33 | 运行中应用可随时意图修改 | 读取实际部署基线、拉取应用仓库、建立修改分支和任务环境，启动 Agent／命令及预览 |
| R34 | 修改环境连接对应业务数据库和文件 | TaskDataBinding 明确资源、授权、模式和期限；支持开发调试及批准的真实数据访问 |
| R35 | 修改完成自动代码入库与受控部署 | 自动提交／推送，按规则合入和发布最终 SHA；保存成功与上线成功分开，失败保留旧版 |
| R36 | 多修改会话与发布并发可控 | 独立分支／工作区，合入与上线前检查基线；按服务环境协调发布并去重事件 |
| R37 | 仓库、任务现场与数据在回收后可恢复 | 回收计算不删仓库和业务数据；未提交代码有检查点，恢复时重新授权并保留来源 |

## 6. 范围与首版边界

### 6.1 首版必须打通的闭环

一个业务团队可以：自动建仓并创建真实 Demo；通过意图创建与修改 Agent 对话构建；连接对应的获授权数据库和文件空间；在同一 TaskEnvironment 内顺序运行分析、编码、测试和审核；完成后自动代码入库并按策略发布。计算环境回收后，对已运行应用仍能随时重新进入意图修改。

业务侧可以取得按服务授权的公司接口文档，通过代理调用接口，处理 Webhook，并在长周期任务中关联两个代码仓环境完成多个子任务。执行结果可追溯，经确认的经验可用于后续工作。

管理员可以：在合格的空 Kubernetes 集群上安装；对平台和业务分别更新；备份并恢复一个项目；撤销权限且不因业务版本回退恢复旧授权。

### 6.2 有意限制

| 范围 | 首版取舍 |
|---|---|
| 应用框架 | 先提供一个 React＋Fastify 源码模板及约定构建协议；其他语言保留容器与适配边界 |
| Agent | 先验证并接通一个适配器，不同时接十种 CLI |
| 任务环境 | 首版支持一个环境顺序运行多个角色 Agent 与命令；不要求首发通用 DAG 和共享目录并行写入 |
| 源码托管 | 一种公司 GitLab 兼容接入，自动建仓入库为首版必需；不自建第二个公司代码平台 |
| 数据 | PostgreSQL、S3 接口对象存储、一种受限持久卷模式 |
| 环境 | Docker 用于本地验证；Kubernetes 是组织部署目标 |
| 业务工作区 | 默认单写入者，后续再扩展多人实时协同 |
| 公共接口 | 先接问题单、代码仓、流水线的必要操作，不声称全公司接口立即可用 |
| 知识 | 先做执行记录、候选提取、验证发布和召回，不自动改写全局知识 |
| 弹性 | 先把生命周期与配额管好，不要求所有服务缩容到零 |

### 6.3 非目标

不重建公司 SSO、上游 API 管控和基础云；不通过共享高权限账号绕过限制；不构建固定所有业务步骤的超级工作流；不把应用目录当成完整平台；不承诺通用 ZIP 自动适配一切项目；不首发全套 Istio、Kafka、服务网格和多语言构建生态；不承诺任意有状态应用无停机、无损回退；不把内部工具快速迭代等同于放松商用交付质量。

## 7. 建议的总体技术路线

| 范围 | 讨论形成的候选基线 | 选择理由／必须验证的部分 |
|---|---|---|
| 控制面与开发工具 | TypeScript、Node.js LTS、Fastify、TypeBox、OpenAPI | 统一契约与 SDK；具体版本需冻结 |
| 控制台 | React、Vite、shadcn/ui | 对话、预览、发布、授权和运行管理 |
| 元数据与后台任务 | PostgreSQL、Drizzle、pg-boss | 减少首版基础组件；外部副作用仍需幂等 |
| 网关与组织部署 | Traefik、Gateway API、Kubernetes、Helm | 流量与管理分离；入口与 CRD 升级验证 |
| 沙箱与任务执行 | OpenSandbox、OpenCode 适配器、TaskRunner 模块 | 任务级生命周期、顺序子任务、多仓工具、隔离与恢复需要原型 |
| 源码托管 | 公司 GitLab 兼容服务＋SourceControlProvider | 建仓、Git 读写、分支和事件逐项验证；不假定具备全部 GitLab API 或 CI |
| 构建与数据 | BuildKit、CloudNativePG、S3 存储；内置对象存储候选 SeaweedFS | 固定产物；数据库与对象权限、备份需验证 |
| 公司身份 | 现有体系适配；OIDC/SAML 在可用时优先 | Keycloak 只作为开发或桥接候选，不强制替代公司体系 |
| 执行分析 | 平台事件＋OpenTelemetry；需要时加入 pgvector | 业务事实与可采样观测分离 |

Knative、OPA、Temporal、Buildpacks、gVisor/Kata、Longhorn 等保留为条件性选项。哪些属于生产隔离前置条件、哪些属于后续增强，依据首轮验证和公司环境决定，不把选项列表直接变成强制部署清单。

## 8. 交付与衡量方式

不预设未经验证的并发数、节省比例或研发周期。先证明完整链路，再记录环境与测量方法。

| 维度 | 应记录的证据 |
|---|---|
| 使用与迭代 | URL 分配时间、Demo 冷／暖启动时间、对话到预览更新时间、构建与发布时间 |
| 接入 | 接口从登记到授权可用的过程，团队需人工协调的环节 |
| 安全 | 服务之间、开发与生产之间的越权测试；撤权实际生效时间 |
| 稳定性 | 会话重连、任务续接、发布失败保留旧版、资源回收测试 |
| 持续修改 | 自动建仓、子任务现场复用、修改环境重建、数据接入、远端入库和固定 SHA 发布全过程 |
| 代码保留 | 环境回收后仓库与未提交检查点可恢复；代码入库失败和部署失败分别可定位 |
| 数据 | 服务替换后数据保留，独立项目恢复，备份恢复时间与数据窗口 |
| 运维 | 空集群安装、离线安装、升级中断重试和卸载保留数据的证据 |

涉及延迟、RPO、RTO、撤权窗口和容量的具体承诺，在受控环境测试后写入发行版本，而不是在提案中填入想象数字。

## 9. 风险与评审需要确认的事项

| 风险／问题 | 处理原则 |
|---|---|
| 公司体系无法通过标准协议接入 | 明确适配器和审批依赖；模拟接入与真实接入分开验收 |
| 用户代码、构建脚本或 Agent 越权 | 独立工作负载、受控凭据、出站限制、配额和资源级授权 |
| 沙箱／Agent 候选不能支持跨环境工具或恢复 | 首轮原型验证，接口边界不绑定候选的内部实现 |
| 共享数据库或对象存储的隔离不足 | 实际账号与存储策略验证；必要时独享资源 |
| 有状态发布不可无停机回退 | 显式迁移模式、兼容性检查、备份恢复流程 |
| 组件太多导致首版不能交付 | 五个自研常驻服务，模块不等于微服务；可选组件后置 |
| 过早自动积累错误知识 | 候选、验证、发布分离，记录来源，允许撤回 |
| “一键安装”掩盖基础资源缺失 | 明确前置条件与状态；不虚构 IP、权限、磁盘和模型访问 |
| GitLab 兼容范围与 Group 权限不明 | 托管管理 API、Git 读写、分支保护和事件分别验收；缺权限不能转用管理员凭据 |
| 环境复用留下旧进程或角色权限 | 子任务清理、前台执行槽、受控工具；更强隔离采用只读快照或独立计算实例 |
| 修改环境接触真实数据或触发线上副作用 | 任务级数据授权、只读诊断／受控变更、关闭预览生产消费者；保存与上线分开 |

评审优先确认：工作名与范围；部署目标和公司接入责任；首个数字人场景；三类数据资源套餐；生产隔离基线；首版验收边界。详细待决项见 Design，执行任务见 Plan。

## 10. 结论

**CrewStation 不是替所有团队开发一套共同业务应用，而是把团队自己拿不到的接入条件和运行资源提供出来，让团队能构建、调试、发布并持续改进自己的数字人。**

提案成立的标志不是平台功能很多，而是一个团队能在不重复协调全部基础设施的情况下，把自己的想法变成可持续运行的业务服务；平台维护者也能独立升级公共能力，不要求所有团队同步改版。
