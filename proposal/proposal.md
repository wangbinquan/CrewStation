## 1. 要解决的问题

**团队已经可以借助 AI 开发自己的工作台，但从“代码写出来”到“整个团队持续使用”，仍然缺少基层团队难以自行获得的公司级接入条件和运行资源。**

前期实践从分发 Agent、Skill、MCP 等套件开始。套件落到个人本地后，使用情况难以观察，改进留在个人环境，公共版本分发和兼容又形成额外管理动作。问题不是应该禁止个人分叉，而是团队缺少将个人优势汇合、共同使用和持续改进的载体。[S1][S3]

两个团队根据各自业务建设了工作台。由懂业务、懂 AI 的成员牵头，大家围绕同一个平台提出问题并改进，部分问题能够小时级兑现。用户观察到其中一个平台每周改版，持续融入团队的新想法。这些是实践观察，不是经过统计验证的提效倍数。[S3]

**组织提效需要共同改进的工作方式，但不必要求所有团队使用同一个业务应用。** 装备应提供共同的接入与运行条件，业务团队保留对页面、流程、产品知识和 Agent 使用方式的决定权。[S1][S3]

### 1.1 用户构建数字人的三大痛点

| 痛点 | 基层团队已经能做的事情 | 团队仍难以自行获得的条件 | 平台应提供的结果 |
|---|---|---|---|
| **认证鉴权难接入** | 写出页面和服务 | 公司已有身份体系的应用接入资格，以及数字人账号、运行身份和权限映射 | 网关统一完成用户鉴权并把身份随请求下发，业务不写登录代码；数字人有独立的工作负载身份与受控权限 |
| **部署／运行资源难获得** | 编写业务服务与 Agent 逻辑 | CPU 服务部署资源、Agent 执行资源、代码环境、数据库和文件存储 | 声明需求后取得由平台调度的服务容器与任务容器，能发布、运行、扩缩和保留数据 |
| **公司接口难访问** | 编写接口调用和业务组合逻辑 | 已受管控接口的授权、凭据、系统适配和事件接收能力 | 管理员接入的接口目录按开放策略可见即可调；公司事件经事件中心推送到业务服务 |

不是重新建设公司已有的鉴权和接口管控体系，也不是绕过审批。平台承接这些体系的对接，并将已获批准的能力供给业务团队。

## 2. 产品定位：借鉴小程序的分工，而不是复制一个应用商店

**CrewStation 是面向全公司各团队的数字人构建、发布与运行平台。** 团队在平台提供的开发容器中借助 Agent 开发业务应用，平台提供身份、接口、计算、数据与发布条件。设计目标是服务整个企业：数百个数字人服务并发运行、数百节点规模的 Kubernetes 集群；所有选型与设计按这个目标评估。[S7]

“小程序”在这里是分工类比：公共平台统一，业务应用各自建设。不要求使用微信技术，不要求所有应用是移动页面，也不把完整数字人限制成一个短时函数。

| 参与方 | 负责什么 | 不负责什么 |
|---|---|---|
| 平台维护者（管理员） | 对接公司身份并在网关统一鉴权；开发并发布 API proxy 与 EventProducer 接入容器；配置接口开放策略并审批定向申请；提供运行与数据资源、配额、部署升级、安全与基础运维；保证控制面高可用 | 不承接业务功能，不编排业务团队的开发过程 |
| 业务团队（项目负责人与开发者） | 定义数字人意图、页面、产品知识、处理规则与使用效果；在开发会话中自行启动 Agent 开发，自行决定分支与协作方式；负责人晋级 prod、审批本项目的数据访问 | 不从零申请和搭建公共基础设施；不写登录鉴权 |
| 团队成员（应用使用者） | 以公司身份经网关使用数字人，反馈问题，让工作台跟着团队实际需要持续修改 | 不需要理解平台概念，不接触平台管理界面 |
| 意图创建与修改 Agent | 在开发容器内按开发者指令创建和修改数字人应用自身的源码、页面与业务逻辑；可经操作 MCP 调用内部 API 与发布工具 | 不取得平台管理权限；不能绕过平台自行打标签发布 |
| 业务执行 Agent | 由数字人业务服务经子任务契约层按需调用，分析和处理具体业务对象，完成定位、检视、代码修改等任务并返回契约产物 | 不直接接收公司 Webhook，不替代必要人工审核，不因执行任务取得应用维护权限 |
| 接入容器（API proxy／EventProducer） | 由管理员开发；出向纯转发公司接口，入向把公司回调转成平台事件 | 不做授权判定（由网关承担），不持有长期上游凭据（由 cs-auth 按需下发） |

**角色按工作对象区分，不按是否写代码区分。** 意图创建与修改 Agent 面向“创建和修改数字人应用”，业务执行 Agent 面向“完成数字人承接的业务任务”。例如，前者开发问题单处理系统的页面和流程；后者由该系统调用，定位问题单所涉及的产品代码缺陷。两者都可能编写代码，但不是同一个职责。[S3]

两类用途复用同一套 Agent 驱动、任务容器和执行资源；各自的实例、会话、工作区绑定与权限仍须分开。平台不定义 Agent 的角色维度：不存在主 Agent、分析 Agent、编码 Agent、审核 Agent 这类平台概念，业务子任务只携带 agentProfile 与输入输出契约，下一步做什么由开发者或业务程序决定。[S7]

与 Agent Workflow 的关系：agent-workflow 是本项目复制改造的代码来源，特别是 OpenCode 与 Claude Code 两个运行时驱动和代码托管客户端；本项目不修改 agent-workflow 仓库。长期看它也是接入平台的一个业务应用，接入时其自带的 OIDC 登录需改为使用网关下发的身份；接入时间后置，不在首版范围。业务应用是否使用 Agent Workflow 或其他工作流工具，由业务自行选择，平台不强制统一编排框架。[S7][S8]

## 3. 业务数字人能力全景与接入约定

平台向一个业务数字人提供的能力必须可被发现、可按约定接入，不能让每个团队从对话记录里翻找。这里给出全景，具体接口与约定在 Design 定义。每个项目模板自带的 `CONTRIBUTING.md` 不复制这些内容，只指向平台的能力说明接口。[S7]

这张全景对应原稿提出的五项装备供给：统一鉴权、统一接口调用、Agent 执行资源池、服务部署环境、Agent 运行环境。表中“用户身份”对应统一鉴权；“调用内部 API”“接收公司事件”“对其他数字人提供 API”对应统一接口调用；“配额”与“业务执行 Agent”分别对应执行资源池与运行环境；“稳定地址与路由”“数据资源”“发布与环境”对应服务部署环境。[S1]

**接入只靠约定，不提供 SDK。** 约定包括环境变量、请求头、处理路径、网关地址与 Manifest 字段，与实现语言无关。开发说明、接口示例和环境使用方式要足够清楚，让团队以及帮助团队开发的 AI 能直接照着做。[S1][S7]

| 能力 | 平台提供方式 | 业务接入约定 |
|---|---|---|
| 稳定地址与路由 | 创建项目即分配；preview 与 prod 两个环境；网关按 Host 转发页面与 API | Manifest 声明服务端口与健康检查路径 |
| 用户身份 | 网关完成登录鉴权，向服务注入可信身份头与平台签名令牌 | 读取约定请求头或验签令牌；不写登录代码；业务内权限规则自己实现 |
| 调用内部 API | 接口目录、默认开放与定向开放、网关操作级放行、API proxy 纯转发 | 经约定网关地址调用；服务身份由工作负载身份自动携带；可用接口见权限化 Swagger |
| 接收公司事件 | cs-events 事件分发中心推送 | Manifest 声明订阅的事件类型与处理路径；处理需幂等 |
| 数据资源 | PostgreSQL、S3 对象存储、单写持久卷，按套餐供给并以 DataBinding 注入 | 约定环境变量读取连接信息；迁移命令在 Manifest 声明 |
| 业务执行 Agent | 长驻任务容器、TaskRunner、子任务契约层 | 经约定平台 API 以服务身份创建任务、提交子任务、读取产物 |
| 发布与环境 | 平台标签、固定提交构建、preview 部署、负责人晋级 prod；配置与 Secret 引用 | Manifest 的 build、service、release 段 |
| 对其他数字人提供 API | 登记进同一接口目录，按开放策略供他人申请与调用 | Manifest 声明暴露的 OpenAPI |
| 观测与追溯 | 日志、指标、任务级 traceId 链路 | 按约定输出日志；traceId 由平台在任务与事件中携带 |
| 配额 | 每数字人并发任务配额 | 超额请求被拒绝并有明确状态 |
| 开发会话 | 长驻开发容器、多 Agent、Web 终端、编辑器、预览、Swagger 调试、能力说明页 | 模板 `CONTRIBUTING.md` 指向能力说明 MCP 与工作台页 |
| 源码托管 | 自动在公司 GitLab 兼容 Group 下建 Project；标签由平台创建 | 分支策略由使用者自定 |

**能力说明接口**：平台以两种形式实时反映最新平台能力与本服务现状，即已获授权的接口、数据绑定、订阅、配额与环境。一是工作台内的能力页，供人阅读；二是能力说明 MCP，供开发容器内的 Agent 读取。它与提供发布、调用内部 API 等动作的操作 MCP 是两个服务。[S7]

## 4. 已明确的产品原则

### 4.1 以数字人业务服务和 Agent 为中心

数字人不是只有聊天窗口，也不是只有底层沙箱。它可以有页面、API、事件处理、业务数据库、文件以及独立身份。架构与产品界面应首先让人看到业务服务和 Agent，容器用于表达它们的隔离与运行边界。

**一个服务运行单元承载一个业务服务；一项任务对应一个由平台调度的长驻容器，容器内常驻 TaskRunner，控制面经它启动 Agent、执行命令、读取文件与取消执行。** 意图开发在容器内启动一个或多个意图创建与修改 Agent，可以并行，工作区如何共享由使用者自行决定；业务执行通过子任务契约层组织，多个子任务可并发，由业务程序协调。[S5][S7]

意图任务只有运行与释放两种状态，释放即回收容器与其存储；业务任务默认相同，可在创建任务时选择持久卷持久、容器可重建的模式，并获得暂停与恢复能力。[S7]

### 4.2 公共条件统一，业务实现不统一

首个模板可以统一技术栈，但平台协议不应限定所有团队只能使用一种语言或 Agent。统一的是身份、资源、接口契约、发布与管理要求，不是每个团队的界面与工作步骤。

### 4.3 确定性动作程序化，Agent 最小化使用

获取问题单、拉代码、创建 MR、投递事件、管理发布等明确动作由程序完成。原稿对问题单数字人提出三条原则：Agent 调用最小化，能程序化的都程序化；Agent 任务原子化，一次做好一件事，执行过程由程序组织；输入输出契约化，交付什么要明确约定并由程序校验，不能只看 Agent 说一句“完成了”。平台以业务子任务契约层支撑这三条，但不强制业务采用。流水线全绿不等于修改正确，商用代码仍按要求审核。[S1]

### 4.4 体验即效率，开发与运行不能脱节

创建业务服务时自动在指定托管 Group 下创建 Project、写入最小样例模板、分配稳定 URL 并部署到 preview。新建和已运行的应用都可开启开发会话：先在下拉框选择工作分支，界面提示当前部署的提交、当前分支以及部署落后分支多少个提交；随后拉起开发容器、预览与获授权的数据绑定，开发者启动所需的 Agent。修改后的源码就是预览使用的源码。发布是独立动作，见 4.8。[S5][S6][S7]

### 4.5 小时级业务改进不应被公共发布流程重新拖慢

在已经批准的身份、权限和资源范围内，团队可以自行构建、验证、发布和回退。新增定向接口、扩大资源或执行破坏性数据变更，进入对应审批，不把所有日常改动都变成装备排期。

### 4.6 源码和数据长期存在，计算环境按需重建

每逻辑业务服务绑定一个公司托管 Project；preview／prod、运行副本和历次发布不重复建仓。仓库保存正式源码历史，业务数据在独立的数据资源中，两者都不随任务释放而消失。开发容器与其持久卷随任务释放回收，未推送到远端的内容由使用者负责，界面在释放前提醒。再次开发时从所选分支重新建立容器。[S6][S7]

数据库连接是开发会话的正式能力。开发库读写、获批真实库只读诊断和受控生产变更分别授权，后两种由项目负责人审批；不能用“有预览环境”代替数据接入，也不能把正式服务的全部权限默认交给 Agent。[S7]

### 4.7 网关统一鉴权，业务不写登录

网关完成用户认证后，向业务服务注入可信的明文身份头和平台签名的令牌；业务服务不做任何登录鉴权动作，直接读取身份。页面与数据的权限规则归业务自身实现，平台只保证身份可信。服务对内部 API 的调用以 Kubernetes 工作负载身份识别，不信任业务代码自报的请求头。[S7]

### 4.8 发布是独立动作，git push 不等于发布

只有经平台创建的 `v大版本.小版本.patch版本` 标签触发发布，手工推送的标签不触发。入口有两个：开发者在工作台点发布，或 Agent 调用操作 MCP 中的发布工具。发布前检查工作区：有未提交内容则提示、不打标签；干净则由平台代为推送当前分支，再创建标签。标签触发固定提交的构建并部署到 preview 环境；晋级 prod 是项目负责人执行的另一个独立动作。发布失败保留旧版本。[S7]

### 4.9 规模目标驱动选型与设计

面向全公司：数百个数字人服务并发运行、数百节点规模；首版单个 Kubernetes 集群，多集群后置；控制面高可用是首版要求；每个数字人有自己的并发任务配额，防止一个人耗尽集群。这些是设计目标而非实测承诺，所有组件选型按此评估，具体性能数字在受控环境实测后写入发行说明。[S7]

### 4.10 公司系统以管理员开发的接入容器承载

出向调用由 API proxy 容器纯转发，入向事件由 EventProducer 容器产生；两者都由平台管理员按与业务服务相同的项目流程开发与标签发布，首版内置 GitLab 格式的 EventProducer 并默认部署。网关按服务工作负载身份与接口开放策略做方法加路径级放行，proxy 不做授权判定；上游凭据由 cs-auth 的凭据服务按需下发，不落在 proxy 配置里。接口默认开放即所有业务可调，定向开放需业务申请、管理员审批。数字人自身的 API 也可登记进同一目录。资源级越权由上游系统或业务把关，平台不做资源级判定。[S7]

### 4.11 执行链路可追溯，知识提取留待未来

一个任务的 taskId 对应一条 traceId 执行链路，链上有多个执行，Agent 的执行过程以 sessionId 记录，traceId 能索引到 sessionId。前台交互的 OpenTelemetry 链路与任务链路在前台触发任务时关联。首版只保留这套追溯能力，不做经验提取与知识版本。[S7]

## 5. 核心用户场景

### 场景 A：创建项目，在开发会话中开发数字人

用户输入名称并选择模板，默认是最小样例模板。平台先记录项目、服务和稳定地址，再以受控身份在配置的公司 GitLab 兼容 Group 下自动创建 Project，提交模板初始代码并保存仓库绑定。作为建议方案，平台以初始提交创建首个 v 标签并部署到 preview，正式地址在负责人首次晋级后生效。仓库、URL、数据、preview 的准备状态分别可见。

开发者开启开发会话。一个项目同时只允许一个开发会话。开发者在下拉框选择工作分支，默认为默认分支，界面显示当前部署的提交、所选分支与落后提交数。平台拉起长驻开发容器、常驻 TaskRunner、检出所选分支，按模板分配并绑定 preview 数据库和文件空间；TaskRunner 按 Manifest 自动启动预览进程并在崩溃后重启，开发者也可以在终端接管。

工作台包含多个 Agent 对话面板、Web 终端、代码编辑器与文件树、预览与发布控制，另有能力说明页和按 preview 授权裁剪的 Swagger 调试页；终端可以留在同一页签，也可以独立页签实现多屏开发。开发者启动一个或多个意图创建与修改 Agent，选择 OpenCode 或 Claude Code 驱动与模型；Agent 通过能力说明 MCP 了解平台能力，通过操作 MCP 调用内部 API 与发布工具。怎么开发、是否分支、如何合并都由使用者决定，平台不协调工作区。

完成后开发者点发布，或 Agent 调用发布工具：平台检查未提交内容，有则提示；干净则代为推送当前分支并创建 v 标签，构建后部署到 preview。项目负责人验证后独立晋级到 prod。关闭会话即释放容器与持久卷，未推送内容丢失，仓库与业务数据保留。

### 场景 B：服务只看到、也只能调用自己获准的内部接口

平台管理员为公司问题单、代码托管、流水线等系统开发 API proxy 项目：Manifest 的 kind 为 APIProxy 并声明暴露的 OpenAPI，走与业务服务相同的建仓、开发会话与标签发布流程。发布后接口登记进目录，管理员把每个接口标记为默认开放，或定向开放给某些业务。

业务开发者在工作台的 Swagger 调试页看到本服务获准的接口并可试调，试调使用服务 preview 环境的授权。业务代码按约定的网关地址调用，网关依据 Pod 的工作负载身份和开放策略做方法加路径级放行，把请求转给 proxy，proxy 从 cs-auth 取得上游凭据后纯转发。定向开放的接口由业务在 Manifest 或控制台申请，管理员审批后可调。资源范围的越权由上游系统或业务自行把关，平台不做资源级判定。数字人服务也可把自己的 API 登记进同一目录，供其他数字人按同样规则申请与调用。

### 场景 C：事件驱动的业务数字人

公司 GitLab 的 Webhook 进入默认部署的 GitLab 格式 EventProducer，验签并归一化后交给 cs-events 事件分发中心；事件中心去重、持久化并可靠推送到业务服务在 Manifest 中声明的处理路径，失败重试并有死信。其他公司系统的事件由管理员按同样的项目流程开发新的 EventProducer 接入。

业务服务收到事件后按业务规则以自身服务身份创建业务任务：一个长驻任务容器，默认持久卷跟随容器，也可在高级参数中选择持久卷持久、容器可重建，以获得暂停恢复能力。业务程序通过子任务契约层提交 Agent 子任务与命令子任务，可并发，由业务程序协调；每个子任务有 agentProfile、输入输出契约、退出状态和 attempt 记录。业务程序经 TaskRunner 直接读取报告、文件、差异与命令结果，决定后续步骤，再经内部 API 提交 MR 并处理后续事件。业务执行 Agent 不直接接收公司原始 Webhook。任务关闭即释放计算与存储，仓库与业务数据不受影响。首版不支持业务服务向事件中心发布自定义事件，也不提供定时触发，定时逻辑由业务自己实现。

### 场景 D：运行中应用的再次开发

数字人已经在 prod 运行并使用独立业务数据库和文件空间。用户对它发起开发会话：选择工作分支，界面提示 prod 与 preview 当前部署的提交、所选分支及落后提交数；平台新建开发容器、检出分支、启动预览，并按 TaskDataBinding 提供数据访问。默认连接该应用的开发库；需要真实数据诊断时申请只读诊断，需要正式数据修正时申请受控生产变更，两者由项目负责人审批；预览关闭生产定时任务、真实消息消费和通知等副作用。

开发完成后发布流程与场景 A 相同：标签部署到 preview，负责人晋级 prod，正式服务在切换前继续运行；数据库迁移独立记录，独占文件状态按维护窗口发布。会话释放后源码、业务数据与发布记录都在，下一次开发重新建立容器即可。

### 场景 E：空集群安装与公共平台升级

管理员向一个网络、DNS 和节点已正常的 Kubernetes 集群提供配置与发行包；本机验证使用 kind 集群，不再提供 Docker Compose 模式。安装器检查入口、存储、镜像、身份、公司代码托管 Group 与权限、模型访问等前置条件，分阶段安装依赖与平台，控制面各服务以高可用形态部署，内置 GitLab 格式 EventProducer 默认部署。随后执行真实验收：自动建仓、最小样例部署、开发会话与多 Agent、标签发布与晋级、事件接入、会话释放后再开发。公司权限仍需实际获得；未连接的能力明确标为待配置。

平台升级不要求所有业务数字人一起改版；任务容器镜像升级默认作用于新任务。备份恢复、撤权和数据迁移不与普通镜像回退混为一谈。

### 场景 F：业务应用接收网关身份

最小样例模板部署后，页面没有任何登录代码：网关完成认证并注入身份头与令牌，样例读取后显示当前是谁。页面内还有一个 Agent 对话框：样例服务以自身服务身份经约定平台 API 创建业务任务、提交 Agent 子任务，并把结果流式显示出来。它同时是新建项目的默认起点和 Plan 中 M5 的验收样例，用来证明身份下发、能力说明与业务执行契约层三件事都能按约定接入。

| R32 | 一业务服务一托管 Project，创建时自动初始化 | 指定公司 Group 下幂等建仓；源码入库，绑定持久；权限不足、冲突和部分失败可恢复 |
| R33 | 运行中应用可随时开启开发会话 | 下拉选择工作分支，界面显示部署提交、当前分支与落后提交数；建容器、预览、数据绑定、启动 Agent；一项目同时一个会话 |
| R34 | 开发会话连接对应业务数据库和文件 | TaskDataBinding 三种模式明确资源、授权、期限；只读诊断与生产变更由项目负责人审批 |
| R35 | 发布为独立标签动作 | 只有平台创建的 v大.小.patch 标签触发；发布前检查未提交内容并代为推送；先部署 preview，再由负责人晋级 prod；失败保留旧版 |
| R36 | 发布并发可控 | 标签顺序、晋级条件与版本比较；迟到版本不覆盖已上线新版本 |
| R37 | 仓库与业务数据在任务释放后保留 | 释放回收容器与持久卷，不删仓库和业务数据；未推送内容由使用者负责且界面提醒 |
| R38 | 规模设计目标 | 数百数字人服务并发、数百节点、首版单集群；选型与设计按此目标评估，压测按此档位报告 |
| R39 | 控制面高可用首版必需 | cs-* 服务多副本、元数据库高可用、网关多副本进入首版验收 |
| R40 | 网关统一鉴权与身份下发 | 网关认证后注入可信身份头与平台签名令牌；业务服务不做登录鉴权；授权规则归业务 |
| R41 | 意图开发工作台与开发会话 | 多 Agent 对话面板、Web 终端（同页签或独立页签）、编辑器与文件树、预览与发布控制、能力说明页、权限化 Swagger 调试页；预览由 TaskRunner 按 Manifest 自动启动 |
| R42 | 双 Agent 驱动 | OpenCode 与 Claude Code 驱动复制改造自 agent-workflow，不修改其仓库；公有云与内部模型一致处理 |
| R43 | 每数字人并发任务配额 | 首版唯一预算；超额请求被拒并有状态；一项目同时一个开发会话 |
| R44 | 接入容器 | API proxy 与 EventProducer 由管理员按项目流程开发发布；proxy 纯转发；上游凭据由 cs-auth 按需下发；内置 GitLab 格式 EventProducer 默认部署 |
| R45 | 接口开放策略与操作级放行 | 默认开放即可调，定向开放需申请且管理员审批；数字人自身 API 可登记；网关按工作负载身份做方法加路径级放行；资源级由上游或业务把关 |
| R46 | 权限化 Swagger 与开发期调用 | 服务端裁剪；工作台内嵌调试页；开发期沿用 preview 授权；Agent 经操作 MCP 调用 |
| R47 | 事件分发中心 | cs-events 接收 EventProducer 事件，去重、持久化、可靠推送到服务声明的处理路径，重试与死信；事件先到业务服务不直达 Agent；首版不支持业务自定义事件与定时触发 |
| R48 | 能力全景与接入约定 | 全景可发现；接入只靠约定不提供 SDK；模板 `CONTRIBUTING.md` 指向说明接口；能力说明 MCP 与工作台页实时反映平台能力与本服务现状；开发说明、接口示例与环境使用方式让团队和 AI 能直接照着做 |
| R49 | 平台角色与审批 | 管理员、项目负责人、开发者三级；负责人晋级 prod 并审批数据访问；管理员审批定向 API 与接入 |

## 7. 范围与首版边界

### 7.1 首版必须打通的闭环

一个业务团队可以：创建项目即自动建仓、分配地址并部署最小样例；开启开发会话，选择分支，在容器内并行使用多个 Agent、终端、编辑器、预览、Swagger 调试与能力说明；连接获批的数据库和文件空间；点发布或由 Agent 调工具打标签部署到 preview，负责人晋级 prod；释放会话后随时再次开启。

业务侧可以：不写登录代码而获得网关下发的用户身份；按开放策略查看并调用内部接口；接收 GitLab 事件；用子任务契约层在长驻任务容器中运行业务执行 Agent 与命令，并读取真实产物。执行链路以 traceId 可追溯。

管理员可以：在合格的空 Kubernetes 集群上以高可用形态安装；开发并发布 API proxy 与 EventProducer；配置接口开放策略并审批定向申请；对平台和业务分别升级；备份并恢复一个项目；撤销权限且不因业务版本回退恢复旧授权。

### 7.2 有意限制

| 范围 | 首版取舍 |
|---|---|
| 应用框架 | 最小样例模板一种，实现语言在评审时确认；其他语言保留容器与约定边界 |
| Agent | OpenCode 与 Claude Code 两个驱动，复制改造自 agent-workflow；不接更多 CLI |
| 任务环境 | 一任务一长驻容器；意图开发多 Agent 并行由使用者协调；业务子任务可并发由业务协调；不做通用 DAG |
| 源码托管 | 一种公司 GitLab 兼容接入，自动建仓与平台打标签为首版必需；本机验证复用已运行的测试 GitLab |
| 数据 | PostgreSQL、S3 接口对象存储、一种受限持久卷模式；数据访问三模式，后两种负责人审批 |
| 环境 | 仅 Kubernetes；本机用 kind 验证；首版单集群 |
| 开发会话 | 一项目同时一个会话；意图任务无暂停；预算只有并发任务配额 |
| 公共接口 | 首版内置 GitLab 格式 EventProducer；API proxy 按管理员接入进度提供；平台只做操作级放行 |
| 事件 | 只接管理员开发的 EventProducer；不支持业务自定义事件与定时触发 |
| 弹性与可用性 | 控制面高可用首版必需；业务服务缩容到零不作要求 |

### 7.3 非目标

不重建公司 SSO、上游 API 管控和基础云；不通过共享高权限账号绕过限制；不编排开发者的开发过程，不管理开发容器内多个 Agent 的工作区共享；不做 ZIP 源码包导入；不做经验提取与知识飞轮，只保留追溯能力；不提供业务接入 SDK，只提供约定；不做 Docker Compose 部署；不做资源级接口授权；不构建固定所有业务步骤的超级工作流；不把应用目录当成完整平台；不首发全套 Istio、Kafka、服务网格和多语言构建生态；不承诺任意有状态应用无停机、无损回退；不把内部工具快速迭代等同于放松商用交付质量。

## 8. 总体技术路线

选型已按 `proposal/tech-evaluation.md` 1.0.0 逐项评估并经用户确认（E01–E22），此处为结论；具体版本在 Plan T0.2 锁定，待验证项对应 M0 原型任务。[S7][S8]

| 范围 | 选型 | 必须验证的部分 |
|---|---|---|
| 控制面语言与运行时 | TypeScript on Bun；Bun workspaces | Bun 长驻多副本服务稳定性、原生模块兼容 |
| 后端框架与契约 | Hono；zod 统一 Manifest、API、事件 Schema 并生成 OpenAPI | Bun 下 WebSocket 与流式行为 |
| 元数据与后台任务 | PostgreSQL 高可用；Drizzle；PostgreSQL 表队列加租约与 fencing token 承载后台任务、多副本协调与 cs-events；首版不引入 Kafka 或 Redis | 目标档位吞吐与锁竞争；多副本续接 |
| 网关 | Traefik 加 ForwardAuth，鉴权与放行决策在 cs-auth；Gateway API | WebSocket 升级；放行决策 p99 时延；备选 Envoy Gateway |
| 用户身份 | OIDC 对接公司 IdP；平台 JWT 由 jose 签发，JWKS 轮换 | 公司 IdP 协议；令牌格式与有效期 |
| 服务身份 | projected ServiceAccount token 绑定 audience，cs-auth 校验 | 提取方式与校验时延 |
| 任务容器 | Kubernetes 原生 Pod、PVC、NetworkPolicy、ResourceQuota，由 cs-controller 直接管理；Pod 与容器即隔离边界，不引入任何额外沙箱层 | Pod 与 PVC 供给时延、预热必要性 |
| TaskRunner | TypeScript；运行时优先 Bun，PTY 不可用则 Node；出向 WebSocket 连接 cs-session | PTY；数百连接的副本迁移 |
| Agent 驱动 | 复制 agent-workflow 的 RuntimeDriver、事件泵与进程管理，OpenCode 与 Claude Code 双驱动，运行方式与 agent-workflow 一致 | 六处依赖反转；版本锁定与模型配置注入 |
| 源码托管 | 公司 GitLab 兼容服务；复制 agent-workflow 的 code-host 客户端并新增建仓、标签、保护标签 API | 公司兼容范围 |
| 构建 | BuildKit rootless 作 Kubernetes Job | 公司集群对 rootless 构建的允许方式 |
| 数据供给 | CloudNativePG；公司已有托管 PostgreSQL 优先接入；对象存储优先公司已有 S3 兼容存储，内置候选待核实许可证 | 高可用切换、单项目恢复、预签名与跨桶拒绝 |
| 控制台 | React、Vite、TanStack Router 与 Query、CodeMirror、xterm.js、嵌入 Swagger UI | 多流式面板与终端并存的性能 |
| 平台 MCP | 官方 MCP SDK，Streamable HTTP，两个独立服务 | 容器内 Agent 的连接鉴权 |
| 观测与追溯 | OpenTelemetry SDK 与 Collector；execution_events 表 | OTel SDK 在 Bun 下的兼容 |
| 发行与安装 | Helm chart；Bun 单文件二进制安装器；本地仅 kind | 离线引导；HA 在多节点集群验证 |

agent-workflow 现有栈为 Bun、TypeScript、Hono、Drizzle、SQLite 默认并有 PostgreSQL provider、React 与 Vite，是复制改造的直接参照。Knative、OPA、Temporal、Buildpacks、Longhorn 保留为条件性选项；gVisor、Kata 等额外沙箱不列为选项。[S8]

## 9. 交付与衡量方式

数百并发与数百节点是设计目标，不是实测承诺。先证明完整链路，再在目标档位记录环境与测量方法。

衡量的顶层问题来自原稿：一个已经能写出工作台的团队，能否取得所需的接入和资源，还是拿到几份文档后仍要逐个协调；一个工作台从开发完成到团队可用，时间花在业务验证还是等待鉴权接入、接口授权和运行环境；工作台上线以后，团队能否在授权范围内持续修改，还是每次改动都重新变成装备的需求和排期。[S1]

| 维度 | 应记录的证据 |
|---|---|
| 使用与迭代 | URL 分配时间、开发会话就绪时间、预览启动时间、标签到 preview 可访问时间、晋级时间 |
| 接入 | API proxy 从开发到业务可调用的过程；定向开放申请审批耗时；团队需人工协调的环节 |
| 安全 | 服务之间的操作级越权测试；伪造身份头与工作负载身份的拒绝；开发与生产之间的越权；撤权实际生效时间 |
| 稳定性 | 会话重连、控制面副本故障切换、元数据库故障切换、发布失败保留旧版、容器回收 |
| 持续开发 | 会话释放后重建、分支选择与部署落后提示、数据接入、标签发布与晋级全过程 |
| 数据 | 服务替换后数据保留、独立项目恢复、备份恢复时间与数据窗口 |
| 运维 | 空集群安装、离线安装、升级中断重试和卸载保留数据 |
| 规模 | 目标档位压测：并发数字人服务数、同时运行的任务容器数、事件吞吐、网关请求量与长连接数 |

涉及延迟、RPO、RTO、撤权窗口和容量的具体承诺，在受控环境测试后写入发行版本，而不是在提案中填入想象数字。

## 10. 风险与评审需要确认的事项

| 风险／问题 | 处理原则 |
|---|---|
| 公司体系无法通过标准协议接入 | 明确适配器和审批依赖；模拟接入与真实接入分开验收 |
| 用户代码、构建脚本或 Agent 越权 | 独立容器、工作负载身份、出站限制、配额和操作级放行 |
| 同一开发容器内多个 Agent 并发冲突 | 由使用者承担；平台只保证容器、配额与发布前的未提交检查 |
| 数百任务容器与控制面长连接的可靠性 | TaskRunner 连接模型、cs-session 多副本、断线补事件，需原型验证 |
| 持久卷供给与回收延迟拖慢会话就绪 | 存储类与预热验证；就绪时间作为衡量指标 |
| 操作级放行不覆盖资源级越权 | 明确由上游或业务把关；接口登记时标注资源语义 |
| 手工 v 标签不触发发布造成误解 | 工作台与 `CONTRIBUTING.md` 明示；手工标签在界面标为未发布 |
| 复制改造 agent-workflow 代码的耦合 | 驱动层对其后端内部依赖需反转；不修改 agent-workflow 仓库 |
| 共享数据库或对象存储的隔离不足 | 实际账号与存储策略验证；必要时独享资源 |
| 有状态发布不可无停机回退 | 显式迁移模式、兼容性检查、备份恢复流程 |
| 组件太多导致首版不能交付 | 五个常驻服务加两个平台 MCP；接入容器走项目流程，不新增常驻服务 |
| GitLab 兼容范围与 Group 权限不明 | 托管管理 API、Git 读写、保护标签和事件分别验收；缺权限不能转用管理员凭据 |
| 开发容器接触真实数据或触发线上副作用 | 数据访问三模式与负责人审批；预览关闭生产消费者与通知 |
| “一键安装”掩盖基础资源缺失 | 明确前置条件与状态；不虚构 IP、权限、磁盘和模型访问 |

评审优先确认：工作名与范围；部署目标与公司接入责任；最小样例模板的实现语言；三类数据资源套餐；生产隔离基线；首版验收边界。选型结论已在 `proposal/tech-evaluation.md` 确认。详细待决项见 Design，执行任务见 Plan。

## 11. 结论

**CrewStation 不是替所有团队开发一套共同业务应用，也不编排团队的开发过程，而是把团队自己拿不到的接入条件和运行资源提供出来：网关身份、内部接口、公司事件、数据资源、任务容器与发布通道，让团队在开发容器里用自己的方式和自己的 Agent 构建、调试、发布并持续改进数字人。**

提案成立的标志不是平台功能很多，而是一个团队能在不重复协调全部基础设施的情况下，把自己的想法变成可持续运行的业务服务；平台维护者也能在数百服务的规模下独立升级公共能力，不要求所有团队同步改版。
