## 1. 来源与确认

- `docs/engineering/implementation-open-questions.md` I16 记录了 Bun 内置 SQL 连接池的错位：09-16 三次；09-23 一天四次，分别在 05:35、07:37、07:44、08:00Z。
- I16 给出三种做法：(a) 升级 Bun，(b) 换 postgres.js，(c) 维持现状。
- 2026-09-23 作者裁定 (b)。按开发规则 §5，这属于非平凡重构，先写 RFC，批准后实施。

## 2. 现状

- **运行时与驱动**：控制面七个进程都是 Bun 1.3.13（Dockerfile 与 CI 锁定），数据库驱动是 Bun 内置的 `SQL`，经 `drizzle-orm/bun-sql` 使用，连接池 `max: 10`。迁移 Job 与测试库也用同一驱动。
- **故障表现**：进程活着，但所有要查库的请求失败或挂起，被存活探针重启，全平台每次不可用 1–16 分钟。
  - 客户端报错：`JSON Parse error`（把别的列当 JSON 解析）、`ERR_POSTGRES_INVALID_MESSAGE`、`ERR_POSTGRES_UNSUPPORTED_INTEGER_SIZE`。
  - 服务端日志：参数里出现 0x00，`SET TRANSACTION ISOLATION LEVEL must be called before any query`，`unexpected EOF on client connection with an open transaction`。
  - 这些说明连接上的收发已经对不上：客户端把 A 查询的回应当成 B 的，或者发出的消息本身错了。TCP 层的丢包只会重传，不会造成这种错乱。
- **诱因**：并发请求集中到达，尤其是新进程刚启动、积压的请求一起涌入时。
  - 09-23 第四次时，共用调试浏览器上有 110 个孤儿页面。
  - 后三次没有孤儿页面：两次是其他会话的 e2e 高峰（每分钟 125–346 个请求），一次是新进程起来 20 秒内。
  - 本机 10 连接／40 并发的八种事务形态压测，复现不出来。
- **已做的缓解**（不治本）：
  - 事务内空闲 60 秒由服务端断开。
  - `/healthz` 走同一连接池、3 秒为界，让探针能发现故障。
  - e73d98e 减少了名册顺带的查询。

## 3. 目标与非目标

目标：

- 所有经由平台代码的 PostgreSQL 连接都改用 postgres.js：七个控制面进程、迁移 Job、测试库、数据模块的建库适配器。Bun 只做运行时，ORM 仍是 Drizzle。
- 行为不变：不改表结构、接口与迁移；会话默认值（事务内空闲 60 秒）、连接池上限 10、就绪探针的语义都保留。
- 用一个能在本机复现的「新进程＋突发并发」脚本，先在旧驱动上跑、再在新驱动上跑，作为对比证据。

非目标：

- 升级 Bun（I16 的 (a)）。放在同一批会混淆原因，另议。
- 引入 PgBouncer 等连接代理、调整数据库高可用方案。
- 顺带改写查询或事务写法。只改为兼容新驱动所必需的地方。

## 4. 待作者确认的问题

| 编号 | 问题 | 建议 |
|---|---|---|
| Q1 | 要不要保留一个环境变量，能随时切回 Bun 内置驱动 | **不保留**。两套驱动并存，要双倍测试，而且类型要在两者之间取交集。回退就是重新部署上一版镜像：本 RFC 不改表结构，回退是安全的 |
| Q2 | 验收的观察期多长 | **24 小时**：本机集群照常多会话使用，外加突发复现脚本对比。满 24 小时没有任何 I16 特征报错，也没有因数据库被探针重启，才置 Done |
| Q3 | 连接池参数要不要趁机调整 | **只保留现有语义**：上限 10、会话默认值不变，另加 10 秒连接超时；其余用 postgres.js 默认值（空闲连接不回收，连接寿命在 30–60 分钟之间随机）。以后要调，按观测再议 |

## 5. 能力影响

不关闭、不收缩任何能力。对外接口、页面、命令行和 Manifest 都不变；数据库表结构与迁移记录不变。本 RFC 不属于开发规则 §5.5 的能力收缩型 RFC。

## 6. 验收标准

| 编号 | 标准 |
|---|---|
| DB-01 | 本地门禁与精确 SHA 的 CI 六项全部通过：单元、模块、工作台用例与 e2e 都跑在新驱动上 |
| DB-02 | 突发复现：对刚启动的 cs-api 反复发起集中并发的真实请求（开发页、名册、会话、档位、日志），新驱动下没有任何 I16 特征报错，也没有探针重启。同一脚本先在旧驱动上跑过，结果如实记录：复现与否都记 |
| DB-03 | 每个服务新建的连接里，`idle_in_transaction_session_timeout` 为 1min；连接串自带 `options` 时，按运维给的值 |
| DB-04 | 就绪探针照旧：连接池被占满或数据库不可达时，3 秒内报不就绪 |
| DB-05 | 数据模块照旧能为项目建库、建角色，发临时诊断与变更凭据，并在到期后收回：在本机新建项目，并走一次 `diagnostic-readonly` 绑定 |
| DB-06 | 迁移 Job 用新驱动：在空库上从头应用全部迁移；在本机集群上升级时，没有待应用的迁移 |
| DB-07 | 进程收到 SIGTERM 后，在终止宽限期内关闭连接池，数据库里没有它留下的连接 |
| DB-08 | 本机集群照常多会话使用，观察 24 小时（Q2）：cs-api、cs-session、cs-controller、cs-events 日志里没有 I16 特征报错，也没有因数据库被探针重启 |
