# 逐 CLI 执行环境

> I15 已按作者 2026-09-15 的全权委托选择方案 (a)。本页补全 RFC-003 的实现契约；RFC-004 的启动前 Hook 仍未开工。

实施状态：第七十六批完成隔离底层；第七十七批已接管理员套餐、开发页逐窗启动、独立终端连接、动态来源汇聚和退出末屏。源码与完整门禁已通过，实际部署和真实四窗／OOM 旅程继续；不能将自动测试当成已经上线验收。

## 用户行为

“＋ CLI”仍然只启动一窗。平台为新窗单独申请算力、创建执行容器，挂载当前工作树；原开发容器继续承担编辑、Git 比较和独立预览。调度等待、套餐不足、启动失败、OOM 和结束都只更新对应窗口。确定失败使用新请求重试，回执不明继续查询原请求，不额外创建进程。旧版本已经运行的 CLI 保持原身份、原容器和输入控制，不自动迁移。

## 管理与资源

管理员在算力档位中选择 CLI 任务套餐；未指定时使用平台默认任务套餐。租户仍只选择算力档位名。登记启动请求时固定档位映射，资源准入时冻结套餐名称、CPU、内存、临时存储和镜像；后续修改档位不改变已经受理的窗口。每个执行容器独立占一个项目并发额度，Kubernetes requests／limits 独立生效。

工作卷只由父开发会话拥有。创建 CLI 只引用原 PVC，不初始化、不检出、不创建卷，套餐 storage 指执行容器临时存储，不改变原卷容量。检查 Bound、PVC UID、父 Pod UID 和挂载节点。ReadWriteOnce 的多个 Pod 必须在同节点，使用调度器的必选节点亲和性；ReadWriteOncePod 明确拒绝共享，不能静默改成空卷。依据 [Kubernetes 卷访问模式](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#access-modes) 与 [节点调度约束](https://kubernetes.io/docs/concepts/scheduling-eviction/assign-pod-node/)。

## 归属与持久化

- task-runtime L4 拥有子执行环境、原卷引用、冻结资源、创建／清理意图和项目配额。子环境仍属于 development，其 parentTaskId 明确区分工作区与执行容器；项目唯一开发会话查询排除子环境。
- dev-session L5 拥有启动请求、用户、算力、agentId／terminalId 与 executionTaskId 的不可变对应关系，完成 Runner 派发与名册投影。
- session 保留每个实际 Runner 独立的事件序列和连接。终端订阅及输入使用 executionTaskId；历史 CLI 没有该字段时继续使用父 taskId。后台动态按来源游标去重，再分配父会话统一投影序号，不能混用多个 Runner 的 seq。
- API 响应和队列只保存身份与配置引用；新的 Runner 凭据预置于该次执行专用的不可变 Secret。创建响应丢失后按相同意图、标签和 UID 接续，不能覆盖同名异主对象。

## 生命周期

HTTP 先登记启动身份并返回准备中，后台从持久名册继续准入和派发。每个执行的准入／停止／退出回收跨实例串行，每进程最多处理两项，避免数据库锁占满连接池。原子准入将执行环境登记、占额与队列入库放在同一项目锁和事务里。准备、等待连接、运行、清理均有持久状态；控制器崩溃或租约转移可以接续。超过五分钟未连接时保存真实调度原因并清理本次 Pod／Secret，原卷及其他 CLI 保持。只有确认 Pod 已消失后才释放本次额度，不自动重跑结束的执行环境。

正常 CLI 退出时先保留其身份、终态和可获取的有限末屏，再回收执行容器；保存失败最多重试 30 秒，随后明确标为不可用并回收。OOM 等导致末屏不可获取时明确提示，不虚构成功或完整历史。末屏单独按需读取，不把所有窗口的屏幕放进名册轮询。

父会话释放先进入 releasing，拒绝新增 CLI，并持久驱动所有子执行环境回收；确认没有活跃引用后才删除父 Pod／按原策略回收工作卷。释放失败继续重试，不能在子 Pod 尚存时删卷。父容器失败与 I14 重建保留仍在运行的子 CLI；重建须遵守同一卷的节点约束，旧子 Runner 不被父 Runner 的代次变化误判结束。
