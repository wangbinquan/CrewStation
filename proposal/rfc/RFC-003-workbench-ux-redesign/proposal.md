## 1. 设计出发点

**让团队在一个明确的项目上下文中，持续完成“开发数字人 → 看效果 → 发布试用 → 上线给团队使用 → 发现问题再改”。**

这条主线来自原始设计，不新增业务编排产品：

| 原始依据 | 对 UX 的约束 |
|---|---|
| 《从个人提效到组织提效…》§五、§六：体验即效率，减少使用者自行关联过程的成本 | 同一个项目、版本和故障保留上下文，页面之间替用户带上对象与筛选条件 |
| 《借鉴微信小程序…》§二、§五：团队自建应用，公共平台供给；在既有范围内持续修改 | 市场服务应用使用者，项目入口服务建设者；业务工作仍在应用内部；不把所有团队业务统一成平台任务看板 |
| `proposal/proposal.md:155–172`：数字人构建、发布与运行平台；两类 Agent 按工作对象区分 | 一个 Project 对应一个数字人服务；开发会话内 Agent 修改应用自身；业务执行留在业务服务里 |
| `proposal/design.md:488–557`：分支选择、并行 Agent、终端、编辑器、真实预览与发布控制 | 主工作区同时支持对话与结果观察；终端、编辑器、多 Agent 仍是完整能力 |
| `proposal/design.md:575–635`：标签发布、待命槽验证、负责人切流 | 开发预览、发布试用、正式访问三者分清；发布成功不等于正式上线 |
| RFC-001、RFC-002（均 Done） | 租户只选择算力档位；平台管理与租户工作空间保持分离 |

本 RFC 新增应用能力市场与负责人可见性配置，见 [专项规格](./market-visibility.md)。不建设通用 Agent 工作流、业务问题单中心、自动审核／自动上线、跨项目协作调度或通用角色模型。原有业务应用如何组织任务，继续由业务团队决定。

## 2. 原型为什么难用

完整可追溯证据见 [audit.md](./audit.md)。以下是本轮已发现的主要问题，并非用户行为统计。

| 优先级 | 具体问题 | 对使用者的影响 | 设计响应 |
|---|---|---|---|
| P0 | 开发页让用户到发布页切流，但切流实际在项目概览 | 找不到把版本交给团队使用的下一步 | 统一“发布与上线”工作区 |
| P0 | 开发页先铺说明与内部标识，再放 Agent／终端，编辑器之后才有预览 | 无法边描述需求边观察结果 | 多 CLI 默认工作区；预览可独立或并排查看 |
| P0 | 两处发布入口使用不同服务端链路，却没有清楚说明发布哪份代码 | 难以判断当前工作区改动是否会被发布 | 明示“当前开发会话”或“已推送分支”，各自预检与确认 |
| P0 | 未推送提交在释放会话的响应中才交给前端 | 决定释放时缺少具体损失信息 | 释放前展示工作区检查结果与未知状态 |
| P1 | 项目导航显示长 ID，概览以槽／成员／配额为主体 | 难辨项目，缺少继续工作的入口 | 名称与 slug 定位；概览突出当前版本、开发状态与下一步 |
| P1 | 租户首页直接展开管理员创建表单，仍可创建接入容器 | 日常入口被低频管理工作占据 | 新建移至管理空间，数字人与接入容器分开创建 |
| P1 | 接口可申请，但 Swagger 不可直接试调，要去终端手动调用 | 发现能力、获得能力、验证能力分散 | 能力详情串起申请、文档、经开发会话试调 |
| P1 | 日志页未使用已有 taskId／releaseId 查询能力，发布失败行无日志入口 | 看到了失败，却还得自己定位日志 | 从故障携带对象跳转到诊断视图 |
| P1 | 管理首页重复导航目录；接入容器详情跳出租户／管理边界 | 管理者需自行查找待处理事项并反复切换 | 管理总览呈现真实待处理项；接入容器留在管理上下文 |

## 3. 人与工作对象

| 人 | 首要目的 | 进入后首先看到 | 主要动作 |
|---|---|---|---|
| 项目开发者 | 做出／改好自己的数字人 | 项目当前状态、现有开发会话 | 开始／继续开发、试用、发布到待命槽 |
| 项目负责人 | 交付可用版本并维持运行 | 正式版本、待验证版本、待办与故障 | 上线、回退、成员与数据访问、生产配置 |
| preview 测试者 | 验证候选版本 | 明确版本的试用地址与访问说明 | 打开待验证版本；可读范围仍由现有服务端裁定 |
| 平台管理员 | 把公共能力供给到位 | 项目开通、接口／出站申请、接入与资源状态 | 开通项目、处理申请、维护接入容器与套餐 |
| 团队应用使用者 | 完成业务工作 | 能力市场或业务应用自己的页面 | 从获准查看的应用进入业务页面 |

角色影响可操作项，不另造四套互相割裂的产品。管理员进入租户空间时按项目上下文工作，平台级管理动作留在管理空间。

## 4. 新的信息架构

应用建设入口为 **“数字人项目”**：搜索名称／slug，按已返回的项目状态筛选，列表显示名称、开通状态、负责人和可用动作。点击项目进入概览；已有会话提供直接继续入口。管理员看全部数字人时明确标为“全部数字人”，不把它误称为“我的项目”。

全局新增 **“能力市场”**，展示当前用户有权查看的应用，应用负责人配置可见范围，见 [market-visibility.md](./market-visibility.md)。数字人项目列表保留为应用建设入口。

项目内保持五个稳定入口：

| 入口 | 回答的问题 | 二级内容 |
|---|---|---|
| **概览** | 现在做到哪，下一步做什么？ | 正式版本、待验证版本、开发会话、需要处理的事项；详情按需展开 |
| **开发** | 怎么把这个数字人改好？ | 逐个新增 CLI、页签与可调分屏；执行／待处理／完成提示；独立／并排预览；生产版本差异 |
| **发布与上线** | 哪份代码在试用，哪一版正在服务？ | 发布准备、进度、版本详情、试用、上线、回退、历史 |
| **运行与诊断** | 哪里出问题，从哪里恢复？ | 健康与告警、日志、事件投递、按 traceId 追溯 |
| **项目设置** | 谁参与，应用用什么配置？ | 应用可见性、成员与测试者、开发／生产配置、开发资源、仓库信息、归档 |

导航显示可读项目名与 slug，支持返回列表／切换项目；长 ID、命名空间、镜像与底层连接信息放在“技术详情”，保留复制能力。当前项目与二级页面写进 URL。全局返回、项目切换、管理空间往返保留有效上下文。

管理空间按工作分组：

- **待处理**：总览、接口申请、出站申请；聚合现有接口的实际状态，不编造指标。
- **供给与接入**：数字人项目（创建与开通状态）、能力接入（接入容器创建／开发／发布、事件来源、API 开放策略）。
- **平台设置**：用户与权限、算力档位、服务套餐、任务容器套餐、出站规则、网关。

保留各设置页独立 URL；分组减少理解负担，不能把所有内容重新挤回一个管理大页。

> **2026-09-21 修订（作者当面裁定，直接修改，不另立 RFC）。** 「平台设置」后来又挂进了认证（RFC-014）与集群管理（RFC-010），八项里有两项并不是配置：集群管理是资源清单、容量与运行实例操作，网关是由项目、发布与开放策略推导出来的只读路由表与放行表，只有一个「重算」。作者反馈「呈现类也在配置里，使用起来很别扭」，逐项裁定后上面三组改为五组，**先后顺序即左栏顺序**：

> - **待处理**（左栏不显示组标题）：总览、申请审批。

## 5. 六条完整旅程

### J1：首次接手一个项目

管理员在管理空间创建数字人，依次选择负责人和模板、确认名称／标识与资源。所有约束初次呈现，错误贴字段显示。提交成功进入该项目的开通状态页；仓库、数据与首个发布各有状态，有问题显示失败对象及恢复入口。

负责人从项目列表进入，看到“样例已可试用”；主动作是“开始开发”，次动作是“打开样例试用”。无项目时说明由管理员开通并给出可复制的需求信息，不渲染不存在的自助申请流程。

### J2：日常开发和即时验证

首次进入开发，工作分支显式选择并保留默认分支语义。已有会话直接进入，顶部持续显示容器实际工作树分支／HEAD、生产实际部署标签／SHA，以及双方独有提交和未提交文件；未知差异显示原因。远端同步数量单列，不能替代生产版本差距。

主工作区是原生 **Agent CLI 窗口**：每点一次“＋ CLI”只启动一个独立 CLI／PTY，沿用平台算力档位，启动前无需填写首条任务。工作页签可新建、命名、关闭；每页签可横排、纵排或网格，拖分隔线调整大小，窗口可跨页签移动、放大和收起。关闭显示页签保留其中所有进程，结束进程另有动作。共享同一工作树，不赋予固定角色，不自动建分支或合并；旧版结构化会话由“会话 → 历史对话会话”独立进入，明确返回 CLI 工作区；取消容易被误解为同一会话视图的“对话模式”按钮。

> 2026-09-23 修订：工作页签与每页签的横排／纵排／网格改为 Xshell 式标签组（每个 CLI 一个标签，拖动排列与分屏，× 即结束进程，新开入口在页头），见 [development-workspace.md §2.1](development-workspace.md#21-页签与分屏规则) 同日修订。

每个 CLI 明确显示执行中、需要你处理、本轮完成和已结束。后台页签聚合需处理与新完成数，顶部动态入口可直达对应窗口；通知不抢焦点，已查看不代表已解决人工请求。数据访问采用“开发数据”“生产数据只读”“生产数据读写”，原 Agent 文件／工具权限放进高级选项，不混为同一个设置。

**实时预览**有独立工作视图、真实地址和并排模式，查看当前工作树已保存的结果；项目支持热更新时实时变化，其余按真实预览进程能力刷新。代码、版本差异、普通 shell 与会话日志按需进入。预览标明开发数据及真实绑定；预览失败不影响 CLI。视图切换／离开只 detach 显示连接，显式结束才停止对应进程。完整交互、生命周期和比较语义见 [development-workspace.md](./development-workspace.md)。

### J3：从改好到正式可用

开发页的“准备发布”把当前会话、分支和项目带到发布与上线。发布面板说明来源，展示工作区检查；有未提交改动时列出文件并直接返回代码位置。用户自行提交代码，平台不会偷偷提交。

版本号使用“修订／次版本／主版本”的可读选项并显示解析后的标签，支持显式版本输入。提交前可读出“把哪份代码发布为哪个标签”；提交后进入同一条发布记录，按真实状态显示推送、标签、构建、迁移与部署，失败步骤附日志与修复入口。

待命槽就绪显示“已发布，可试用”，给出地址和精确版本，说明**试用版本与正式版本共用生产数据**。负责人在同一页面确认从哪个版本上线到哪个版本。上线成功后正式版本立即更新，旧版本显示为可回退候选；回退只适用于仍在待命槽且允许回退的版本。普通历史发布不是任意一键回退点。

“从已推送分支发布”保留为明确的另一种来源，不要求凭空创建开发会话；它只发布已在远端的代码，不能声称包含本地工作区。

### J4：看到故障后找到原因

概览与发布记录上的异常直接进入诊断，并带上 `releaseId`／`taskId`／槽／来源；展示当前筛选对象。日志局部刷新，用户向上阅读时不被自动滚动打断。无记录、筛选无匹配、获取失败分别呈现。

事件订阅放在项目设置的开发资源；投递失败、重试与死信放在运行诊断，互相链接同一订阅与 trace。已有日志源只有尾部时明确“最近 N 行”，不能出现虚假的历史分页或完整检索。

### J5：找到并使用平台能力

使用者从能力市场发现有权查看的应用，查看用途、负责人和正式版本，打开实际业务应用；尚未上线的应用明确显示状态。负责人从应用详情进入可见性设置，选择项目成员、全部登录用户或项目成员与指定用户，保存后市场按新范围展示。市场可见性不授予项目开发或 API 调用权限。

开发者的 API 文档、申请与试调收在项目设置的“开发资源”；平台能力接入由管理员完成。试调仍从当前开发会话、以本服务身份发出，文档与 MCP 同源。详见 [能力市场与可见性规格](./market-visibility.md)。

### J6：管理员供给能力

进入管理空间，先处理真实存在的开通失败、接口申请与出站申请。审核详情显示项目、人、申请内容与理由，操作结果就地呈现。创建接入容器、查看详情、开发与发布始终使用管理空间导航；返回仍回该容器列表与筛选状态。算力／套餐等低频维护有独立页面，表单按需打开。

## 6. 交互与视觉原则

1. **一个页面围绕一个主要目标。** 主动作随真实状态变化：开始开发、继续开发、处理发布失败、试用版本；不固定把所有按钮排成一行。
2. **概念解释放在发生影响的地方。** 发布确认解释生产数据；数据绑定解释有效范围；页首不再复制架构文档。
3. **提供原始事实，同时给出可行动的表达。** 显示版本和人名，技术详情可展开；失败必须说明对象、原因、下一步和当前保留的结果。
4. **状态独立。** 项目开通正常不等于服务健康；容器运行不等于 Agent 有模型输出；发布成功不等于上线。
5. **层级清晰、工作区紧凑。** 保留 CrewStation 的蓝色主动作和明暗主题；弱化大面积卡片与重复框线，列表用于扫描、面板用于工作、确认区用于决策。
6. **可访问且可恢复。** 真实 label、字段级错误、键盘焦点可见、选中态有文字、长名称换行；加载保留布局、失败可重试、提交不丢草稿。
7. **小屏仍能操作。** 1280／1440 支持 CLI 平铺及预览并排；1024 优先保留终端可用宽度并可切独立预览；窄屏切为单栏工作页签，320／390 无整页横向溢出。代码与日志可在自身区域横向阅读。

品牌采用“协作舱”：C 形工作站、三条并行轨道与终端交付箭头，见 [brand-design.md](./brand-design.md)。

## 7. 能力影响清单

本方案不关闭现有能力；以下是每项主要迁移的接续位置。若实现无法保持其中任何一项，应作为能力收缩重新呈作者确认，不得默默删掉。

| 现有能力 | 新位置／保留方式 |
|---|---|
| 新建 DigitalWorker／APIProxy／EventProducer | 管理空间数字人创建／接入容器创建，三种类型全保留 |
| 项目概览、归档、成员、测试者、配额、仓库 | 概览／项目设置／开发资源，原有深链接提供重定向 |
| 分支选择与落后数 | 开发准备、远端发布来源；默认分支与未知值语义保留 |
| 多 Agent、算力与权限、取消、消息 | 逐个新增 CLI，旧版对话独立历史入口与三档 Agent 操作权限保留；支持页签、可调分屏和逐 CLI 状态，不新增 Agent 角色 |
| 终端、文件树、代码保存、冲突处理、真实预览 | 开发工具区；切换显示不重开终端、不销毁草稿 |
| 会话释放、负责人强制释放、空闲提醒 | 会话菜单；先预检再显式确认，空闲只提醒 |
| 会话发布与远端分支发布、标签明细 | 发布与上线的两个来源，保留非平台标签的区分 |
| 切流、回退与历史 | 发布与上线；能力保留，作用对象更清楚 |
| 两组配置与只写 Secret | 项目设置，开发／生产明确切换；原权限不变 |
| API 申请、撤销、开放策略、Swagger | 项目开发资源／管理员能力接入与申请处理 |
| 数据访问三种模式与审批 | 开发会话数据面板／项目负责人待处理事项 |
| 事件类型、订阅、投递与重试 | 开发资源＋运行诊断，双向链接 |
| 健康、日志、告警、追溯与能力约定 | 运行诊断／开发资源，补接已有但未呈现的接口 |
| 平台管理的八页及两空间切换 | 保留对应独立入口，并按工作分组；往返记忆保留 |

> **2026-09-23 修订（作者 2026-09-23 当面裁定，直接修改，不另立 RFC；基线 Design D59）**：上表「三档 Agent 操作权限保留」作废。开发会话的 CLI 与历史 Agent 一律完全权限，两处权限下拉框去掉；数据访问三种模式与审批不变。作者逐项确认了去掉的能力，见 development-workspace.md §8 同日修订。

## 8. 验收与待批准决策

所有页面不是一次铺完样式就算完成。每一旅程必须跑通“入口 → 实际动作 → 状态变化 → 结果 → 恢复”；用例与实施依赖见 [plan.md](./plan.md)，接口与布局细节见 [design.md](./design.md)。[prototype.html](./prototype.html) 为交互设计附件，全部数据与执行结果均为演示。

本 RFC 请求批准的具体设计是：

- 能力市场、负责人配置应用可见性、五个项目入口，以及“多原生 CLI Agent＋独立实时预览＋工作树对生产版本差异”的开发工作区。
- 将发布、试用、上线与回退统一为一条带明确源码来源的流程。
- 管理职责收回管理空间，补齐接入容器在管理空间内的完整路径。
- 按设计中列明的接口补齐工作区预检、能力试调、成员定位等阻断 UX 的缺口；不改变既定平台／业务分工。

作者已明确补充多 CLI、独立预览与工作树版本差异的具体期待，本稿已据此修订 J2 和实现规格；这仍不是量化用户研究结论。此澄清确定开发方向，不代表 RFC 其余页面已获整体实施批准。
