## 1. 来源与确认

| 编号 | 来源 | 要求与状态 |
|---|---|---|
| C1 | 作者本轮需求 | 默认进入使用者界面，只展示能力市场的应用；市场卡片不提供项目编辑入口 |
| C2 | 作者本轮需求 | 系统分为用户、开发者、管理员三类平台角色；开发者进入项目开发，查看有权限的项目或新建项目；管理员进入平台管理 |
| C3 | 作者明确回答 | 管理员包含开发者能力，也能开发和创建项目 |
| C4 | 作者明确回答 | 开发者创建项目后自动成为负责人，管理成员、发布和上线 |
| C5 | 作者本轮澄清 | 试用成员在首页能看到未发布应用并试用，对应应用卡片加 Beta 标签 |
| C6 | 作者追加需求及源码判断 | 作者询问全局 Agent 动态用途，并要求无用则删；全局入口删除，已有开发会话内 CLI 状态与待处理提示保留 |
| C7 | 作者 2026-09-20 批准完整 RFC | 原管理员保持管理员；现有项目负责人／开发成员转为开发者；其他账号为用户；测试成员保留试用资格 |

本 RFC 改变 RFC-003 的全局导航与管理员独占创建规则，补充 RFC-002 的空间划分，调整 RFC-007 的角色播种与默认落点。
RFC-008 开发会话、RFC-009 项目设置与开发资源继续沿用。并行 RFC-010 的集群管理只属于管理员空间，不在本 RFC 增设集群功能。

## 2. 目标与边界

让首次使用的人只需理解“选一个应用，开始工作”。开发和管理是明确的独立入口，按角色出现。
角色同时约束服务端访问和界面；隐藏导航不代表权限已经实现。

范围：账号平台角色、已有账号迁移、管理员授权、用户首页、项目开发入口、开发者自助创建、相关 API／CLI／开发登录器与实机验收。
本轮不增加角色组合、自定义权限组、申请开发者的审批流、应用收藏／分类、应用内部业务授权或收费体系。
平台三类角色不替代项目内的负责人／开发成员／测试成员；项目关系继续决定“能开发哪些项目”和“谁能上线”。

## 3. 三类角色

| 能力 | 用户 `user` | 开发者 `developer` | 管理员 `admin` |
|---|---|---|---|
| 默认首页 | 能力市场 | 能力市场 | 能力市场 |
| 查看和打开应用 | 按现有应用可见范围 | 按现有应用可见范围 | 沿用现有管理员范围 |
| 试用待发布版本 | 被指定为测试成员时 | 有该项目试用权限时 | 可试用 |
| 项目开发入口 | 不显示，直达拒绝 | 显示 | 显示 |
| 项目开发列表 | 不可读取 | 仅本人为负责人／开发成员的数字人项目 | 全部数字人项目，明确标“全部项目” |
| 新建数字人项目 | 不可创建 | 可以；固定本人为负责人 | 可以；项目开发中默认本人，平台管理中可代建 |
| 开发／发布 | 不可操作 | 还需项目负责人／开发成员资格 | 可以 |
| 成员管理／上线 | 不可操作 | 还需项目负责人资格 | 可以 |
| 接入容器、平台配置、用户角色管理 | 不可访问 | 不可访问 | 平台管理中进行 |

新登录账号默认是用户；首次引导管理员和既有明确配置的管理员初始化方式保留。
管理员在“平台管理 → 用户与角色”设置三选一角色；赋予开发者身份不会自动加入任何已有项目。
负责人添加开发成员时，目标必须已是开发者或管理员；添加测试成员可以选择用户。
负责人不通过项目成员操作授予平台开发者身份。

已批准的降级规则：用户仍担任项目负责人时，先转交负责人再降为用户；非负责人的开发成员可降级，原成员记录保留但开发权停止。
恢复开发者角色后按仍存在的项目关系重新生效，管理员确认区说明这种效果。不得移除最后一名管理员。

## 4. 页面与使用路径

### 4.1 能力市场：默认的使用者界面

- `/` 和 `/market` 都进入能力市场，不因管理员身份或上次进入管理界面而改变默认落点。
- 顶栏只保留品牌、当前空间、语言与账号；普通用户没有项目开发、平台管理、Agent 动态或技术侧栏。
- 开发者顶栏增加“项目开发”；管理员再增加“平台管理”。能力市场页不再重复一份左侧全局导航。
- 页面标题“能力市场”，说明“找到适合你的应用，开始处理日常工作。”；搜索按名称或用途，保留分页。
- 卡片显示应用图标、名称、用途、负责人，以及“可使用／尚未开放／暂不可用／状态待确认”等用户语言。
- 正式应用主动作“打开应用”；成员可试用的未发布应用卡片标 **Beta**，主动作“试用应用”；次动作“了解应用”。对所有角色都移除“进入项目”“配置可见性”“编辑应用”等开发动作。
- 不显示 Git SHA、部署槽、容器状态、发布链、Agent 术语。业务卡片直接打开应用主页，移除应用详情页。
- 状态未知必须与尚未上线区分；读取失败保留错误与重试。必要的 HTTP 状态／trace 等放在错误详情，不放在正常卡片。
- 现有可见范围继续有效；搜索不泄露不可见应用。没有应用时说明“暂时没有可使用的应用，请联系应用负责人”，不引导普通用户创建项目。

### 4.2 应用试用：保留测试成员的工作

“试用成员”是指定应用的关系，不是第四类平台角色。普通用户成为试用成员后，首页即可看到未发布应用的 **Beta** 卡片，并可直接点“试用应用”，不必先找项目或详情。
未发布应用只有获准的成员可以试用；尚未准备好试用版本时卡片显示“准备中”，不放出无效入口。
已有正式版本的应用仍以“打开应用”为主，不因存在待发布版本而把正式卡片标成 Beta；有资格的成员在详情的独立 **Beta** 试用区试用新版。
进入试用时保留“试用版本与正式应用共用业务数据”的提示，必要时在打开前行内确认。正式使用与试用不能用同一个含糊的“打开”按钮。
仅返回获准访问的试用信息，不加载项目配置、成员、开发会话或仓库接口。
旧测试者项目链接和旧应用详情链接迁移到能力市场，不让普通用户进入开发壳层；没有应用可见权或测试资格时不提供入口。
试用权不等于开发权，也不改变应用可见性或业务应用自身的权限。

### 4.3 项目开发：有项目可继续，没项目可创建

入口名统一为“项目开发”。列表主内容是当前账号有权开发的项目，主操作“新建项目”，行内“继续开发／进入项目”。
默认显示项目名称、我的项目角色、当前进展和主要动作；部署、仓库等详情进入项目后查看。
只有测试关系的项目留在应用侧试用，不混进可开发项目列表。无项目的开发者直接看到“创建你的第一个项目”。

开发者新建数字人项目时填写名称、访问标识与模板；负责人固定为本人，资源采用平台默认配置并以只读摘要说明。
不加载管理员用户目录，不允许通过请求自行指定他人负责人、接入容器类型或提升资源额度。
管理员在项目开发中使用同样简单的自建流程；代建、指定负责人和资源配置继续在平台管理中处理。
创建成功进入本项目的开通进度，再进入开发；开通失败显示失败步骤和下一步，沿用异步开通链。
表单初始即展示全部约束；字段错误、草稿、返回修改、失败重试和离开保护保留。

### 4.4 平台管理：权限与供给集中

管理员从独立入口管理用户与角色、算力、套餐、接入容器和平台资源。
用户目录将“是否管理员”改为“平台角色”：用户、开发者、管理员。编辑时展示对象、旧角色、新角色与影响，成功后刷新相关身份和目录。
管理员仍可在管理目录处理所有项目；日常开发从“项目开发”进入，数字人项目内部结构遵循 RFC-009。

全局顶栏删除 Agent 动态按钮及通知弹层；市场和管理页不再为这个入口挂载开发会话查询或活动订阅。
开发会话内已有的 CLI 执行状态、需人工处理、未读完成和工作区定位保留。跨空间的全局动态通知随入口移除，不另造一个“通知中心”替代它。

### 4.5 入口、草稿与权限变化

显式打开且仍获授权的项目／管理深链接继续有效；只有无目标登录和点击首页默认回市场。
身份待读取、失败和无权限三种状态分开；未确认权限前不挂载技术子页面，不闪现入口。
切换空间仍遵守未保存草稿确认。权限被撤销后暂停写入和会话连接，保留可复制的未保存文本，给回市场的动作；不因后台身份刷新偷偷保存或丢弃草稿。

## 5. 能力影响清单

以下变化作为 breaking behavior 随本 RFC 一并批准；每条拒绝分支均须测试。

| 编号 | 原能力／入口 | 变化与保留路径 | 来源 |
|---|---|---|---|
| B1 | 所有账号可见“数字人项目”入口 | 仅开发者／管理员可见并可进入项目开发；用户首页只含应用 | C1、C2 |
| B2 | 市场卡片和详情可进入开发／编辑 | 对所有角色删除；经顶栏项目开发 → 对应项目操作 | C1 |
| B3 | 有 owner／developer 项目关系即可开发 | 需同时具备平台开发者或管理员身份；迁移按 C7 保留既有能力 | C2、C7 |
| B4 | 测试者通过项目列表／概览试用 | 首页未发布应用卡片标 Beta，直接试用；已发布应用的新版从卡片次要 Beta 入口试用；旧链接迁移 | C5、后续业务卡片要求 |
| B5 | 管理员独占项目创建 | 开放开发者创建数字人并自动成为负责人；接入容器和代建仍归管理员 | C2、C3、C4 |
| B6 | 成员表可直接给普通账号 developer／owner | 目标须先具备平台开发者／管理员身份；不自动提权 | 三类平台角色的职责边界 |
| B7 | 用户目录只有管理员开关 | 改为三类角色选择；最后管理员和在任负责人降级有明确前置条件 | 建议的角色维护规则 |
| B8 | 开发登录器按角色默认落项目／管理页 | 默认三类角色都落市场；测试成员保留为用户角色下的验证视角，显式测试深链接仍可用 | C1、RFC-007 接续 |
| B9 | 所有页面右上角汇总 Agent 动态和跨空间通知 | 删除全局入口与弹层；只保留开发会话内部既有状态、待处理和定位能力 | C6 |
| B10 | 点击市场卡片标题先进入应用详情页 | 删除该页面，业务卡片直接打开应用主页；旧详情 URL 返回市场，正式／Beta 使用能力保留 | 作者明确要求“点击就打开 app 主页，不要显示那个应用详情……那个页面都应该下掉” |

不移除开发会话、CLI、发布上线、应用可见性、项目设置、开发资源或管理员接入能力；改变的是入口与资格边界。

## 6. 验收标准

详见 [plan.md](./plan.md) 的 RH-01…RH-20。完成需同时具备：三类角色真实登录路径、直达 URL 与 API 的拒绝／成功证据、开发者真实创建后的开通和负责人证据、迁移与降级回归、桌面／窄屏视觉核对。
交互附件只使用模拟数据，不作为服务端权限或项目开通通过的证据。批准前不修改生产代码、不迁移真实账号或部署。
