# 三类旧来源缺口的恢复方案（待作者裁定）

本方案未获批准，未启用。已批准的 I35 只处理三个全平台巡检任务；本文件不放宽业务、网关或 PostgreSQL 的现行删除合同。

## 已核实的问题

原专用验收项目为 `01a0f30b-c652-7000-8d6f-553e3b5f6135`，标识 `rfc037-creation-proof`，服务为 `01a0f30b-c652-7001-8634-f8d25dd9590e`。截至本轮实施前，项目仍为 active，删除操作数为0。

| 来源 | 真实缺口 | 现行规则的结果 |
| --- | --- | --- |
| business-task | 旧执行任务 `01a0c12a-de2e-7015-b669-bf7cfb7caf6e` 只剩迁移别名及子任务引用，任务根、受理意图、原运行环境均缺失；父任务属于另一项目 | 子引用不能冒充原执行归属，所有项目盘点均会遇到这条全平台历史 |
| gateway | 17条服务Pod记录缺少 service_source，旧放行文档41、42、43缺少完整原归属 | 无法清理未知部分，也不能默认当作平台或其他项目 |
| data-control | 原项目14条迁移前回调缺少 journal_version 及原 SQL/卷 before/after；两库仍存在，最近只读 OID 为276598、276606 | 当前目录、同名资源或 finished 状态不能补造旧回收证明 |

平台登记 object_backups 为空，PostgreSQL archive_mode=off，已登记恢复表没有缺失任务。最早及最新本机部署备份同样没有任务根/受理/运行环境，仅有旧别名和子引用；中间归档11份完成后下一份触发原120秒读取截止时间，全备份审计未通过。原件见 `cs-rfc037-original-history-current-blockers-v3.json` 与 `cs-rfc037-original-history-local-backups-v3-incomplete.json`。这些结果不能排除外部持有的原备份。

## 可选做法

**A：恢复真实原历史。** 由可核对的原备份、原Pod UID及其不可变事实、或原执行接收记录恢复完整来源。每一条都核对原身份和原正文摘要；恢复后继续现行合同。只有别名、父引用、名称、当前目录或时间接近不够。拿不到原记录时继续阻断，不能承诺这条路径能完成原项目删除。

**B：新增管理员重新确权流程。** 对无法恢复的旧记录明确采用一份新的、管理员确认的当前资源归属基线。保留原历史原样及“未知”状态；新基线标注 `operator-confirmed/v1`，不称为旧出生、旧回调 before/after 或退出证明。管理员必须看到实际对象、来源、影响和保留项再确认。该选择改变现行“必须恢复旧出生/回调历史”的约束，需要作者明确批准。

建议采用B处理这次验收，再保留A作为有真实原件时的常规恢复路径。批准本方案后才形成正式基线和实现；批准流程本身不自动认领任何未知对象。

## B 的具体约束

1. 先完成当前实际资源、反向引用和原消费者的全部分页读取。候选绑定项目/服务UUID、记录主键及原正文摘要；物理资源另绑定实际Pod UID、容器和卷身份、PostgreSQL服务器/目录/OID。只给名称或读取到 absent 不得受理。
2. 业务及网关未知记录先逐项展示。能够取得真实原件的走A；仍无法归属的由管理员逐项确认其是否与目标项目有关。不能自动把缺失记录归到父项目、平台或其他项目，也不能因没有目标UUID就自动排除。无法确认的条目继续阻断。
3. 对确认属于其他范围而需保留的记录，新事实只表达“本次目标项目不回收该完整原记录”，绑定目标UUID及原记录摘要，不改变其未知历史归属。变更正文、出现指向目标项目的当前引用、活跃消费者、共享资源或新条目，都使该确认失效并继续阻断。不得删除或改写这些保留项。
4. PostgreSQL须单独确认实际两库、角色和所有已登记旧名字。新确认仅绑定当前实际对象，并检查其他项目的反向绑定及共享卷/目录；任何冲突、未知目录、未知tablespace或缺失来源都继续阻断。迁移前14条NULL保持原样，不将当前OID写成它们的旧OID。
5. 管理员确认形成独立持久记录，记录操作者、项目UUID、合同版本、实际来源、原条目摘要和确认时间；不写入冒充旧来源的表。收集和最终绑定均在相应owner的原准入锁内重读；范围或身份变动后重新确认。数据库、业务、网关各存自己的事实，经公开API组合；不增加跨schema事务或内部import。
6. 新基线只替代明确批准的旧归属/出生前提。仍必须证明原消费者停止；未知原进程、running旧回调或无法核对的原容器不能用 absent/finished 代替停止证明。实际回收继续原七阶段、逐项持久回执、原UID/OID条件和完整独立after。
7. 归属修复使用既有FormDialog，说明“旧历史未恢复、此处确认的是现在的资源”；保存后重新生成删除预检。永久删除继续现有两层确认和输入delete，不把修复保存当作删除授权。实际验收仅沿用原专用项目；其他项目及平台资源保留。

## 实施和验收

- 作者选择后，把对应约束并入RFC-037 proposal/design/plan；未裁定前不改生产行为。
- 用真实PG验证管理员授权、完整原记录摘要及确认失效、旧NULL不可改、并行变化、重启和重放；验证公开owner边界及未知/共享/活跃原消费者仍拒绝。
- 原生验收复用原容器/卷/服务器，证明实际UID/OID变化拒绝、原消费者退出、原目录实际回收，并验证其他项目和保留历史未被回收。用受控metadata测试不能替代这些证明。
- 精确上库、确切SHA六项CI和八组件部署后，原专用项目必须重新预检完整，才执行两层确认；全22方及独立after通过才能报告原项目全部资源回收完成。
