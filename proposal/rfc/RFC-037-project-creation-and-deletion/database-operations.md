# RFC-037｜原数据库删除的原生步骤

补充 design §6.2；仍使用 data-control L2 的原生 PostgreSQL 适配器。入口是组合根内部端口，必须逐步核对正式 data-control/purge 许可，不开放按名字删除的 HTTP。正式 owner 的关闭、全部消费者／DDL 回调排空及最小意图接线完成前，此执行器不构成可开放的产品删除能力。

所有平台数据库与角色 DDL 使用同一原生服务器上的名字锁，锁键与项目 slug／当前根查询无关。原生连接在整个命令期间持有锁，删除必须等原连接释放，而不是看主库租约或 PID 消失。旧、新供给器都要接入；调用方每次取得锁后再检查原项目许可，禁止等待锁的旧供给在删除后继续执行。外部管理员绕过协议的修改不由平台接管，实际盘点发现身份变化时阻断。

数据库不能在事务中 DROP。先持有原名字与本操作唯一隔离名字的原生锁，在一个短 catalog 事务中锁住 pg_database 的变更，核对原 OID、原名和原物理来源。存在连接、prepared transaction 或复制槽时等待／阻断；不使用 FORCE 杀掉未知消费者。满足排空条件后关闭连接准入，原子改名为由 operationId 与原身份摘要生成的隔离名字，并留下只含操作、原身份摘要的注释。事务提交前失败不改变原名；同名新 OID 拒绝改名或删除。

隔离名字属于该操作，重试核对原 OID、原注释和原物理来源；不能接管碰巧占用隔离名字的对象。事务外再次检查正式许可与原身份，执行正常 DROP，再使用完整原 OID／tablespace 文件来源复核。隔离提交后掉线可按同操作恢复；DROP 成功但回执丢失时可以复核实际归零，不能先删除最小原身份和意图。同名替换、读取故障和原目录残留不生成 done。

角色删除同样须按原 OID 与全部原数据库依赖盘点；不将运行角色放进既有临时角色回收。角色、legacy 新建／重试、连接串续发、口令轮换及全部历史资源的正式 owner 接线仍在后续同批工作中。此步骤不会修改共享 PostgreSQL 配置或移除其他库、角色、tablespace。

用例使用独立测试库和真实 pg_database 锁：正常删除／原文件归零、活动连接保护、原 OID 替换、隔离名字冲突、改名后的同操作恢复、错误许可与原来源失败均需覆盖。原生产验收项目尚不执行删除。
