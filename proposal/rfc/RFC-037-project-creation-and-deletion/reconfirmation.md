# 封闭期间的重新盘点与确认

实现设计 §59、§75 的恢复路径：普通 retry 沿用原确认摘要；只有管理员重新查看服务器盘点并输入 `delete`，才能接受新的材料。仍使用同一删除操作，不创建第二条删除流程。

- 仅在 `needs-attention`、`seal` 且没有后续阶段证明时重新盘点。实际销毁开始后，不能用重新确认认领替换 UID 或覆盖原物理证明。
- 新计划绑定原 operationId 和前一确认摘要，十分钟过期。受理时重新读取全部来源，核对目标的原项目、namespace、service 与域名，比较新材料并原子写入操作、最小确认历史和 outbox。
- 已完成 seal 的 owner 保留原确认材料与证明。再次读取该来源必须完整，资源种类、原 ID 和数量不能增加、减少或替换；内部封闭进展造成的内容摘要变化不使其重新执行。未完成 owner 的完整新报告显示给管理员确认。
- 请求键在所有首次确认和重新确认之间串行核验。原请求和历次请求均可重放当前操作，异参拒绝；最小历史仅含计划 ID、请求键、确认摘要、实际管理员 ID 和时间，不保存资源原文。
- owner 只有在原操作的新世代、经 project 验证的新确认材料下，才能更新尚未完成的封闭摘要。仅 retry、旧许可、客户端自填资源名单均不能绕过持久失败事实。API 目录及资源申请的未验证屏障须重新比较真实完整内容；已经验证的屏障不能换材料。
- 盘点项明确区分内容摘要与物理来源身份；旧材料或未分类项按物理身份保护。当前修订 `identity` 与稳定来源 `sourceIdentity` 分开；缺少稳定来源时保守地比较完整 identity。所有 owner 的原 UID、OID、remote ID 等不得消失、换身份或降级成内容摘要；新盘点不能借确认扩大对替换物的认领。同一原 PVC 的首次绑定可改变当前修订，并增加归属已证明的新 PV，原 PVC UID 必须保持。

该路径补足已批准方案的恢复细节。永久删除入口仍等待全部 owner、实际清理和二次确认界面齐备；本文件不作为完整删除验收。
