## 1. 来源与确认

作者 2026-09-23 提问：「现在是不是没能力下线待验证版本，下线正式版本？待验证版本长期开着 Pod 也浪费资源，正式版本也需要临时进入维护状态，不被非开发者调用。」

核对结论（§2）：负责人与开发者都没有办法下线待验证版本，正式版本也没有办法下线或进入维护。随后七轮问答得到 §4 的全部裁定。

本 RFC 作废基线的「暂停项目」（Design §4.3 的 `POST /v1/admin/projects/:id/pause`、§9.7「暂停项目」一行、Plan T6.7 与 AT-24 中的暂停项目部分），并改写基线里「维护窗口」的含义（Proposal R19、Design §6.5／§9.4／§9.6、Plan T2.7、AT-13／AT-14）。新增需求、决策与验收编号在回填基线时分配（见 [plan.md](./plan.md) T12）。

## 3. 目标与非目标

目标：

- 负责人（和平台管理员）可以在工作台随时下线待验证版本，释放它的 Pod。
- 平台自动回收长期闲置的待验证版本：切流后留作回退目标的旧版本保留一段时间后下线；长期没人访问的待验证版本也会下线。到期前提醒负责人，负责人可以推迟。
- 下线后的版本不会丢：可以从发布记录重新部署到待命槽，不需要重新构建，再切回来。
- 正式版本可以临时「维护中」：Pod 照常运行，用户流量、服务域调用、事件推送三类流量各有开关；维护期间项目成员、平台管理员和临时指定的人照常访问，其余人看到维护页。
- 项目维护就是破坏性迁移的维护窗口，替代全平台环境变量。

非目标：

- 不停止正式版本的 Pod，也不缩到 0（M8）。需要彻底停掉正式版本，走管理员归档。
- 不做业务服务按流量自动缩到零（Proposal §7「业务服务缩容到零不作要求」不变）。
- 不做可逆的「停止／启动」（M1 取的是下线）。
- 不改 CLI 与操作 MCP：这些动作只在工作台（M16）。
- 不新增通知渠道：提醒走现有通知端口，Q20（告警渠道）仍待定。
- 正式槽为空时（从未切流），prod 地址的表现不在本次范围。

## 4. 作者裁定

全部来自 2026-09-23 七轮问答。「作者原话」一列只在作者写了备注时出现。

| 编号 | 问题 | 裁定 |
|---|---|---|
| M1 | 待验证版本（待命槽）的「下线」语义 | **不可逆的下线**：删除工作负载，槽变空；preview 地址显示说明页 |
| M2 | 要不要自动下线 | **两种都要**：切流后，原正式槽作为回退目标保留一段时间，到期下线；preview 地址一段时间没人访问，也下线 |
| M3 | 正式版本要哪种「下线」 | **只要「维护中」**：Pod 照常运行，网关只放行指定的人，其余人看到维护页；不提供停止正式版本 |
| M4 | 维护期间除负责人外还放行谁 | **项目开发者、项目测试者、平台管理员、维护时临时指定的人**（四项全选） |
| M5 | 回退目标到期下线之后 | **可以从发布记录重新部署**：下线只删工作负载，发布记录里的镜像与配置还在，可以把这个版本重新部署到待命槽（不重新构建），再切回。因无人访问被下线的待验证版本同样可以拉回 |
| M6 | 维护期间服务域调用与事件推送怎么处理 | 作者原话：「可选维护中的断流策略，上面说的都支持，用户流量和事件流量单独开关控制」。即：只拦用户域、服务域也拦、事件暂存后补发、事件照常推送，这些组合都要支持，各类流量用各自的开关 |
| M7 | 服务域调用归哪个开关 | **单独的第三个开关**：用户流量、服务域调用、事件推送三个开关互相独立 |
| M8 | 手动下线、开关维护由谁做 | **都只限负责人** |
| M9 | 平台管理员有什么权限 | **与负责人同权**：对任何项目都能下线、开关维护、重新部署，不必是项目成员 |
| M10 | 重新部署历史版本由谁做 | **只限负责人**（管理员按 M9 同权） |
| M11 | 自动下线的时长由谁定 | **平台统一**：管理员在平台设置里定，所有项目一样 |
| M12 | 默认时长 | **回退目标保留 72 小时；preview 连续 14 天没人访问下线** |
| M13 | 维护期间被挡住的人看到什么 | **平台统一的维护页，显示负责人进入维护时填写的原因与预计恢复时间；市场卡片标「维护中」**；接口请求返回 503 |
| M14 | 项目维护与破坏性迁移 | **项目维护中就是维护窗口**，去掉全局环境变量 `CS_MAINTENANCE_WINDOW` |
| M15 | 基线的「暂停项目」 | **用维护加下线替代**，从基线删除「暂停项目」 |
| M16 | 这些动作的操作入口 | **只做工作台**（该题作者没有勾选；按题面「都不选就只有工作台」理解，作者没有更正） |
| M17 | 破坏性迁移要求开关处于什么状态 | **处于维护中，并且三个开关都拦** |
| M18 | 维护期间切流后维护状态怎么办 | **跟着正式入口走**：切流后仍在维护，由负责人手动退出 |
| M19 | 自动下线前要不要提醒 | **提前提醒负责人，负责人可以把这次下线推迟一个周期** |
| M20 | 能力影响清单 | §6 四项**全部同意** |
| M21 | 推进方式 | **实施、部署、实机验收**：负责人、开发者、测试者、普通用户、管理员五个身份 |
| M22 | 提前多久提醒 | **两种下线都提前 24 小时** |
| M23 | 最多推迟几次 | **不限次数** |
| M24 | 界面名称 | 待验证版本的动作叫**「下线」**（Take offline），状态叫「已下线」（Offline）；正式版本叫「进入维护／维护中」（Enter maintenance／Under maintenance） |
| M25 | 服务域开关拦不拦项目自己的负载 | **自己的负载不拦**：只拦服务身份与目标不同的调用方 |
| M26 | 已有待命槽的计时 | **从升级时开始算**，不按历史追溯 |
| M27 | 切流到含破坏性迁移的版本 | **切流也要求维护**：按基线补上切流这一侧的检查 |
| M28 | 三个时长的设置入口 | **新增「平台设置」页**，以后其他平台级参数也放这里 |

问答之外，本 RFC 自己的取舍（不是新的产品规则，是裁定的落地方式）：

| 编号 | 内容 | 依据 |
|---|---|---|
| B1 | 进入维护时原因必填，预计恢复时间选填；表单里三个开关默认全开；临时指定的人退出维护时清空 | M13「填写的原因与预计恢复时间」；M4「维护时临时指定」。作者在第七轮前看到了这条默认，没有反对 |
| B2 | 回退目标从切流时起算，访问不延长；待验证版本从在待命槽就绪时起算，每次访问 preview 地址都重新计时（最多每 5 分钟记一次） | M2 的两种说法 |
| B3 | 推迟一次＝当前到期时间再加一个周期（回退目标 72 小时，待验证版本 14 天），推迟后重新提醒；平台至少提前「提醒时间」发出提醒才下线，因此调短时长也不会不经提醒就下线 | M19、M22、M23 |
| B4 | 重新部署不重新构建、不重跑迁移，按当前生产配置渲染环境（记录新的配置版本），与平时部署一致；兼容规则与回退相同：当前正式版本含破坏性迁移或禁止回退时，不能重新部署更早的版本 | M5；R19；`modules/release/application/switchTraffic.ts:28-30` |
| B5 | 事件暂存：暂存期间不算投递尝试，不进死信，界面显示「维护暂存」；开关放开或退出维护时，按事件接收顺序重新排队投递，之后的并发与重试与平时相同 | M6 |
| B6 | preview 地址没有工作负载时（已下线，或从未部署），显示平台的「未部署待验证版本」说明页，代替网关报错 | M1 |
| B7 | 集群管理（RFC-010）对非正式槽的「删除」改为同一个下线动作，原因记为「集群管理」 | M1、M9 |
| B8 | 发布时间线加上下线、重新部署、推迟、提醒，以及进入、调整、退出维护的记录，带操作人姓名 | 审计需要 |
| B9 | 提醒记在库里并显示在发布页与概览，同时经现有通知端口发出（与开发会话空闲提醒一样，目前只写平台日志） | M19 |
| B10 | 「平台设置」页放在管理左栏末尾，单独成「平台」分组，不改动现有分组 | M28 |

## 5. 用户故事

1. **负责人：回退窗口到期自动回收。** 发布 v1.3 并切流后，v1.2 留在待命槽作为回退目标。发布页写着「将于 9 月 26 日 14:00 自动下线」。到期前 24 小时，发布页和概览出现提醒，负责人可以「推迟 72 小时」。到期后 v1.2 下线，Pod 释放；时间线记一条「保留期满，平台自动下线 v1.2」。
2. **负责人：主动下线闲置的待验证版本。** 待验证卡上点「下线」，确认后工作负载删除，preview 地址显示说明页。之后想再给测试者试用，在发布记录里对这个版本点「重新部署」，几十秒后待命槽就绪。
3. **负责人：修数据时临时维护。** 在正式版本卡上点「进入维护」，勾选拦用户流量、拦其他服务调用、暂存事件，填写原因和预计恢复时间，指定一位业务方同事临时放行。成员照常打开 prod 地址核对，其余人看到维护页；其他数字人调用它的接口得到 503；GitLab 事件在「维护暂存」里排着。退出维护后，暂存的事件按接收顺序补发。
4. **负责人：发布含破坏性迁移的版本。** 进入维护并三个开关全拦，发布，迁移在待命槽部署时执行；切流（同样要求完整维护），验证，退出维护。没有进入完整维护时，发布与切流都会被拒，并说明原因。
5. **测试者：** 待验证版本已下线时打开 preview 地址，看到「当前没有待验证版本，已于某时下线」，而不是网关错误。
6. **普通用户：** 市场卡片显示「维护中」与原因；打开 prod 地址看到维护页和预计恢复时间。
7. **平台管理员：** 在「平台设置」调整三个时长；对任意项目下线待验证版本、开关维护、重新部署历史版本。

## 6. 能力影响清单

四项都是 breaking change，作者 2026-09-23 逐项确认（M20）。每条禁用或拒绝分支都有用例（开发规则 §5.5）。

| # | 被关闭或收缩的能力 | 受影响的形态 | 处理 |
|---|---|---|---|
| 1 | 全平台维护窗口 | 环境变量 `CS_MAINTENANCE_WINDOW`（`packages/settings/platformSettings.ts:71`）与 `ReleaseSettings.maintenanceWindow`；管理员不能再一次为所有项目打开维护窗口 | 删除。项目在完整维护（三个开关全拦）中才能部署含破坏性迁移的版本，切流到这类版本也一样（M17、M27） |
| 2 | 基线的「暂停项目」 | Design §4.3 的 `POST /v1/admin/projects/:id/pause`、§9.7「暂停项目」一行、Plan T6.7 与 AT-24 的暂停项目部分；项目状态 `paused`（契约 `ProjectStateSchema`、项目状态机、工作台两处状态筛选、项目生命周期卡、中英文文案）。之后没有任何办法停掉正式槽的 Pod | 基线作废这些条目；删除 `paused` 状态（库里没有处于该状态的项目，本机核对 11 个项目全是 `active`）。替代做法：下线待验证版本，加正式版本完整维护 |
| 3 | 切流后随时可以即时回退 | 今天回退目标一直保留到下一次发布。改后默认 72 小时下线，之后回退要先从发布记录重新部署、等它就绪、再切回 | 可推迟、不限次数；管理员可以调整时长 |
| 4 | 待验证版本一直可以试用 | preview 连续 14 天（默认）没人访问就下线；之后测试者打开 preview 看到「未部署」说明页，需要负责人重新部署或发布新版本 | 到期前 24 小时提醒，可推迟；管理员可以调整时长 |

## 7. 验收标准

| 编号 | 内容 |
|---|---|
| SM-01 | 负责人在发布页下线待验证版本：待命槽 Deployment 删除（`kubectl` 核对），Service 保留；槽显示「已下线」与原因、时间；发布记录中该版本状态为「已下线」；时间线有带姓名的记录 |
| SM-02 | preview 地址在待命槽没有工作负载时，浏览器得到平台的「未部署」说明页，接口请求得到 503 JSON |
| SM-03 | 从发布记录重新部署一个已下线的版本：不产生构建与迁移 Job，待命槽回到就绪并可切流；重新部署的版本早于正式版本、而正式版本含破坏性迁移或禁止回退时被拒 |
| SM-04 | 切流后新待命槽显示回退目标的到期时间（72 小时）；待验证版本显示无人访问的到期时间（14 天），访问 preview 后到期时间向后推 |
| SM-05 | 到期前 24 小时发出提醒（记录、时间线、发布页与概览可见）；负责人推迟后到期时间加一个周期、提醒重置，可以反复推迟；未经提醒不下线 |
| SM-06 | 到期后平台自动下线，原因分别记为「保留期满」「无人访问」；推进过程中的发布或集群运维操作期间不动 |
| SM-07 | 升级时已存在的待命槽从升级时开始计时，不会在升级后立刻被下线 |
| SM-08 | 负责人进入维护（三个开关、原因、预计恢复时间、临时指定的人），可以调整、可以退出；切流后维护仍在；开发者、测试者看得到维护状态但不能操作；非成员得 404 |
| SM-09 | 用户流量开关打开时：负责人、开发者、测试者、平台管理员、临时指定的人访问 prod 地址照常；其他登录用户看到维护页（原因、预计恢复时间），接口请求得到 503；开关关着时所有人照常 |
| SM-10 | 服务域开关打开时：其他服务调用它暴露的接口（含 `/api/<proxy>/`）得到 503；项目自己的负载与平台组件照常；开关关着时照常 |
| SM-11 | 事件开关打开时：推给它的事件进入「维护暂存」，不算尝试、不进死信；开关放开或退出维护后按接收顺序补发并投递成功；开关关着时照常推送 |
