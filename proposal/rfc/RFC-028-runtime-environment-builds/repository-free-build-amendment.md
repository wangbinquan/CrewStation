# RFC-028 仓库无关构建补充方案

状态：已实施并交付。2026-09-27，作者明确批准“按推荐方案实现”；a12c7d13 已推送并部署，精确SHA六项CI通过，无仓库构建、两业务工具验证及真实业务任务初始化执行已完成，详见 acceptance.md 末节。

## 问题与当前边界

扩展前配方只有 `source`（仓库 Dockerfile）和 `existing`（登记已有平台仓库镜像）。平台镜像已不归属于业务，但从零构建仍需要选择来源业务及其仓库；登记已有镜像不能替代平台内安装依赖、执行脚本的构建能力。

## 用户流程

新增镜像弹窗中的“构建来源”提供三项：**直接编写 Dockerfile**、从仓库构建、登记已有镜像。直接编写不展示也不要求来源业务、仓库或分支。

选择用途与架构后，编辑 Dockerfile；平台提供任务／Agent／服务的起始示例。Dockerfile 可安装 pip/npm/系统软件包、运行脚本和下载二进制。脚本可通过 Dockerfile heredoc 写入；需要 `COPY` 的文件通过“构建文件”上传并指定相对路径，不需要为此建立业务仓库。文件列表显示路径、大小和删除操作，二进制不强制作为文本编辑。

保存生成不可变配方修订；“保存并构建”固定该修订并显示构建进度、日志和产物版本。修改 Dockerfile 或构建文件生成新修订，不覆盖正在运行或已完成构建的输入。后续验证、业务授权、版本选择和实际使用历史全部沿用现有入口。表单与文件编辑均在统一弹窗或独立页面，不向列表底部追加。

## 实现设计

- 在 `RuntimeImageSourceSchema` 增加独立 `inline` 分支，包含 Dockerfile 内容、构建文件、架构、用途、可选 target、普通构建参数及 Agent 底座修订。内容保存在 runtime-environment 配方记录，不自动创建或借用 GitLab 仓库。
- 首版界限：Dockerfile UTF-8 不超过 256 KiB；最多 32 个构建文件，解码后总量不超过 512 KiB。文件内容用严格 base64 表达，路径限制为上下文内相对路径，拒绝重复、绝对路径、越界、链接和平台保留文件名。较大二进制通过固定 URL 加校验摘要下载；未来需要大文件时再接平台对象存储，避免把上传功能伪装成无上限。
- 不可变修订的摘要覆盖 Dockerfile、文件路径／内容／执行权限、构建参数和底座。接受请求前校验总大小，避免存储与 Kubernetes 挂载尺寸不一致。重复请求沿用现有幂等机制，不重复创建修订或启动构建。
- 复用现有 Dockerfile AST 策略、BuildKit、构建租约、资源台账、取消／日志／产物回执。inline 构建直接将固定内容挂载并写入隔离构建上下文，不克隆仓库、不申请 Git 凭据。源码与 inline 共用构建执行链；已有镜像登记仍不创建构建 Job。
- 任务／Agent 镜像仍必须继承平台固定的 `CS_BASE_IMAGE`，保留 Runner 和执行契约；仓库无关不改变运行兼容要求。Agent 底座使用具名算力档位及固定修订。服务用途沿用服务镜像规则。
- 构建输入只接受普通配置，不把密码写进 Dockerfile、构建参数或上传文件。首版 inline 不新增平台构建 Secret 管理能力；如需要私有包源凭据，需独立明确凭据管理、授权与日志遮盖合同，不能隐式借用某业务的凭据。
- 源码来源业务字段保持可选且只用于来源边界；inline 普通构建不读取业务仓库或业务 Secret。沿用平台构建的命名空间、额度、产物前缀和管理员管理权限。

## 落地与验收

1. 契约与配方：补 inline 正向解析、空内容、总大小、恶意路径、重复文件、错误编码及权限测试；旧 source/existing 兼容。
2. 执行链：固定输入、无 Git 凭据、真实构建产物身份、失败／取消／重试和控制器重启幂等；不改变既有源码构建流程。
3. 页面：三种来源具名切换、草稿保留、编辑／上传／移除文件、明确校验、版本与日志入口；中英文、明暗、320／390／1440 宽度、键盘与弹窗返回。
4. 实机：不选择任何业务／仓库，构建含 Python 包、npm 包、脚本及二进制的镜像，验证工具并由授权业务实际执行。给第二业务授权后复用同一不可变版本；撤销授权不影响原构建输入。
5. 真实 API 未登录、非管理员、超限请求拒绝；记录精准提交 CI 和本地部署回执。不得以已有镜像登记或单元测试替代真实无仓库构建。
