## 1. 问题与目标

AW 服务中的配置、skills、插件包等不能继续以容器本地文件作为唯一持久来源。用户已明确：**服务容器不要 PVC；执行任务需要 PVC，任务结束后自动清理。** 因此本 RFC 提供服务对象存储能力，并补上任务终结归档和回收合同，不增加服务挂卷功能。

作者在本轮自审中进一步明确：**工作卷寿命跟随整个业务任务，不跟随容器、Pod 或某个执行环节。** 同一 taskId 的环节 A Pod→环节 B Pod→归档 Pod 可依次挂载同一个 PVC／PV；每个环节完成仅回收该执行环境，卷保持同一身份。只有整个任务最终结束且归档／停止条件满足，才删除该任务的 PVC，并由存储供应器回收 PV／底层数据。这是已明确要求，不是新的待定选项。


RFC-027 已解决 CS 执行合同，不等于 AW 接入完成。现状依据：

| 现状 | 源码依据 |
|---|---|
| data 只投影 PostgreSQL，s3 尚未供给 | `modules/data/domain/dataRecords.ts:50–54` |
| v3 创建任务已有 volumeMode，但没有归档与终结清理策略 | `packages/contracts/api/business/requests.ts:9–14` |
| close 目前在执行环境 released 后完成，没有归档收据门槛 | `modules/business-task/application/execution/lifecycle.ts:38–65` |
| persistent 卷投影 retain；只有 follow-container 自动发出卷释放 | `modules/task-runtime/domain/ledgerProjection.ts:176–184` |
| 回收先等子执行结束，再删除父 Pod，卷删除判断仍取决于 follow-container | `modules/task-runtime/application/nativeExecution.ts:154–172` |

以上是批准时的现有实现；以下为本次已批准的目标合同，完成情况以 plan.md 和实施证据为准。

## 2. 数据放在哪里

| 数据 | 持久来源 | 谁改造 |
|---|---|---|
| AW 任务状态、配置、权限、版本指针、小型 skills 文本 | AW PostgreSQL | AW 后续接入工作 |
| 插件包、大附件、上传文件、归档产物 | S3 兼容对象存储；PG 保存身份、摘要、权限与引用 | CS 本 RFC 提供接口，AW 适配 |
| git、worktree/iso、依赖、运行中的原生会话和 Runner 日志 | 每个父业务任务的 PVC | 沿用 RFC-027；CS 补终结生命周期 |
| 服务临时缓存 | 容器临时目录，可随 Pod 丢失 | AW 后续改造为可重建缓存 |
| 密钥 | 平台 Secret／配置 | 沿用配置注入；AW 不再临时生成持久主密钥 |

对象存储通过 API 读写，不挂成服务目录。多副本和蓝绿槽使用同一服务的生产存储空间、独立对象版本与数据库引用；不需要 RWX。AW 仍需解决单主调度、PG 冷启动、身份与远程执行，不能只换 spawn 就认为完成接入。

## 3. 使用过程

1. 默认选择 Garage v2.4.1：本机提供可选的独立系统组件安装，正式环境登记经过验证的 Garage 后端；校验访问与数据完整性能力，给项目配置容量上限。具体对照、单机／生产边界见 [存储选型](./storage-selection.md)。
2. 开发者在服务 Manifest 声明对象存储。CS 建立按项目、服务和环境隔离的逻辑空间；服务通过平台身份调用文件接口，不取得整个 bucket 的凭据。
3. 应用上传不可变对象，平台验证后返回 objectId、摘要与长度。应用把 objectId 写入自己的数据库；下载按权限读取，服务重建不丢数据。
4. AW 创建带终结回收策略的 persistent 业务任务。暂停、等待人工和仍需重试的失败留卷。
5. AW 判断最终成功、最终失败或取消后，提交终结意图和需要保留的文件清单。CS 停止接纳新执行，确认任务静止，归档并持久保存收据，再自动回收 Pod／PVC。
6. 用户在任务详情看到业务结果、归档结果和资源清理结果。归档完成但清理仍在进行时，不显示「全部结束」。已归档产物在任务卷删除后仍可下载；日志全文不自动等同于长期产物，留存提案见 D6。

终结由业务应用明确声明；CS 不从某个 Agent 退出、Pod 失败或等待人工推断整个工作流结束。

## 4. 能力影响清单

| 对象／操作 | 新行为与影响 |
|---|---|
| 服务挂载 PVC、RWX 服务卷 | 原草案未实施，本 RFC 删除该目标；无服务本地目录持久化保证 |
| 已有 v2/v3 任务与 retained 卷 | legacy 保持原 volumeMode：persistent 留卷，follow-container 按原规则删除；不统一改 retain，不批量清理 |
| 新启用终结回收的任务 | persistent 在 pause 时保留；必须走 finalize 归档握手；旧 close 返回明确前置条件错误 |
| finalize 后重试／resume／写文件 | 被关闭；卷最终会删除。需要再次执行时创建新任务，可显式引用已归档产物 |
| 原生会话在任务最终关闭后续跑 | 首期不保证；保留事件和结果不等于保留可续跑的原生会话 |
| 活动或状态未知的执行 | 不强删，不凭超时推断停止；终结操作显示阻塞原因，取消与确认继续可用 |
| 归档失败、对象存储不可用或容量耗尽 | 自动重试可恢复错误并保留卷；不可恢复错误等待修正，不自动丢弃唯一数据 |
| 终结过程中的清单修订／产物删除 | 清单与收据由同一绑定互斥裁决；回收完成前禁止销毁归档产物，避免先丢副本再删卷 |
| 自动归档范围 | 仅应用显式列出的文件与已有对象引用，加平台事件持久水位；不自动备份全工作区 |
| 新增对象空间与上传 | 有独立容量和并发限额；超限明确拒绝，不占 Agent 算力单位 |
| 项目归档／服务下线 | 阻止新写，保留对象与审计历史；对象销毁是独立确认操作 |
| APIProxy／EventProducer、v2 的对象空间声明 | 首期不开放；明确拒绝新字段，不能静默剥离 |
| 逐条执行事件长期留存 | 建议保留现有七天原始日志语义，长期留摘要／终态证明；应用提前消费现有游标接口并上传产物，断档必须标记，不新增默认全量导出作业（D6） |
| 无应用接管／不可恢复数据 | 新增代终结、确认损失后清理两项提案（D7–D8）；都要求授权，不自动丢数据 |
| 启用新存储后的平台回退 | 首期不允许直接降到 RFC035 前版本；更新后的官方工具拒绝不兼容镜像，不声称能阻止管理员绕过工具启动旧程序 |
| 灾难恢复 | 首期恢复 CS 已归档数据；完整 AW 还需其业务 PG，运行／暂停会话还需任务卷快照，不冒称已覆盖 |
| 对象存储可观测界面 | 管理员看后端、真实容量、吞吐／错误／延迟和积压；项目成员按权限看空间配额、对象、归档／清理及阻塞，观测过期和缺失明确标注 |

每条新增拒绝和能力收缩均纳入 [验收计划](./plan.md)。

## 5. 范围与非目标

本 RFC 只改 CS：对象存储登记与隔离接口、归档操作、任务终结清理、公共资源投影、工作台状态以及接入文档。沿用现有模块，不新建模块或调整层级。

不修改只读的 AW 仓库；不自动迁移 AW 本地文件；不建设通用备份调度系统，但交付对象与 PG 配套备份／恢复操作规程；不保证关闭后原生会话恢复；不安装 RWX、分布式文件系统或 S3 FUSE；不扩大 Agent 算力例外；不清理历史 retained 卷。本机 Garage 安装属于后续实施范围；生产三故障域部署及独立备份目的地是上线依赖。系统 Garage 自己有持久卷，AW 服务仍不挂卷；不能用模拟后端或单机结果冒称生产容灾已验收。

## 6. 本稿请作者审视的决定

已确定的底线是「服务无 PVC、任务有 PVC、最终结束自动回收」。以下 D1–D8 已由作者于 2026-09-28 随 RFC 整体批准；保留原编号供实现和验收逐项对照：

- **D1：存储后端**：默认 Garage v2.4.1，平台代理传输；提供本机单节点系统组件（自有基础设施 PVC，仅开发／验收），生产采用三独立故障域 Garage。支持登记外部端点，但其他 S3 产品需另行兼容验证；详见 [选型与运维边界](./storage-selection.md)。
- **D2：兼容方式**：新任务显式选择 `archive-and-delete`；旧任务以 legacy 沿用原 volumeMode，新模板默认选择新策略。最终状态由应用调用 finalize 声明。
- **D3：留存方式**：终结仅归档明确清单，归档成功后立刻进入自动清理；ready 对象无默认过期删除，显式解除引用并确认后可删除。
- **D4：恢复边界**：暂停继续可恢复；finalize 是不可撤销的终结意图，不再在原卷重试；首期不实现终结后的原生会话恢复。
- **D5：故障处理**：归档失败保留卷，平台不设置「失败超过 N 天就强删」；阻塞可见并允许授权修正归档清单。
- **D6：日志留存**：建议长期留任务摘要、收据和终态证明；原始逐条事件保持现有七天，长留由应用提前显式导出成产物。若要求默认永久全量日志，需再补容量与后台归档策略。
- **D7：代为终结**：建议负责人／管理员在应用无法接管时，经清单预览与确认代为提交最终取消等意图，仍走相同归档及停止屏障。
- **D8：确认数据损失**：建议只在不可恢复且负责人／管理员明确确认时，写 lossReceipt 后清理，状态明确为 completed-with-loss；不自动触发、不绕过停止证明。
