# RFC-035｜本机传输性能记录

## 环境与边界

2026-09-29，Bun 1.3.13、真实隔离 PostgreSQL 17 与 Garage 2.4.1 RF1。Garage 限制 1 CPU／512 MiB；显式 `NO_PROXY=*`，排除本机系统代理。直连指调用同一个 S3 适配器；平台通道包含正式对象 HTTP／元数据／独立字节 listener。字节逐一核对长度和 SHA-256。没有经过 Traefik，也没有模拟三节点生产耐久。共享机器同时有测试／归档负载，数值是本次测量，不是吞吐上限。

每格一个批次、并发 1 或 4，P95 只描述这 1／4 次传输，不是长期统计。普通 API 每 100 ms 读一次对象空间；CPU 数据、原始耗时、样本数和进程内存完整保存在 `/tmp/cs-rfc035-performance-direct-final.json`。API 峰值取该格上传／下载阶段的最大值，包含进程已分配但尚未返还的内存；直连时字节主要在客户端进程，API 只接受并行普通请求。

## Linux 部署内存限额验证

额外将同一 API 组合放入原生 Linux ARM64 的 Bun 1.3.13 容器，限制 **1 CPU／1 GiB 内存**，Garage 与 PG 仍独立。四路各 1 GiB 上传、完整读回验证及下载全部完成，API 进程 RSS 峰值 **453.2 MiB**；上传 60.28 MiB/s、下载 64.93 MiB/s，普通 API P95 最大 103.2 ms。客户端正常退出 0，没有通过提高容器内存限制完成验证。原始记录 `/tmp/cs-rfc035-linux-memory.json`、`/tmp/cs-rfc035-linux-memory.log`。

macOS 四路数据的 RSS 分配行为与 Linux 不同，不能直接用 macOS 数值宣称集群会 OOM，亦不能用单次通过宣称所有流量下都只有该内存用量。真实 TCP 停读／取消和分段读取用例另外约束流控。

## 小文件归档与发现的缺陷

一万份 4 KiB 文件使用只读 Linux 助手、正式授权／上传／验证／结果确认接口和真实 Garage。早期运行保留以下未完成记录：系统代理介入；逐文件重复读取整份清单；负载下元数据锁超时返回 409，被助手当作冲突结束。已排除代理、按路径查询清单并将临时锁拥堵改成可重试 503，保持 2 秒准入上限和原有冲突拒绝。对应日志 `/tmp/cs-rfc035-scale-direct.log`、`/tmp/cs-rfc035-scale-diagnostic.log`。

修正后完整运行 `/tmp/cs-rfc035-scale-verified.log` 执行中。夹具若需替换到时的助手，只在 Docker 确认原进程退出后关闭旧授权、复用相同 binding 与已验证上传；这验证持久接续，不代替真实 Kubernetes 停止证明或原 PVC/PV 回收验收。结果未产生前不计为通过。
