## 1. 来源与范围

作者于 2026-09-22 提出：给每个项目呈现各自的部署和运行形态（当前有几个工作负载、几个 Pod 在执行、执行时间、Pod 信息），以图形化方式呈现；
平台管理的集群管理界面也要图形化呈现系统的各元素和部署状态；要求先充分反问对齐思路，再出原型，看过后再动手。

作者提到的 Archify（tt-a1i/archify）经查是 Agent 技能加 Node CLI，把 JSON 中间表示渲染成自包含 HTML，没有运行时组件、没有喂活数据的接口。
作者说明「说 archify 是指它渲染的图好看」，认可借鉴其视觉、由工作台自绘组件（十四问的答复「按你推进的来做」）。

本 RFC 的范围：一个无第三方依赖的 SVG 形态图组件；项目侧两处入口（概览缩略、运行与诊断全图）；集群管理一个新页签（系统层、项目层、Pod 层）；
一条给项目成员的项目范围只读盘点接口；集群摘要按项目计数。数据全部来自 RFC-010 的集群盘点快照与现有项目接口，不新增采集、不新增管理动作。

## 2. 三处入口与展示内容

### 2.1 项目概览（`/projects/:id`、`/admin/integrations/:id`）

两张部署卡之下新增「部署与运行形态」卡：一行横带汇总卡铺满内容区，每条横带一张卡（线上槽、待命槽、开发会话、业务任务、构建与迁移），
显示最差状态、Pod 数与就绪数、需要关注数、版本或人；卡上方一行计数（工作负载、Pod、就绪、运行、需要关注）。点任一卡进入运行与诊断的全图。

### 2.2 运行与诊断（新页签「部署与运行形态」）

横向四条泳道：入口 → 工作负载 → Pod → 数据与存储；纵向按横带排：线上槽、待命槽、开发会话、业务任务、构建与迁移。节点与显示项：

| 节点 | 来源 | 显示 |
|---|---|---|
| 入口（主机） | release 槽的 `host`、开发会话的 `previewHost` | 域（用户域／服务域）、指向的槽或开发容器、当前指向 |
| 工作负载 | 盘点里的 Deployment／Job | 版本 tag 与 SHA、副本 期望／就绪、发布 id、年龄 |
| Pod | 盘点里的 Pod（用途分类沿用 RFC-010） | 用途、节点名、重启数、存活时长、状态短语（`ContainerCreating`、`Insufficient cpu` 原样保留）；Agent 与子任务 Pod 另显示执行时长、档位、上级任务 |
| 数据与存储 | data 模块的 DataResource、盘点里的 PVC | 生产库／开发库、套餐、注入的环境变量名；工作卷容量与绑定状态 |

连线只画观测到的关系：主机路由到槽、工作负载管理 Pod、Agent Pod 从属开发工作区、Pod 挂载工作卷、Pod 连接数据库（按注入的环境变量名）。
筛选：用途、状态、只看需要关注；右侧只读详情：概览事实、关联（可点跳）、容器、事件，并给出去往日志、开发会话、发布与上线的入口。

### 2.3 集群管理（新页签「拓扑」）

三层，默认系统层：

- **系统层**：调用方 → 网关与身份 → 平台服务 → 基础组件 → 外部系统五条泳道；`crewstation-system` 命名空间画成边界框，
  九个 Deployment 与两个 StatefulSet 的状态来自盘点；调用方一栏是项目命名空间的聚合卡（服务槽、开发会话与 Agent、业务子任务、构建与迁移）；
  调用关系是静态架构标注（虚线），默认显示，图例明写「不是实测」。
- **项目层**：每个项目一张卡，工作负载／Pod 与就绪／线上与待命或开发会话三行计数；需要关注的项目置顶；正常项目超过 60 个时只显示前 12 个并折叠。
- **Pod 层**：从项目卡的详情进入，与运行与诊断的全图同一组件、同一份快照；面包屑可返回项目层。

点节点打开右侧详情：Pod 层与系统层复用 RFC-010 的资源详情（事件、日志、管理动作仍在那里）；项目层的卡片详情给出命名空间、两槽版本、开发会话与需要关注的原因，并可展开 Pod 层。

## 3. 视觉与交互规则

- **颜色只表达语义。** 九个固定语义：网关入口、身份与安全、服务槽、开发会话、业务任务、构建与迁移、数据与存储、平台组件、外部系统；每个语义一组描边色与填充色，浅色深色各一套，进 `tokens.css`。
- **状态不靠颜色单独表达。** 状态点加状态短语；等待中虚线边框、失败红边加警示三角、外部系统点线边框、已完成淡填充。Running 不等于 Ready，计数口径沿用 RFC-010 §4。
- **两种证据分开画。** 观测到的关系实线；静态架构标注虚线并在图例说明。
- **排布确定、不重排。** 泳道与横带由数据顺序或显式行号决定；每 15 秒换一份快照时节点位置按 UID 固定，只有新增行会把下方横带下移。
- **宽度用满。** 节点随容器撑宽、1:1 渲染；项目层列数随宽度 2–8 列；内容区不设最大宽度（已于 2026-09-22 对全部页面去掉 1200px 上限，提交 `6a69195`）。
- **窄屏降级。** ≤640px 不画 SVG，改为按横带分组的列表，语义与状态提示一致；320／390px 无整页横向溢出。
- **可达。** 节点是 `role=button` 的可聚焦元素，Enter／空格选中，聚焦与悬停同样压暗无关节点；尊重 `prefers-reduced-motion`。
- **部分来源失败** 时观测行明写失败来源，受影响的计数显示占位而不是 0，图上受影响节点标「待核对」。

## 4. 已裁定的设计取舍

2026-09-22 十四问作者答复「按你推进的来做」，采用当时的推荐；两轮原型评审后作者另作裁定：

| 项 | 裁定 |
|---|---|
| Archify 的用法 | 只做静态对照，不引入、不 fork 渲染器；工作台自绘 SVG 组件借鉴其视觉 |
| 项目页位置 | 概览放缩略（横带汇总卡），运行与诊断放全图 |
| 谁能看 | 负责人、开发者、管理员；测试员不看 |
| 画哪些元素 | 入口、工作负载、Pod、数据与存储全画 |
| 执行时间 | 图上只画活着的，Pod 显示存活时长，Agent／子任务显示执行时长；已结束的执行只在详情或历史里 |
| 数据来源 | 项目成员经新的项目范围只读盘点接口读同一份快照；不用现有项目接口拼 Pod 事实 |
| 集群层级 | 系统层、项目层、Pod 层三层，默认系统层 |
| 连线含义 | 系统层画静态调用线并标明；项目层只画观测关系 |
| 与现有页签 | 新增「拓扑」页签，计数卡不动 |
| 规模 | 异常置顶；正常项目超过 60 个折叠 |
| 交互 | 点节点开详情；筛选与图联动 |
| 刷新与移动端 | 位置按 UID 固定；不做缩放；手机宽度降级为列表 |
| 依赖 | 零新依赖，确定性分层排布，不引入 dagre／elk |
| 详情面板 | 放右侧（作者 2026-09-22） |
| 静态调用线 | 默认显示（作者 2026-09-22） |
| 语义色 | 进 `tokens.css`（作者 2026-09-22） |
| Archify 对照图 | 不入库；IR 保留在原型目录（作者 2026-09-22） |
| 内容宽度 | 全部页面去掉 1200px 上限（作者 2026-09-22，已实施） |

> **2026-09-23 修订（作者当面裁定，直接修改，不另立 RFC）。** 「新增拓扑页签，计数卡不动」改为：拓扑升为集群管理的**默认顶层页签**（`tab` 缺省），
> 与「资源清单」并列；计数卡压进顶部指标条。三层、层级切换（改用共享的 `Segmented` 控件，行为不变）、右侧详情、静态调用线与宽度用满都不变。页面结构见 RFC-010 §3 同日修订。

## 5. 非目标与能力影响

- 不新增采集、不改 RFC-010 的快照周期与操作模型；不新增重启／扩缩／删除入口。
- 不做力导向布局、自由拖拽、缩放平移；不做历史回放。
- 不引入 Archify 或任何图形库；不把静态架构标注当实测流量。
- 不改现有页签、计数卡、资源表；不改开发会话页。
- **能力影响清单**：本 RFC 不关闭、不收缩任何既有能力（开发规则 §5.5 不适用）。

## 6. 验收标准

按 [plan.md](./plan.md) §2 的 TP-01…TP-18 逐项实机核对；概括为：

1. 三处入口在本机集群的真实数据上渲染，节点、连线、计数与 `kubectl`／现有页面一致，没有凭空的 Deployment 或 0 冒充读取失败。
2. 项目成员（开发者、负责人）能看本项目的图与 Pod 事实，测试员 403，跨项目 403；管理员三层可用，Pod 层与系统层详情等于 RFC-010 资源详情。
3. 换快照不重排；部分来源失败有明示；1728／1280／1024 铺满内容区且无整页横向溢出，390／320 为列表；浅色深色、中英文、键盘可用。
4. 完整本地 gate、改动行防护、精确 SHA CI 全绿；本机部署与浏览器验收记录在 `acceptance.md`。

## 7. 待作者确认

**项目成员看 Pod 级信息的边界。** 建议：项目成员看到的 Pod 事实与管理员在集群管理里看到的同一投影（名称、用途、状态与原因、重启、创建时间、节点名、镜像、容器状态、上级任务／Agent／终端 id、发布与槽），
**不含**环境变量值、Secret、完整注解、原始 YAML（RFC-010 的投影本来就不含），并且 `availableActions` 恒为空；事件、日志、管理动作仍只在集群管理里给管理员。
作者若认为节点名或镜像不该给项目成员，请指出，实施时按裁定裁剪。

**作者 2026-09-22 裁定：按建议实施**（「按你的建议来做，批准」）。实施结果：成员经 `GET /v1/projects/{projectId}/cluster-resources` 拿到 RFC-010 同一份投影（须有该项目的 `develop` 授权），`availableActions` 恒为空；成员详情里的「查看日志」进本项目日志页，Kubernetes 事件与管理动作仍只在集群管理。
