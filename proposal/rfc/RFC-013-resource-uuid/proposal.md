# RFC-013｜平台资源统一使用完整 UUID

> 状态：In Progress · 2026-09-20；作者已批准实施、部署及提交上库。
> 来源：作者要求「现在系统内的各种资源索引已经用长uuid了吗，有没有还是用name的，都要统一改成长uuid，和agent-workflow一样」。
> 作者已确认格式：「标准 UUIDv7：36 字符、带连字符，名称只作展示属性」；随后明确回复「批准实施、批准部署、批准提交上库」。

## 1. 问题与核对结果

当前资源身份没有统一：

- 项目、服务、用户、发布、任务等多数实体已用完整的 128 位随机标识，但序列化为 `prj_`／`tsk_` 等前缀加 32 位十六进制；不是截短 UUID，也不是标准带连字符 UUID。
- 服务套餐、任务资源套餐、算力档位、API 代理、API 操作、事件生产方、事件类型仍把名称或名称组合当主键。配置项及算力凭据也通过含名称的复合键定位。
- 项目模板按目录名选择；启动前步骤使用 `file-1` 等短 ID。改数据库的一两个字段不能完成这次统一。
- 集群运维操作等已经使用标准 UUID；Runner 原生会话、Kubernetes UID、Git SHA 等属于外部标识或协议值，需要保留其含义。

逐项源码证据见 [audit.md](./audit.md)。核对范围是当前源码与契约，不是对运行数据库逐行做过检查。

参照仓库的实际情况也已核对：agent-workflow 的 Agent、Skill、Workflow、工作组由 `ulid()` 分配独立 ID；这些是 ULID，不是标准 UUID。借鉴的是**资源身份与名称分离**。作者随后明确选择 UUIDv7，因此本 RFC 的目标为 36 字符、带连字符的 UUIDv7，平台自有的旧 UUIDv4 也纳入迁移。

## 2. 目标

1. 每个可独立创建、选择、修改或引用的平台资源都有稳定、不可修改的完整 UUID；数据库主键、资源引用、管理 API 路径、前端路由、选择值和缓存键使用该 ID。
2. 名称用于显示与搜索。仅修改显示名称时，ID、关联关系、历史记录和已有书签保持稳定；复制得到新 ID。
3. 套餐、档位、模板、代理、操作、事件定义、配置项、凭据与步骤全部纳入，不只修改已有 `*IdSchema`。
4. 迁移旧库中的资源及引用；保留已发布记录、固定修订、任务工作卷和现有业务数据。无法判定归属的历史引用要报告并阻止切换，不能猜测后绑定。
5. 补齐契约、升级、真实数据库、工作台及运行链验证；最终有防止重新引入名称主键与短 ID 的检查。

## 3. 名称与业务符号的边界

UUID 标识资源身份。环境变量 `DATABASE_URL`、HTTP 方法和路径、事件类型编码、DNS 地址、Git 分支／标签、文件路径仍表达原来的业务含义。它们可以有唯一约束或查询索引，不能再充当另一资源的持久主键。

例如：API 操作有 `operationId`，同时保留 `method` 和 `path`；配置项有 `configItemId`，同时保留用于注入的 `name`；步骤有 `stepId`，同时保留 `name`。网关先把业务路径解析成资源 ID，再按 ID 使用目录和关系。

Manifest 中引用平台资源的套餐、算力、API、订阅及配置绑定升级为 ID 引用。Manifest 自己声明的 Agent 档案与输出契约可保留项目源码里的符号名，但发布时必须生成稳定 ID 与映射，执行及历史关联使用 ID。已有符号调用仅在明确的兼容入口解析，不把名称继续保存成平台关系。

## 4. 用户故事

- 管理员编辑算力档位的名称后，项目仍选中原档位，默认设置与允许清单保持，已受理 Agent 仍使用原固定修订。
- 开发者在列表里看可读名称，选择和复制链接时得到完整 ID；同名资源不会误操作。
- 管理员维护服务／任务套餐后，通过 UUID 更新原资源；创建与更新分开，输入同名不会静默覆盖另一资源。
- 发布同一组 API 和事件声明，不会反复产生新 ID；删除或更换协议操作仍按现有生命周期规则处理。
- 已有项目升级后能打开、继续开发、查看历史、发布、调用 API 和投递事件；迁移不重建业务库或工作卷。

## 5. 能力影响清单与建议兼容策略

以下是需随本 RFC 一起批准的变更，不能以重命名名义静默实施。

| 受影响能力 | 目标行为 | 建议过渡 |
|---|---|---|
| 按 name／旧前缀 ID 访问管理接口与页面 | 新接口和页面只生成、存储完整 ID | 旧读链接经显式只读解析入口转到新地址；响应提供 canonical ID；修改请求不接受含糊的 id-or-name |
| 以名称 upsert 套餐／配置／凭据 | 显式创建与按 ID 更新；名称只作业务字段 | 同步升级 console、CLI、MCP；旧写法返回明确字段错误及迁移指引 |
| Manifest 平台资源引用 | 使用 ID；默认档位使用显式默认选择语义 | 版本化解析旧 Manifest 并保存解析后的引用；新编辑和新模板生成新格式 |
| 本地 Agent 档案／输出契约的符号名调用 | 服务边界解析后得到固定资源 ID | 为当前发布保存一次映射，重试沿用已受理 ID，不重新按名称解析 |
| 改名与复制 | 显示名称改变不换 ID；复制资源及其子资源得到新 ID | 协议名、HTTP path 和事件编码改变仍按契约变化处理，不自动继承其他操作的关系 |
| 已运行的旧 Runner、已部署业务和旧令牌中的引用 | 经有界、显式兼容入口映射到新 ID | 保留协议版本与旧 ID 映射；不能只收紧 Schema 使现有容器失联；兼容入口移除另行落档 |

迁移旧数据是方案的一部分。对共享集群实际执行维护切换时，应先给出具体备份、影响清单和执行步骤；本草案没有执行这些动作。

## 6. 验收标准

| 编号 | 可观察结果 |
|---|---|
| ID-01 | 新建与复制的所有平台资源返回完整 UUID，名称与 ID 分离；短 ID／名称不能写入资源引用字段 |
| ID-02 | 显示名称修改不改变 ID、关系、路由、默认设置；重名不会使选择或操作串到另一资源 |
| ID-03 | 服务套餐、任务套餐、算力档位、项目模板的选择到实际开通／启动全链按 ID 生效 |
| ID-04 | 固定修订、启动步骤、凭据、测试记录、项目算力允许清单与默认值完整迁移 |
| ID-05 | API 目录、申请、Grant、Swagger 试调和网关使用同一个 operationId；重复发布 ID 稳定 |
| ID-06 | 事件生产方、类型、订阅、收件与投递关联按 ID；去重、重投和历史查看不变 |
| ID-07 | 配置项按 ID 修改／删除，变量名和开发／生产隔离及版本历史完整保留 |
| ID-08 | 旧库升级保留数量与关系，重复运行幂等，失败可回退；哈希式旧 ID、保留主体、跨类型同后缀均覆盖 |
| ID-09 | 旧链接、历史 Manifest、旧业务请求和运行中 Runner 有明确兼容行为；不得静默改指向或丢历史 |
| ID-10 | Pod／PVC 的实际名称和 UID 保留，新命名不依赖旧前缀长度；重连和保卷恢复成功 |
| ID-11 | console／CLI／MCP 的传参、路由、缓存键按 ID，显示仍可辨识，长 ID 不造成窄屏溢出 |
| ID-12 | 全量本地门禁、变更行防护和发布精确 SHA CI 通过；实机证据及未验证项独立记录 |
