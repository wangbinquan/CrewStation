## 1. 来源与已确认范围

| 编号 | 来源 | 要求 |
|---|---|---|
| C1 | 作者原始需求 | 平台提供 Kubernetes 集群管理界面，看到工作负载、Pod 等资源的数量与运行情况，每项能辨认所属项目与 Pod 类型，包含系统内置工作负载 |
| C2 | 作者本轮明确选择 | 首版同时支持重启工作负载、调整副本、删除资源等操作 |
| C3 | 作者本轮明确选择 | 只覆盖 CrewStation 管理的项目资源与平台内置服务；不做整个 Kubernetes 集群的通用管理台 |

管理员从管理空间进入。覆盖 DigitalWorker、APIProxy、EventProducer 三种项目，归档项目的残留资源仍可查。
平台服务、工作台、平台 MCP、数据库、网关、镜像仓库、构建器、算力档位测试和本机 dev-auth 均纳入。
`kube-system`、`local-path-storage` 等集群基础组件不进入资源列表与统计。部署形态中没有的组件显示不存在，不造记录。

生产实现已落地；交互预览仍仅为演示附件。模块、浏览器与集群验收分开记录，见 [acceptance.md](./acceptance.md)。本机 RBAC 已获具体批准并应用，完整清单与专用项目真实动作已核对，发布门禁见验收记录。

## 2. 要解决的问题

现在项目目录、开发会话、发布页与日志页分别展示平台对象，没有跨项目的 Kubernetes 资源目录。
只按 `managed-by=crewstation` 查会漏掉部分内置组件；只读 `workload=dev-session` 又分不清工作区容器与独立 CLI。
运维动作还必须与任务释放、发布槽、配额、保卷恢复协同。具体证据见 [audit.md](./audit.md)。

管理员的完整路径是：**发现异常或资源规模 → 按项目／用途定位 → 查看关联工作负载与容器 → 执行操作 → 看见实际结果**。
页面不能只回“请求成功”；必须保留目标、操作 ID、操作者、时间、进度和失败原因。

## 3. 页面与使用路径

新增管理导航 **集群管理**，地址 `/admin/cluster`，沿用现有管理空间与管理员守卫。

首屏提供可点击的数量摘要：工作负载、Pod（Running 与 Ready 分开）、Service、PVC、异常资源。
摘要注明当前范围与采集时间；切换项目、命名空间或系统范围时同步变化。未能读取的资源不能算成 0。

固定页签为 **工作负载／Pod／网络／存储与配置／命名空间／操作记录**：

| 页面 | 主要内容 |
|---|---|
| 工作负载 | Deployment、StatefulSet、DaemonSet、Job、CronJob、独立 ReplicaSet／ReplicationController；默认隐藏受上层控制器管理的中间对象，详情可展开 |
| Pod | 全部在范围内的 Pod，包括独立工作区／Agent Pod；用途、项目、拥有者、状态、Ready、重启次数、节点、创建时间 |
| 网络 | Service、Ingress、IngressRoute、Middleware、NetworkPolicy 的有界概要和关联关系 |
| 存储与配置 | PVC、ConfigMap、Secret 元数据、ServiceAccount、ResourceQuota；显示引用关系，配置正文仍在对应配置功能维护 |
| 命名空间 | 项目／系统命名空间、项目状态、配额；不把命名空间本身称为“运行中工作负载” |
| 操作记录 | 重启、扩缩、删除的受理、执行、观察和结果；可按项目、对象、状态筛选 |

筛选包括：全部／项目／平台系统／归属待确认、具体项目、资源 kind、Pod 用途、状态、命名空间及名称搜索。
过滤条件、页签与选中资源进入 URL；从项目跳入时带 projectId，返回保留上下文。
列表按资源名、命名空间、UID 稳定排序，每页 50 条；数量是完整筛选结果，不能把当页数量当总量。

点资源进入详情：概要、关联对象、容器、事件、日志。日志可选普通／初始化容器与上次终止实例；没有日志时保留原因。
关联对象可跳到其资源详情；有平台对象时可打开项目、开发会话、发布记录、Agent 或档位测试。
尚未实现的跳转不做空按钮；未能解析的关联显示明确状态。

桌面以紧凑表格为主；窄屏摘要双列、筛选单列，资源表格在自身区域横向滚动并保留完整列，点行展开详情；320／390px 不出现整页横向溢出。
沿用共享 Card、DataTable、Badge、Tabs、QueryStatus、InlineConfirm、Stack、ActionRow 与中英文文案。

## 4. 资源归属与 Pod 类型

归属与用途是两个独立字段：

- **归属**：具体项目（名称＋稳定 ID＋项目种类）、平台系统、归属待确认。平台系统不是虚构项目。
- **Pod 用途**：业务服务、API 接入服务、事件接入服务、开发工作区、开发 CLI、开发 Agent、业务任务工作区、业务 Agent 子任务、构建、迁移、算力档位测试、平台服务、平台基础设施、其他／待确认。
- **Kubernetes 类型**：Pod 本身的 kind 始终是 Pod；另列其拥有者，例如 Deployment → ReplicaSet → Pod，或者“独立 Pod”。

服务 Pod 同时显示物理槽 blue／green 与当前角色正式／试用；晋级以后角色跟随 release 的真实映射变化。
不能把 green 固定当正式，也不能根据 Pod 名称包含 `cli` 推断 Agent 类型。
来源缺失、项目归档、标签与平台记录冲突均保留解释。已经确认由平台管理但无法解析项目的对象仍可见。

## 5. 管理操作

**作者已整体批准下列操作语义及实现。**

| 目标 | 重启 | 调整副本 | 删除 |
|---|---|---|---|
| 项目服务 Deployment | 重启该槽，保留版本与配置 | 遵守套餐上限；持久保留运行时覆盖，提供恢复发布配置 | 经 release 更新槽状态；正式槽先切流，试用槽可删除；明确只删选定工作负载及其从属 Pod |
| 独立开发工作区 Pod | 保留同一任务与 PVC 的受控重启；明确中断当前连接与子执行 | 不适用 | 执行“释放开发会话”，先展示未推送改动、子执行与工作卷影响 |
| 开发 CLI／Agent Pod | 通过所属运行流程重新启动一个执行实例，显示新旧关联 | 不适用 | 结束该执行并回收 Pod，保留父工作卷，归还对应配额 |
| 业务任务／Agent 子任务 | 工作区按持久模式恢复；子任务重试经业务契约，不自动重放已完成业务 | 不适用 | 经业务任务取消／关闭与 task-runtime 回收；必须向调用方反馈结果 |
| 已完成 Job／孤立且无平台活动引用的受管资源 | Job 不提供“重启”，保留原记录 | 不适用 | 按精确对象 UID 删除，保留操作记录；运行中的发布 Job 走发布生命周期 |
| 内置 Deployment／StatefulSet／DaemonSet | 按部署策略重启；记录可观测中断 | 仅已声明可扩缩的组件；单实例存储组件给出不支持原因 | 核心组件不开放删除和缩到 0；仍展示资源与限制原因 |
| PVC／Service／配置和策略资源 | 不适用 | 不适用 | 无活动引用的受管残留可删；有引用的资源转所属流程，不能绕过依赖关系 |

每个资源的可执行动作与不可用原因都由服务端返回；前端不按名称猜。
点击动作先显示精确目标、影响范围与相关卷／任务；确认后生成持久化操作记录。取消检查不改变任何资源。
资源在确认期间被替换、发布、切流或回收时，旧确认失效；操作结果无法确认时显示“待核实”，不重复执行有副作用的动作。
删除命名空间、PV、节点及安装级卸载不在本首版操作范围，项目归档和数据生命周期入口保持可用。

## 6. 验收标准

1. 同一范围下，清单、数量与 Kubernetes 实际对象一致；控制器与从属对象不重复计工作负载，独立 Pod 单列。
2. 每项均有明确归属或待确认原因；内置服务与接入项目不会漏掉或混成同一类。
3. CLI／Agent／子任务／档位测试及发布物理槽分类准确，来源不足时不猜测。
4. 从列表定位异常，打开容器原因／事件／日志，再执行可用操作并追到最终实际结果。
5. 重启、扩缩、删除在专用验收资源上实机跑通；不丢任务配额、保留卷或平台状态。
6. 部分 API 故障、首次读取失败、空范围、过期数据和真正的 0 各自可辨识。
7. 中英文、浅深色、键盘、1280／390／320px 验证通过；操作面板不抢刷新焦点。

逐项编号与证据要求见 [plan.md](./plan.md)。

## 7. 已批准的设计选择

- D1：采用本方案的信息架构、归属判定和用途分类。
- D2：采用 §5 操作矩阵；开发会话与 Agent 动作通过现有领域流程扩展，平台核心组件不开放删除／缩到 0。
- D3：项目副本调整保留为运行时覆盖，按 `serviceId＋physicalSlot` 定位，跨该槽后续发布保留，管理员可恢复当前发布配置；不修改源码 Manifest。
- D4：采用 [ADR-0006](../../../docs/adr/0006-cluster-management-module.md) 新增 L6 `cluster-management`，拥有受管资源索引与操作记录，各领域继续拥有各自生命周期。

作者于 2026-09-20 明确要求“完整实现 RFC 并批准提交上库”，D1–D4 随本 RFC 获批。随后作者明确批准本机共享集群 RBAC 应用，实际授权和执行证据记录于验收文档。
