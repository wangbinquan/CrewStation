## 1. 背景

RFC-022 让新开的 CLI 在终端区域中间显示步骤条，「已就绪」时撤掉步骤条、露出终端。问题在于「已就绪」的判据是
**PTY 进程拉起**：Runner 在 `backend.open` 返回后立刻把记录改成 `running`（`runtimes/task/src/terminal/nativeSupervisor.ts:123-126`），
平台把「Agent 启动中」与「已就绪」都记在这一刻（`modules/dev-session/domain/nativeTerminalProjection.ts:49-50,71-77`）。

而 CLI 进程拉起不等于能用。OpenCode 的 TUI 在进程内先起 server worker、校验会话、取初始快照，最后才建渲染器
（OpenCode 源码 `packages/opencode/src/cli/cmd/tui.ts:210-279`、`packages/tui/src/app.tsx:194`）。RFC-022 实测：本机 150m CPU 下
进程拉起约 9 秒后才第一次输出，30 秒内画完整界面（RFC-022 design §14.1 第 12 条）。这段时间步骤条已经撤了，用户看到的是
**一块十来秒不动的黑屏**，像是卡死。

## 2. 目标与非目标

**目标**

- G1 步骤条一直保持到 CLI **真的画出界面**，不再在进程拉起那一刻撤掉。
- G2 进程拉起与界面画出之间单独成段（「CLI 初始化」），有计时，用户知道在等什么、等了多久。
- G3 判据不依赖具体 CLI 的私有协议：OpenCode、Claude Code、通用终端协议用同一套屏幕判据。
- G4 判据失灵时不把用户挡在门外：超时后照常撤步骤条，并在该段写明「未检测到界面，已超时放行」。
- G5 旧 Runner（不上报界面状态）的行为与今天完全一致。

**非目标**

- N1 不缩短 CLI 本身的启动时间（CPU 额度、OpenCode 冷启动不在本 RFC）。
- N2 不让无人持有控制时也能画出界面。STATE.md 已记录的观察（OpenCode 要等终端回答查询、只有持有控制的视图会回答）仍待
  作者另行决定；本 RFC 只保证这种情况下按超时放行，不比今天更差。
- N3 不改档位测试（`ProfileTestPanel`）的阶段：档位测试跑的是一轮模型调用，不是交互界面。
- N4 不用 Agent 动态（OpenCode 插件 `ready`、Claude `SessionStart`）作判据：它们只说明后端加载好了，不说明画面出来了。

## 3. 用户故事

- U1 开发者点「＋」新开一个 OpenCode：步骤条走到「CLI 初始化」并开始计时，十来秒后步骤条消失，露出的就是完整的 OpenCode 界面，没有黑屏。
- U2 同一会话的另一名成员打开页面：看到的是同一份进度（CLI 初始化中／已就绪），与刷新前后一致。
- U3 某个 CLI 因故一直不画界面：90 秒后步骤条照常撤掉，「CLI 初始化」一段写着「未检测到界面，已超时放行」，用户可以点进终端看现场。
- U4 CLI 在画出界面之前就退出了：步骤条停在「CLI 初始化」并标为失败，给出退出信息和日志入口（沿用 RFC-022 的失败展示）。

## 4. 行为

- 步骤条从六段变成七段：……准备环境 → **Agent 启动中**（到进程拉起）→ **CLI 初始化**（到界面画出）→ 已就绪。
- 「CLI 初始化」判为完成的条件（Runner 在自己的无头终端上判定，平台与浏览器都不猜）：
  屏幕上出现可见文字，**并且**此后连续 500 ms 没有新输出（界面画完一帧、停下来等输入）。
  终端能力／光标／配色查询不产生可见文字，不算画出界面。
- 进程拉起后 90 秒仍未判定，按超时放行（G4）。
- 标签头的「x/6」改为「x/7」；状态条在启动中显示当前段，与 RFC-022 一致。
- 创建者窗口在整个启动期间（含 CLI 初始化）都算「在用」，控制不会在界面画出前被 30 秒空闲释放掉（否则 OpenCode 等不到查询应答）。

## 5. 能力影响

本 RFC 不关闭或收缩任何既有能力。唯一可感知的变化：步骤条撤掉的时间比今天晚（晚到界面画出，最多 90 秒）。
这段时间里终端被步骤条盖住、不能点进去输入——今天这段时间终端是空白的，本来也无法有效输入。

## 6. 待裁定

| 编号 | 问题 | 推荐 |
|---|---|---|
| Q1 | 静止窗口取多长 | 500 ms。更短容易在分段绘制的中间判完成；更长则每次都白等。实机按 OpenCode／Claude Code 各测一次再定 |
| Q2 | 超时放行取多长 | 原定 45 秒（RFC-022 实测 150m CPU 下 OpenCode 30 秒内画完）。**修订（2026-09-23，作者裁定）：90 秒**——验收实测 OpenCode 43.2 秒才画出界面，45 秒几乎撞上（[验收 §3](./acceptance.md)） |
| Q3 | 无人持有控制导致 OpenCode 不画界面（N2）是否并入本 RFC，由 Runner 的无头终端在无人持有控制时代答查询 | 不并入。它改变「谁在替 TUI 回话」的语义，涉及控制交接时的重复应答，单独立 RFC |

## 7. 验收标准

| 编号 | 标准 |
|---|---|
| UI-01 | 本机集群新开 OpenCode：步骤条经过「CLI 初始化」段，撤掉时终端已是完整界面；录屏或逐秒截图，撤掉前后各一张 |
| UI-02 | 名册接口返回的 `startup` 七段起止时间单调、首尾相接；「CLI 初始化」的时长与 Runner 日志记录的判定时刻一致 |
| UI-03 | 新开 Claude Code（或通用终端协议）同样在画出界面后撤掉步骤条 |
| UI-04 | 另一名成员与刷新后看到的进度一致；就绪后冻结，不再读事件 |
| UI-05 | 用例覆盖：判定器（可见文字＋静止、仅查询不判完成、超时）、Runner 事件、平台组合（新 Runner 等待／就绪／超时／初始化中退出，旧 Runner 与今天一致）、工作台七段文案与创建者控制保持 |
| UI-06 | 旧任务底座（不上报界面状态）的 CLI 行为与今天一致 |
