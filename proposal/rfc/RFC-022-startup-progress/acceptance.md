## 1. 范围、环境与部署

入口 `http://console.cs.localhost`，context `docker-desktop`。验收专用项目 `rfc022-verify`：项目 `01a0ccdb-2ba7-7000-a131-2840c74aa50b`，服务 `01a0ccdb-2ba7-7001-bbb0-d8c3f792935b`，namespace `cs-rfc022-verify`；负责人 dev-developer，套餐 `rfc010-cluster-qa`（25m／256Mi），并发额度 6，没有临时调整。dev-admin 作为开发者成员加入，用作「另一名成员」。

## 4. 与计划的偏差

- **SP-02 没有用「超大套餐」。** 档位（及其资源规格）保存即测试，通不过就不能选，所以资源大到调度不上的档位开不出 CLI。改用占位 Pod 临时占满节点 CPU，两次各约 40 秒，事先通知了两个并行会话。
- **SP-02 没看到「正在拉取镜像」。** 本机仓库与节点在同一台机器上，150MB 的独有层 331 毫秒就拉完了，短于观测间隔。中间态的文案与判定由用例覆盖；只有在拉取慢的集群上页面才会显示它。
- **SP-05 的三个故障档位。** 档位测试的工作目录是空的 `/work`，而真实 CLI 的工作目录是项目仓库（有 `crewstation.yaml`）。于是：
  - 「启动前脚本失败」的脚本只在有 `crewstation.yaml` 时退出 1；
  - 「二进制路径错误」把二进制指向 `/tmp/rfc022-bin/opencode`，这个链接只在档位测试里由步骤建出来；
  - 「镜像不存在」先用一份独有摘要的镜像副本通过测试，再从仓库删掉清单、从节点删掉镜像记录。
  
  档位镜像只能放在 `runtime/` 前缀下，所以副本推在 `runtime/rfc022-missing:v1`。
- **SP-08 的令牌打码没法实机看到。** git 的这类报错不打印克隆地址，日志尾部里本来就没有凭据。打码逻辑（`maskDiagnosticsText`）由用例覆盖。
- **启动前步骤的脚本输出不进日志。** 按 RFC-006，脚本输出不向租户广播；失败时展开的是执行容器的 Runner 日志，1d45592 之后只留 info／warn／error 行（例如 `before-start step failed … script_failed`）。
