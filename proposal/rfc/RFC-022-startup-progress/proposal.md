## 1. 来源与确认

作者 2026-09-23 的两句话：

1. 「按你说的改。」指上一轮报告里我提的做法：「谁点了『＋ 创建开发Agent会话』，就自动替谁取得输入控制」。起因是新开的 CLI 在有人取得输入控制之前一直空白：OpenCode 启动时要等终端回答它的查询，而只有持有控制的窗口会回答。
2. 「现在在启动新agent会话的时候，状态显示的无法理解，只有未连接、已连接这种。还应该标识容器状态，比如容器未启动、容器启动中、容器已启动，agnet启动中，这种类似的细粒度状态」

我先实测了一个 CLI 从点击到可用的全过程（§2.1），再经两轮问答定下 §4 的八项裁定。

## 2. 今天的情况

源码基线 `95c38de`。

### 2.1 实测：一个 CLI 从点击到可用

2026-09-23，本机集群，dev-developer 在「演示数字人」新开一个 CLI（档位 volc-glm-5-2 修订 4）。脚本高频读取 CLI 名册，同时读页面上显示的文字。

| 时刻 | 平台实际状态 | 页面显示 |
|---|---|---|
| 0.7 s | 已受理，执行环境排队（「已受理，正在准备此CLI的独立执行环境」） | 「已登记，等待分配独立运行环境｜终端未连接」 |
| 1.3 s | 执行容器已创建，等待调度 | 同上 |
| 4.6 s | 执行容器已运行，等待 TaskRunner 连接 | 同上 |
| 5.2 s | TaskRunner 连上，开始执行启动前步骤 | 同上 |
| 5.7 s | 启动前步骤完成，开始准备 CLI（探测版本、写配置） | 「终端已连接」 |
| 10.5 s | CLI 进程拉起 | 「终端已连接」 |
| 11.0 s | — | 「空闲 · 点击终端即可输入」，终端空白，直到有人点进去 |

平台其实经过了五六个能分辨的阶段。页面前 5 秒一直是同一句话，又在 CLI 进程拉起前约 5 秒就显示「终端已连接」；5.7 s 到 10.5 s 这段，页面没有任何表示。CLI 拉起之后，在有人取得输入控制之前，终端仍然空白。

## 3. 目标与非目标

目标：

1. **一套公共的启动进度**：后端按阶段产出，每段有状态、起止时间、细节，失败时有原因；存在库里，刷新不丢；工作台、`crewstation` 命令行和今后读这份数据的工具看到的是同一份。
2. **三处先用上**：新开的 CLI（六段）、开发会话容器（五段，重建时换一段）、档位测试（迁到同一套）。
3. **一个公共的步骤条组件**，放在终端区域中间；状态条显示当前阶段；失败停在出错的那一段，标红，写出原因，给出「重试」「查看执行容器日志」；就绪后换回终端。
4. **点击创建的那个窗口自动取得新 CLI 的输入控制**，CLI 一拉起就显示界面。
5. **容器阶段的细节由平台读 Kubernetes 得到**：等待调度及原因、分配到的节点、拉取哪个镜像和耗时、检出代码。

非目标：

- **不改变任何成败判定。** 什么时候判失败、等多久（执行容器拉不到镜像立即失败、5 分钟连不上失败）都不变。本 RFC 只把判定的过程和结果按阶段显示出来。开发会话拉不到镜像时平台今天不判失败，之后也不判，只在那一段显示警告。
- **业务任务容器和业务 Agent 子任务的界面。** 后端同样为它们产出容器阶段（task-runtime 对所有环境一视同仁），但本 RFC 不做界面，也不改业务任务接口。
- **操作 MCP 不新增工具**（见 Q4）。
- **不做启动历史。** 每个 CLI、每个开发会话只保留最近一次启动的过程。
- 不改 TaskRunner 协议版本（仍为 3），不用 Kubernetes watch。
- 开发预览不算开发会话的阶段（D7），继续在预览面板单独显示。

## 5. 阶段定义

### 5.1 八种公共阶段

名称用裁定里的原话。「开始」指这一段从什么时候算起，「成功」指它什么时候结束。

| 阶段 | 名称 | 开始 | 成功 | 进行中的细节 | 失败（只在平台判定失败时） |
|---|---|---|---|---|---|
| `queue` | 排队分配容器 | 受理 | 平台建出 Pod | 已受理，等待平台创建容器 | 受理后被拒（父工作区断开、建 Pod 失败），原因原样 |
| `replace` | 替换旧容器 | 重建作业开始替换 | 原容器已退出、新 Pod 已建 | 正在停止原容器，工作卷保留 | 重建失败，原因原样 |
| `container` | 容器启动中（调度、拉取镜像） | Pod 建出 | 第一个容器开始运行（有 init 容器时是 init 容器） | 等待调度 → 已调度到节点 X → 拉取镜像 Y（计时）→ 镜像已就绪（拉取用时，或节点上已有）→ 创建容器 | 镜像拉取失败、容器无法创建 |
| `checkout` | 检出代码（分支 xxx） | init 容器开始运行 | init 容器以 0 退出 | 正在克隆分支 xxx | init 容器非 0 退出（Pod 不重启，即判失败），附 git 报错 |
| `connect` | 容器已启动，等待连接 | 主容器开始运行 | TaskRunner 连上平台 | 等待 TaskRunner 连接 | 握手被拒（协议不一致）、容器退出、超过 5 分钟未连上 |
| `prepare` | 准备环境（启动前步骤 x/y） | TaskRunner 连上 | 启动前步骤全部成功 | 当前第几步、步骤名；没有步骤时这一段为「跳过」 | 某一步失败，写出步骤名与原因 |
| `agent` | Agent 启动中 | 启动前步骤结束 | CLI 进程拉起 | 准备 CLI 配置并拉起进程 | 进程拉不起来，原因原样 |
| `ready` | 已就绪 | 前一段结束 | 同一时刻 | — | — |

每段的状态：未开始、进行中、成功、失败、跳过。整体状态：启动中、已就绪、失败、已取消（启动中被关闭或释放）。

### 5.2 三处的阶段

| 对象 | 阶段 |
|---|---|
| 新开的 CLI（D2） | 排队分配容器 → 容器启动中（调度、拉取镜像）→ 容器已启动，等待连接 → 准备环境（启动前步骤 x/y）→ Agent 启动中 → 已就绪 |
| 开发会话：开始开发（D7） | 排队分配容器 → 容器启动中（调度、拉取镜像）→ 检出代码（分支 xxx）→ 容器已启动，等待连接 → 已就绪 |
| 开发会话：重建（D7） | 排队分配容器 → 替换旧容器 → 容器启动中（调度、拉取镜像）→ 容器已启动，等待连接 → 已就绪 |
| 档位测试（D8） | 排队分配容器 → 容器启动中（调度、拉取镜像）→ 容器已启动，等待连接 → 每个启动前步骤一段 → Agent 启动中 → 真实模型轮次（已知协议）或测试命令（通用终端） |

### 5.3 共同规则

- **首尾相接**：每一段从上一段结束的那一刻开始，中间没有无人负责的空档。
- **只进不退**：一段成功后不会回到进行中。
- **时间以源头为准**：结束时间优先取 Kubernetes 自己记的时间（Pod 条件、容器的开始与结束时间）、TaskRunner 记的步骤时间和平台收到事件的时间。平台多久读一次，只影响页面多快看到，不影响时间准不准。
- **拉取镜像的开始和用时取自 Kubernetes Events。** Events 可能被合并或过期，缺了就不显示用时，不影响阶段本身。

## 6. 界面与旅程

### 6.1 新开的 CLI

```text
┌ CLI 83638e  启动中 4/6   volc-glm-5-2  ↗ ··· ─────────────┐
│ ● 4/6 准备环境（启动前步骤 1/2）· 写入 settings.json · 1s  │ ← 状态条
│                                                           │
│      正在启动 CLI · volc-glm-5-2 · 已用 5.9 s              │
│      ✓ 排队分配容器                               0.6 s   │
│      ✓ 容器启动中（调度、拉取镜像）                3.3 s   │
│          已调度到节点 docker-desktop · 镜像节点上已有       │
│      ✓ 容器已启动，等待连接                       0.6 s   │
│      ● 准备环境（启动前步骤 1/2）                  1 s…    │
│          写入 settings.json                                │
│      ○ Agent 启动中                                        │
│      ○ 已就绪                                              │
└───────────────────────────────────────────────────────────┘

失败时停在那一段：
│      ✕ 容器启动中（调度、拉取镜像）              12.0 s   │
│          镜像拉取失败（ImagePullBackOff）：…not found       │
│      [重试]  [查看执行容器日志]                             │
```

1. 点「＋ 创建开发Agent会话」，新标签出现并被选中，终端区域中间是步骤条，状态条同步显示当前阶段。
2. TaskRunner 连上之后，点击创建的那个窗口就已取得输入控制（D1）。CLI 进程拉起的那一刻步骤条消失，终端里直接出现 CLI 界面，焦点在终端里，可以直接输入。
3. 其他窗口（同一个人的其他窗口、其他成员）看到同样的步骤条和计时；就绪后看到 CLI 界面，状态条显示「某某 正在输入 · 只读」，点进终端按既有规则取得。
4. 失败时停在出错的那一段，红色 ✕，下面写原因；「重试」见 Q2，「查看执行容器日志」在步骤条里展开平台回收容器前留下的日志（B8）。

### 6.2 开发会话：开始开发与重建

1. 开始开发或重建期间，CLI 区域中间是步骤条，页头的连接芯片显示当前阶段（例如「启动中 3/5 · 检出代码」）。就绪前「新开 CLI」不可用，这一点与今天相同。
2. 就绪后步骤条消失，恢复今天的空 CLI 区域。
3. 失败时停在出错的那一段，写出原因；按钮「重试」（见 Q1）、「查看容器日志」。

### 6.3 档位测试

管理员保存档位后的自动测试和手动测试，改用同一个步骤条组件。档位测试特有的内容（逐步定位到编辑器、退出码、输出尾部）保留在对应的那一段下面。

### 6.4 `crewstation` 命令行

`crewstation session open` 与 `session show` 在原有字段之后打印启动过程，每段一行：状态、名称、用时或细节。

### 6.5 多窗口、多人与刷新

- 刷新页面、换一台机器、换一个人看，各段和时间都一样（后端存的）。
- 进行中那一段的计时按服务器时间校正，不受本机时钟快慢影响。
- 启动期间页面每秒读一次进度；就绪或失败后回到原来的刷新间隔。

## 7. 本 RFC 自己的取舍

这些不是新的产品规则，是裁定的落地方式；作者批准三件套时一并确认。

| 编号 | 内容 | 依据 |
|---|---|---|
| B1 | 只有平台判定失败时才标红。Kubernetes 仍在重试的问题（调度资源不足、镜像拉取退避）显示为那一段的黄色警告 | 非目标「不改变任何成败判定」 |
| B2 | 「已就绪」对 CLI 是 CLI 进程拉起，对开发会话是 TaskRunner 连上。CLI 自己画界面的那一两秒不算阶段，直接在终端里看到 | D2、D7；平台看不到 TUI 有没有画完 |
| B3 | 没有启动前步骤时，「准备环境」这一行仍在，显示「跳过」，六段的形状不变 | D2「自动跳过」 |
| B4 | 重建时「替换旧容器」排在「排队分配容器」之后、「容器启动中」之前 | D7；重建作业先停原容器再建新 Pod（`modules/task-runtime/application/rebuildExecution.ts:28,41`） |
| B5 | 各段首尾相接、只进不退，时间以源头为准（§5.3） | D6「带起止时间」 |
| B6 | 自动取得只在点击创建的那个窗口、只做一次；刷新页面后不再自动取得；取得后按 2026-09-23 已定的规则：焦点在终端才保持，离开 30 秒释放。就绪时把焦点移进终端，除非用户这时正在别处输入 | D1 |
| B7 | TaskRunner 允许在 CLI 进程拉起之前取得输入控制（输入和改尺寸仍要等进程拉起），这样 CLI 第一次查询终端时，创建者的窗口已经能回答。执行镜像还是旧底座时 Runner 会拒绝，页面在进程拉起后再取得，这时 CLI 可能仍要空白几秒 | D1；§2.1 实测 |
| B8 | 判定失败后、回收容器之前，平台读取相关容器日志的最后 100 行（按凭据形状打码），存进失败的那一段；「查看执行容器日志」在步骤条里展开这份日志，容器还在时另给日志页入口 | D3；执行容器失败后立即回收，不先留下就看不到 |
| B9 | 启动期间页面每秒读一次进度，只对还在启动的对象；计时按服务器时间校正 | D3「计时」 |
| B10 | 每个 CLI、每个开发会话只保留最近一次启动的过程，重建会替换开发会话的启动过程 | 非目标「不做启动历史」 |
| B11 | 档位测试的「拉取镜像」「Runner 握手」由公共的前三段取代，「启动 CLI」改为「Agent 启动中」；逐个启动前步骤、模型轮次、测试命令保留为档位测试自己的段；旧的测试记录照原名称显示 | D8「同一套阶段契约」 |

## 8. 待作者裁定

| 编号 | 问题 | 推荐 | 备选 |
|---|---|---|---|
| Q1 | 开发会话启动失败时，「重试」做什么 | **按失败的位置分**：失败在「检出代码」或更早（工作卷里还没有可用的仓库），释放后按原分支重新开始开发；失败在「等待连接」（仓库已检出），走现有的「恢复」（保留工作卷重建）；重建本身失败，再次恢复 | 一律打开现有的恢复面板，不加新按钮 |
| Q2 | CLI 启动失败时，「重试」做什么 | **原位替换**：用同样的档位选择、权限和工作目录新开一个 CLI，替换这个失败的标签（位置不变）；档位按当前修订解析，管理员修好档位后重试即生效 | 保留失败的标签，另开一个新标签 |
| Q3 | 就绪之后还能看启动过程吗 | **能**：CLI 标签的信息菜单和开发会话的「会话与环境」面板里放「启动过程」，显示各段用时。数据已经存了，不增加后端工作 | 就绪后不再显示 |
| Q4 | 运维 MCP | 裁定 D6 的选项写了「运维 MCP 看到同一份」。运维 MCP 今天没有读开发会话或 CLI 状态的工具（`packages/mcp-server/operations/` 只有日志、内部 API、发布、分支、预览）。**推荐本 RFC 不新增工具**：Agent 就在已就绪的容器里跑，读自己的启动过程没有用；以后要加，读的就是这份数据 | 加一个只读工具，返回开发会话与 CLI 的启动进度 |

## 9. 能力影响清单

本 RFC 不关闭或收缩既有能力，开发规则 §5.5 不适用。有两处显示上的变化：

- CLI 名册里执行环境的那一句说明（`execution.message`）仍保留在接口里；工作台在启动期间改显示步骤条。
- 档位测试记录的阶段增加公共种类（B11）；旧记录里的 `image`、`runner`、`launch` 仍能读出，照原名称显示。

## 10. 验收标准

| 编号 | 内容 |
|---|---|
| SP-01 | 新开 CLI：六段依次推进，每段有用时，进行中那段有细节和计时；刷新页面、另一名成员看到的阶段和时间一致 |
| SP-02 | 「容器启动中」的细节：等待调度及原因（用验收专用的超大套餐制造调度不上）、分配到的节点、拉取的镜像和用时（先删掉节点上的镜像缓存）、「节点上已有」 |

| SP-04 | 创建者的窗口在 CLI 进程拉起后不用点击就显示 CLI 界面，可以直接输入；同一个人的另一个窗口和另一名成员不会自动取得，看到「某某 正在输入 · 只读」 |
| SP-05 | 失败停在出错的那一段，标红并写出原因：镜像不存在的档位停在「容器启动中」，启动前脚本失败停在「准备环境」，二进制路径错误停在「Agent 启动中」；「查看执行容器日志」能看到回收前留下的日志；「重试」按 Q2 |
