## 1. 问题与现状

当前准备弹窗依次选来源、检查、填写版本；请求受理后清掉 `source`，弹窗关闭，详情画在版本卡之后。构建／迁移日志在运行与诊断，正式上线另开切流确认弹窗。作者必须主动找下一入口并理解各按钮关系。见 `apps/console/src/features/release/pages/ReleasePage.tsx:58`、`apps/console/src/features/release/components/SelectedRelease.tsx:24`、`apps/console/src/features/release/components/TrafficSwitchDialog.tsx:36`。

发布页已有发布、切流、重新部署、下线、推迟和维护的合并时间线；但发布 DTO 只有当前状态及创建／更新时间，不能显示每次操作完整的历史向导。内部 `pipeline` 也会随着重新部署变化。见 `apps/console/src/features/release/components/ReleaseTimeline.tsx:35`、`packages/contracts/api/release.ts:10`、`modules/release/domain/release.ts:28`。完整核对见 [source-evidence.md](./source-evidence.md)。

## 2. 已确认的产品方向

1. 一次发布一直在一个独立页面内推进，直到正式上线或明确停在失败／待处理步骤。
2. 自动工作结束后自动进入下一个需要人处理的步骤。正常流程只有发起构建、验证完成、确认上线三个关键动作。
3. 正式上线由负责人或管理员在同页明确确认；开发者完成发布后能交给有权限的人接续同一流程。
4. 发布页签保留历史发布记录。每条历史记录能进入同样的向导视图查看该次流程及当时的进展。
5. 刷新、稍后返回、查看日志、打开待验证应用，都能保留发布对象、进度与当前操作位置。

前四项为作者明确要求；具体布局、阶段留存和异常处理为本 RFC 待批准方案。

## 3. 发布页签

发布页签作为发布总览，包含紧凑的正式／待验证版本、进行中的发布以及历史记录。主操作为「发布新版本」。有进行中的流程时突出「继续发布」，写清版本与当前阶段；不要求作者关闭某个弹窗再找对应版本卡。

历史以每次发布操作为单位，而非把同一版本的重新部署覆盖进第一条记录。每行显示：版本、操作类型、当次结果、最后到达的步骤、发起人、开始／结束时间与说明。失败行直接显示失败阶段与一句原因；点击「查看流程」进入该次历史向导，进行中的记录显示「继续发布」。较早记录用游标分页访问。

发布、上线／回退、下线、推迟与维护的现有事件仍可查看；不把所有运维事件伪装成一次新构建。返回时恢复历史的页码／游标、滚动和触发按钮焦点。新、历史和管理空间共用一套发布视图与文案。

## 4. 连续发布向导

页面持续显示项目、候选版本、固定提交与「返回发布记录」。顶部五步始终可见；中部显示当前步骤；底部只强调本步骤的一个主动作。已完成步骤可点击回看，执行中的发布不会因此重新执行或跳过尚未完成的步骤。

| 步骤 | 用户看到什么 | 主动作与连续性 |
|---|---|---|
| 1. 准备发布 | 来源、分支／开发工作区、当前提交、版本号和说明放在同一屏；自动读取现有来源，错误就地说明 | 「构建并继续」：明确发起发布；提交的是已展示的完整 SHA 与具体版本号 |
| 2. 构建与部署 | 排队、构建／复用镜像、迁移／无需迁移、部署、就绪各段；当前阶段与日志在同页 | 后台推进；实际待验证版本就绪后自动进入步骤 3。可「稍后继续」，不会取消后台工作 |
| 3. 验证版本 | 待验证地址、当前就绪状态、生产数据共用提示、本次版本与提交；验证说明可选 | 新标签打开应用，向导留在原页；「验证通过，继续上线」记录一次人工确认 |
| 4. 确认上线 | 当前正式版本 → 本次目标版本、两次提交、操作说明、过期或维护阻断原因 | 「确认上线 vX」是唯一正式上线确认；原位显示路由生效与需要时的执行权交接 |
| 5. 完成 | 实际上线的版本、正式地址、操作者与时间；旧版本的当前保留情况 | 「打开正式应用」「返回发布记录」；回退／重新部署按实时允许条件发起新流程 |

「验证通过」表示操作人确认业务验证完成，不是平台自动测试通过。打开地址、计时经过、资源就绪都不会替用户确认业务验证或正式上线。

构建及兼容迁移可能影响共享生产数据；步骤 1 发起前和步骤 3 验证入口附近明确说明。版本号默认展示算出的下一补丁版本，允许换递增类型或填写合法具体版本；发出前固定成明确标签，避免受理回执丢失时只剩不确定的 `patch` 意图。

准备阶段改来源／SHA保留版本与说明，并重新核对来源。受理后来源与版本为只读；修改代码或换版本会发起一条新发布，原来的流程完整留存。

## 5. 历史向导与继续操作

历史页和当前向导使用同一五步结构。历史回看能选择各步骤，查看来源、版本、阶段开始／结束时间、失败原因、验证人及上线人；结束的流程不显示可执行的原确认按钮。

历史结果与当前版本状态分开：当次「已上线」不会因为后来被替换变成「发布失败」；当前是否在线、是否下线另显示。首次发布、重新部署、单独上线及回退分别有独立的流程身份，重复操作不覆写原步骤或耗时。

仍在构建／部署／交接的记录可继续观察。同一待验证部署仍存在且当前权限允许时，可从「待验证」接着确认；被另一个发布替换或下线时原流程说明原因，提供重新部署的新流程入口。失败后只有实际支持的恢复动作：构建失败后「修改后发布新版本」，部署历史制品则按原重新部署条件操作，不虚构失败构建的原地重试接口。

升级前记录按可证的原发布、内部时间和切流记录回看；不能恢复的时间、来源类型、人工验证或中间阶段标为「未记录」。只读查看不会补写旧数据，也不会运行构建、迁移或切流。原日志被回收时显示「日志已不可用」，阶段事实与错误摘要仍保留。

## 6. 能力影响

| 既有能力 | 本次处理 |
|---|---|
| 已推送分支发布／开发会话发布 | 均进入准备步骤；开发会话未提交内容仍阻断，平台不代提交 |
| 开发者发布、负责人／管理员切流 | 权限边界保留；允许有权限者跨浏览器接续已受理流程 |
| 手动验证、单独上线、回退、重新部署 | 向导内呈现；独立操作仍支持，不强迫重新构建 |
| 维护窗口、破坏性迁移与禁止回退策略 | 保留全部后端检查；同页显示原因与恢复入口 |
| 自动下线与推迟、日志、运维时间线 | 保留入口、原保留期和真实结果 |
| CLI／MCP／直接 API 发布 | 保持既有请求可用；新历史留存也记录这些入口产生的实际流程 |
| 原 `source`／`release`／`switch` 深链接 | 兼容定位新向导；未知 ID 仍报错，不换成最新版本 |
| 项目永久删除 | 新流程数据归 release owner，进入原完整盘点、封写、回收与独立证明 |

本 RFC 不提出既有能力的关闭／权限收紧。主流程中拆散的准备、详情与切流弹窗由独立路由承载；放弃未保存草稿或维护管理等确需模态的操作继续复用共享 Dialog，不在列表后 append 管理内容。

## 7. 验收标准

| 编号 | 必须可观察的结果 |
|---|---|
| RW-01 | 从项目、开发页或管理空间进入同一向导；空间、来源和返回位置正确 |
| RW-02 | 一屏填写来源、版本、说明；正常流程不再经历三次准备确认 |
| RW-03 | 发起发布后页面持续打开，受理不标为就绪；自动工作结束后原位进入验证 |
| RW-04 | 自动前进只依据实际状态；不能跳过未完成的构建、迁移、部署或交接 |
| RW-05 | 验证应用与日志在新标签／同页展开，向导进度及输入保持 |
| RW-06 | 完成业务验证与正式上线各有明确用户动作，均不会自动发送 |
| RW-07 | 开发者不能上线；负责人接续同一目标，校验最新部署后操作 |
| RW-08 | 来源／目标／正式版本变化使旧确认失效，提示与恢复操作留在当前步骤 |
| RW-09 | 发出前离线零写；回执未知不自动重发；刷新恢复同一发布与交接意图 |
| RW-10 | 构建／迁移／部署失败停在对应阶段；原因、已有记录和合法恢复入口保留 |
| RW-11 | 交接受理和正式生效分开显示；路由未实际生效或执行权未完成不标上线成功 |
| RW-12 | 历史可查看每次操作的完整阶段、时间、人员、验证与上线结果；旧缺失字段明确未记录 |
| RW-13 | 同一 release 重新部署两次产生两条独立流程；后来状态不改写首次成功历史 |
| RW-14 | 历史 GET 和阶段回看零资源写入；终态流程只能只读回看或发起新的合法操作 |
| RW-15 | 发布页长列表末行打开即进入独立路由，返回保留分页／滚动／焦点 |
| RW-16 | 历史跨页可访问；部分来源失败不显示为空；未知流程不退回到最新一条 |
| RW-17 | 下线、推迟、维护、回退、旧客户端发布与原深链接能力保持 |
| RW-18 | 1440／1024／390／320px，中英文、明暗主题、键盘无遮挡／横向溢出；底部动作可达 |
| RW-19 | 新流程表在项目删除范围内；读尽完整范围、封写后拒写、外项目内容保持 |
