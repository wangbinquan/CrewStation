# RFC-044：服务数据库 epoch 迁移

> 状态：Done · 2026-10-29（2026-10-28 作者批准「按推荐实现」）。验收见 acceptance.md。
> 来源：agent-workflow（AW）RFC-395 T19。AW 用户 2026-10-24 决定：托管实例迁移的平台侧（冻结、开空目标库、源库只读访问、展示计划供批准、验证 Job、切换与回退）在 CrewStation 落地，真实托管迁移前两侧联调。

## 问题

AW RFC-395 重建了数据库目标 schema（epoch 2）。已有的 epoch 1 安装不能靠普通发布的只增迁移升级：要冻结旧库，把数据转换写入一个独立的空目标库，验证后再切换。AW 已经实现了迁移、验证和旧 epoch 恢复三个 Job 入口，也写明了它们对平台的输入与回调合同（AW `docs/crewstation-deployment.md`「epoch-2 发布的数据库切换」，入口 `packages/backend/src/bootstrap/epochMigrationHostedEntry.ts`）。

CrewStation 目前做不了这件事：

- 普通发布的 migration Job 只在当前生产库上前滚。epoch 2 的 AW 在 epoch 1 库上会拒绝启动，发布停在迁移阶段。
- RFC-042 只支持「从业务备份恢复到空目标库再切换」，不运行迁移计划、不收审批、不提供 Job 回调接口，也不支持首写前回退。
- 平台没有 AW 需要的操作回调接口（`/v1/operations/<operationId>` 下的 artifacts、freeze/verify、prepared、activation、rollback、backup），Job 也拿不到平台 API 令牌。

因此本机正式 AW（项目 `agent-workflow`，v0.6.30，epoch 1）无法升级到当前版本。

## 目标

平台管理员可以对一个服务发起「数据库 epoch 迁移」，由平台编排、业务程序执行转换：

1. 选定已构建、声明了迁移命令的新版本。平台为本次迁移准备独立的空目标库（需要时再加一个 scratch 库），原生产库与正在运行的旧版本不受影响。
2. 平台用新版本运行只读的 plan Job，展示迁移计划：阻断项、限制、需要操作者确认的事项和预计影响。管理员审阅后批准，批准绑定计划的批准摘要（approvalDigest）。
3. 管理员确认切换后，平台进入维护、冻结执行权并证明旧写入者全部停止，再运行 run Job 把数据转换进目标库。
4. Job 交回激活回执后，平台把生产数据库世代切到目标库，部署绑定目标库的新版本候选槽，再运行独立的 verify Job。
5. 首次业务写入之前可以撤回：回到原数据库世代和原版本，解除冻结。确认后开放准入并切流，记录完成回执。之后只能前滚，或从目标库的备份恢复。
6. 任一步失败都保留操作、目标库与证据，可以在同一操作中重试；切换提交之前可以放弃。旧库始终保留，不自动删除。

合同按「业务程序声明迁移命令、平台提供冻结与世代切换」写，不绑定 AW 的内部实现；第一个使用者是 AW。

## 非目标

- 平台自行决定迁移时机，或在普通发布中自动触发迁移。
- 跨服务、跨安装的数据迁移；把新旧库的数据合并。
- 删除旧库或目标库（均保留，在资源中心按现有方式管理）。
- 让业务 Agent 或项目成员发起迁移。第一版只有平台管理员能操作，项目成员按原有 view 权限查看。
- 非 PostgreSQL 的服务数据库。

## 用户旅程

1. 管理员在服务的发布页进入「数据库迁移」。页面列出可用的新版本：已构建，且 Manifest 声明了 `spec.service.databaseMigration`。也会展示当前生产版本、当前数据库世代和这次迁移的影响。
2. 发起迁移后，平台创建空目标库和 scratch 库，运行 plan Job。旧版本照常服务。
3. 页面展示计划：源与目标的识别信息、阻断项、限制、需要确认的事项、预计耗时与容量。有阻断项时不能批准；管理员处理后可以在同一操作中重新生成计划。
4. 管理员批准计划。批准摘要与计划一起保存。
5. 管理员确认进入维护并切换。平台冻结执行权，验证旧写入者全部停止，运行 run Job；页面显示进度。
6. run Job 完成后，平台核对激活回执，切换数据库世代，部署候选槽，运行 verify Job。验证通过前保持维护。
7. 页面给出两个选择：「撤回到原版本」或「开放并完成」。撤回在首次业务写入前有效。开放后平台交接执行权、切流，运行 complete Job，记录完成回执。
8. 关闭页面后可以从发布页重新进入，操作状态与证据都保留。

## 权限与能力影响

- 只有平台管理员能发起、批准、切换、撤回、放弃。项目成员按原 view 权限只读查看。不新增角色。
- 迁移进行中，同一服务的发布、下线、重新部署、切流和数据库恢复都会被拒绝，返回具名错误码（与 RFC-042 恢复进行中的规则相同）。
- 迁移期间服务需要维护窗口：从冻结到开放准入之间，用户请求得到维护响应。
- 迁移 Job 获得的回调令牌只对本次操作和当前 Job 有效，只能访问本操作的回调接口和原服务对象空间（只读）。
- 不提供任意连接串、命令或环境变量覆盖；命令只能来自已构建镜像的 Manifest。

本 RFC 不关闭或收缩任何既有能力。

## 验收

- DBM-01：目标库和 scratch 库独立创建、有空库出生证明；旧库及其凭据不变；同一请求重复提交不会多建。
- DBM-02：plan Job 只读运行；计划、阻断项、approvalDigest 持久化并在页面展示；有阻断项或未批准时不能进入切换；重新生成计划时，旧批准作废。
- DBM-03：run 之前，维护、执行权冻结与停写证明全部完成；run 使用同一操作、同一目标与批准摘要；中断后沿原操作续跑，不重复已完成的外部动作。
- DBM-04：平台核对激活回执后才切换世代、部署候选槽；verify Job 独立确认目标库；验证通过前不开放准入。
- DBM-05：首次业务写入之前可以撤回：数据库世代、版本、路由与执行权回到原状，冻结解除；首写之后拒绝撤回。
- DBM-06：开放后，执行权交接、切流与完成回执齐全，complete 关闭撤回窗口；旧库保留并标记。
- DBM-07：各阶段断线、Job 丢失、平台重启后都能冷恢复；状态未知时先观察，不重做不同的目标；失败尝试保留证据并可重试；切换提交前可以放弃。
- DBM-08：回调接口（artifacts、freeze/verify、prepared、activation、rollback、backup）按 AW 合同对接，AW 的迁移、验证与旧 epoch 恢复 Job 在真实 PostgreSQL 上跑通。
- DBM-09：真实验收。先用独立验收服务端到端跑通迁移、撤回和完成；再经逐实例批准，迁移本机正式 AW（项目 `agent-workflow`）。
