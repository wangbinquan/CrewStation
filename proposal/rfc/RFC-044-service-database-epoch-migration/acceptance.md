### 联调中发现并修复的缺陷

| 编号 | 现象 | 原因 | 修复 |
| ---- | ---- | ---- | ---- |
| F1 | 候选构建推送失败：`invalid reference format` | 候选版本号 `v0.1.2+migrate.<操作>` 被原样用作镜像标签，镜像标签不允许 `+` | `f622b5aa`：构建统一经 `releaseImageReference`，标签里的非法字符换成 `_`；普通 `vX.Y.Z` 不变。CI `40703073335` |
| F2 | plan Job 退出：「迁移回调请求超过 32 MiB」 | AW 把约 37 MiB 的 epoch-1 PostgreSQL 参考目录作为一个产物整块写入 | AW `a3b4920ed`：参考目录改经 4 MiB 分块的产物端口保存，名称下只留摘要指针 |
| F3 | plan Job 退出：「权限正在更新，请稍后重试」 | 回调与每 3 秒的进度循环争用同一操作锁；锁等待超过 1.5 秒时返回 409，AW 把 409 视为终局 | `e349c64a`：锁忙带 `coordination_busy`，归入暂时码；回调对暂时码返回 503 与 `Retry-After`。CI `40710702006` |
| F4 | plan Job 退出：「回调请求格式不合法」 | 产物 `bytes` 的分组正则在 Bun 1.3.13（平台镜像与 CI 所用版本）上对约 4 MB 以上的合法 base64 返回 false，AW 的每个 4 MiB 分块都被拒绝 | `dd02302e`：改为单一字符类加规范往返校验；契约面不变。CI `40712944904` |
| F5 | 操作被挂起：「原生存储挂载或探针在观测期间变化」，运行中的 plan Job 因此失去回调资格 | 进度循环每次观测目标库的原生来源；平台刚滚动完，探针与服务器 Pod 仍在更新，这类观测期间的变化被报成需管理员处理的错误 | `6fa0b6bb`：观测期间的变化改用 `native_postgres_source_busy`，由进度循环记为观察、下次再看；真实替换仍由下一次观测的身份核对拒绝。CI `40716337208` |
| F6 | run Job 内存一直顶在 512Mi、CPU 节流在 250m，长时间没有进展 | 设计让迁移 Job 沿用服务套餐（250m/512Mi），平台现有套餐内存都不超过 512Mi，而 AW 的转换需要 GB 量级 | 作者批准「迁移 Job 单独指定套餐」：`c86ddb97` 增加 Manifest `databaseMigration.servicePlanId`，迁移 Job 用它，候选槽仍用服务套餐；构建时核对套餐。AW `ceec41fe3` 的发布档案增加 `migrationServicePlanId`。平台目录新建套餐 `aw-epoch-migration`（500m/3Gi）。之后 run Job 内存峰值约 1 GiB |
| F7 | op3 在 `ready-to-open` 请求撤回，rollback Job 退出 1：`reverse-migration-required` | AW 候选在 `activating` 阶段启动时（00:40:41），把 hosted 启动收敛和执行控制行的写入算作首次写入，在目标库打了首写标记；verify 又把它记进迁移 journal 和切换回执。实际上服务仍在维护，没有用户写入到达目标库 | AW `8024fe5ad`：PG 客户端区分写入是否算首次写入，hosted 启动收敛不算；AW `1187547bb`：执行控制行的写入不算。两者都带回归用例。op3 的 journal 已经记下，无法再撤回；激活后撤回改在 T9b 用修复后的 AW 验收 |
| F8 | rollback Job 失败后，操作停在 `rolling-back`，唯一的动作 `retry` 只会重复同样的拒绝，服务一直维护 | 撤回回执成功之前，平台不改任何东西（绑定、候选、停写屏障、维护都不动），但没有回到 `ready-to-open` 的路 | 作者批准新增管理员动作：`e936dcb9` 增加 `cancel-rollback`。只在撤回 Job 失败、没有撤回回执和撤回请求、已有 verify 回执时可用；在操作锁内复核生产绑定仍指向目标世代、候选仍在目标槽，然后回到 `ready-to-open`，失败的尝试留在历史里。契约、路由、api-client、控制台一并接入。CI `40809300876` |

环境故障（不是平台缺陷）：

- 本机并行构建任务镜像时，buildkitd 超出 4 GiB 内存上限被 OOMKilled，候选构建失败；重试后成功。
- run Job 运行时，共享 PostgreSQL（`postgres-0`，上限 2Gi）第 5 次被 OOMKilled，平台 API 与各项目连接一起中断，run Job 随之失败。作者批准后原地扩到 4Gi。op3 的 run 期间，PG 容器内存（含页缓存）在 3.5–3.9 GiB，采样窗口内最高约 4.0 GiB，没有再被 OOMKilled。StatefulSet 模板仍是 1Gi，Pod 重建会回落。

## DBM 逐项

| 编号 | 结论 | 依据 |
| ---- | ---- | ---- |
| DBM-01 | 通过 | 每次操作都新建目标与 scratch 两个世代（如 T9b 的 `01a186f0-6dff-7000`、`-7001`），源世代与凭据不变；撤回与完成后源世代都是 `retained` 或仍为生产。T9 op2：同一请求重放返回同一操作，同一请求 ID 换输入返回 409。空库出生证明由 T8 用例覆盖 |

| DBM-03 | 通过 | 每次切换都先进入维护、冻结执行权，并等到停写证明才进入 `migrating`。T10 op2 在写入者停下之前一直不前进。T9 op3：冻结数据与批准时不同，第一次 run 只输出新计划，转入 `awaiting-reapproval`，重新批准后继续。T9 op2 的 run Job 因共享 PostgreSQL OOM 失败后，在原操作上重试 |
