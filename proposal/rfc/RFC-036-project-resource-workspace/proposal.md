# RFC-036｜项目资源中心：授权、拓扑、配额与申请

> 状态：Done · 2026-10-01 · 已按审核原型实施、发布并本机部署；主体与最后修正的精确 SHA 六项 CI 全部通过，实际页面、持久变更、拓扑归属和焦点复验见 [发布与部署后验收](./deployment.md)。
> 配套：[技术设计](./design.md) · [实施计划](./plan.md) · [原型说明](./prototype/README.md)

## 1. 目标与已确认要求

项目管理与平台管理的项目详情各有一个「资源中心」页面，共用一张项目资源拓扑。页面成为负责人、开发者与管理员了解和管理该项目资源的核心入口，复用当前 SVG 拓扑能力。

作者在本轮明确：

- 展示全部项目资源及逻辑归属，区分已有、可申请、申请中，展示每个元素的配额等信息。
- 资源申请、配额修改申请直接用页面中的统一弹窗完成。
- **只有项目负责人能够提交资源与配额申请；开发者不能提交。管理员审批。**
- **只向项目展示平台明确标记为可申请的未授权资源**，内部隐藏目录不因此曝光。
- **管理员也在本页面直接分配资源、调整配额和审批**，不能只给到其他管理页面的跳转。
- 先完成原型并经作者审核，再实施产品。

## 2. 页面与核心旅程

两个入口使用相同布局、资源身份、状态与关系；项目视角按项目权限裁剪，管理员多出直接管理和审批操作。第一层导航为「资源拓扑／资源清单／申请记录」。原有运行实例拓扑保留，资源中心可以下钻至具体实例。

负责人：识别容量压力 → 点配额或资源 → 查看当前生效值与占用 → 弹窗填写目标与理由 → 提交 → 图中出现申请关系与目标值 → 在原页跟踪审批及生效。

开发者：查看同一份有效资源、使用约束、配额和申请进度；操作区说明由项目负责人发起变更，不显示可提交表单。

管理员：查看项目全景与待办 → 从节点直接调整分配／配额，或从申请记录审批 → 核对影响、当前值与目标值 → 写入分配并显示实际生效进度；拒绝、冲突和失败均留有可追踪原因。

## 3. 信息与连线

页面的项目边界是归属根。横带按「生产服务、开发与任务、接口与协作、项目底座」组织；列按「归属与约束、消费方、已有能力、扩展与申请」组织。搜索与筛选保留必要的父节点和关系上下文。

- 已有能力继续区分自动供给、继承平台默认、项目显式授权，以及已授权但未使用。
- 可申请节点显示用途、规格范围、审批方与申请操作，不冒充已绑定的工作负载。
- 申请中以独立变更节点叠加到原资源旁，原资源仍显示当前有效值；不能把申请目标当成配额。
- 授权状态、运行状态、数据新鲜度为三个独立维度。批准、授权写入、容器／空间实际就绪分别呈现。
- 连线具有明确方向和含义：拥有、占用共享额度、使用／挂载、授权、待审批变更、事件推送。计划关系用虚线，并明确「尚未生效」。
- 正式与待验证槽连接同一生产数据库／对象空间；开发环境连接开发资源。PVC 归属于 taskId，Agent 只挂载其父任务卷；聚合节点保留成员关系，下钻显示逐实例归属。
- 不把套餐、授权、业务绑定、物理实例混成同一个 UUID。节点展示具体层次；资源只计数一次。

## 4. 覆盖资源与动作

| 类型 | 展示内容 | 项目负责人 | 管理员 |
|---|---|---|---|
| 服务规格、槽、副本 | 可用范围、当前版本实际规格、每副本规格与最大副本数 | 申请增加规格范围或配额 | 本页调整项目分配；全局模板修改另属目录治理 |
| 源码、构建与制品 | 仓库归属、构建／迁移、服务镜像、引用版本、共享容量约束 | 查看默认供给和关联，不把发布变成资源审批 | 查看归属并调整其所属项目约束 |
| 开发／业务任务与工作盘 | 套餐、实例、所属任务、工作盘、占用并发 | 申请套餐／并发额度调整 | 本页调整分配与额度 |
| Agent 算力、运行镜像 | 默认来源、可用档位、固定修订、兼容用途与消费者 | 申请目录中明确可申请项 | 分配／撤销未来使用资格，查看受影响引用 |
| 数据库、对象空间 | 开发／生产隔离、用量、上限、预留、后端健康、绑定 | 对象档位与扩容申请；任务级生产数据访问申请 | 本页授权与调额，查看应用和资源实际状态 |
| API、事件、平台工具 | 已授权操作、默认开放来源、订阅、身份和调用方向 | API 申请；查看事件／工具配置 | 本页审批授权，按所属能力处理变更 |
| 配置与密钥 | 环境、配置键数量、版本及消费者，不展示密钥值 | 按已有权限管理项目配置 | 相同页面弹窗或明确业务详情路由 |
| 项目总配额与限流 | CPU／内存请求、Pod／PVC 数、执行并发、共享限流桶 | 提交各项变更申请 | 本页直接调整或审批 |

无独立限额的资源显示「未设置独立上限／共享项目额度／不适用」。读取失败显示「未知」及原因，不能画成 0 或无限。申请中的扩容显示「当前 50 GiB → 申请 100 GiB」，进度条分母仍为 50 GiB。

## 5. 本次审阅的行为影响

1. 增加统一资源／配额申请合同，补齐当前仅管理员直接配置的资源类型。
2. 根据作者「开发不能提交」的要求，资源申请的新旧入口均需服务端按负责人校验；不能只隐藏新页按钮。现有 API 申请的 develop 权限需要调整。
3. 原型按负责人申请、管理员审批展示生产数据访问。本项涉及现有「开发者申请、负责人审批」的变更，已纳入作者批准的设计；实施时新旧入口一并对齐，服务端重新判定角色。
4. 增加 requestable 目录属性，默认不因这个功能而公开隐藏资源。新增明确授权不得意外把继承模式改成固定允许集合。
5. 管理员在项目页修改的是项目分配与约束；全局共享套餐的规格不会被项目操作顺带修改。
6. 生效条件因类型而异：授权改变允许新选择；服务规格需要后续发布／部署；运行镜像不热换；对象扩容及并发额度按所属模块的确认结果生效。页面必须写明。

## 6. 验收要求

两个入口同项目读到一致的授权与实际资源；负责人、开发者、管理员三种动作边界可验证。原型至少可走通资源申请、配额申请、直接调整、批准、驳回、撤回和失败／冲突展示。

详情和表单均用既有 Dialog／FormDialog／ConfirmationDialog。关闭保持筛选、视图、滚动与触发点焦点；二级弹窗 Esc 只关闭最上层。宽屏以拓扑为主，窄屏提供相同数据与关系的清单；深浅主题、键盘、空态、部分来源失败和大量节点均需覆盖。

本 RFC 完成的判据包含真实后端权限／并发、现有授权迁移、实例关系对账、精确 SHA CI 与经过授权的实机验收。原型模拟成功不作为实现或部署证据。

## 2026-10-01 作者追加裁定：同类资源合并

作者指出同类资源平铺会使拓扑随目录规模失控，要求「把同类资源合并到一个节点上，点开之后显示权限列表」。这是既有首屏聚合要求的修正，不增加资源权限或改变审批流程。

每个分类中的资源类型固定显示一个节点，取消数量阈值以及环境／权限拆分。节点展示已有、可申请与申请进度；点击打开统一弹窗里的权限列表，可搜索、按资格筛选和分页查看，每项保留来源、环境、配额和可用操作。原单项详情、申请、配额调整和管理员管理继续从列表进入。

验收要求：同类资源从 1 项增长到数百项，拓扑节点数量与布局高度不随成员增加；混合资格不会被标成首项资格；原始关系方向、单项身份和配额范围保留；长列表下钻及关闭保持上下文与焦点。
# 2026-10-01 大类收敛追加

作者进一步裁定：技术类型仍过度平铺，项目资源入口按命名空间、服务、存储、网络、平台 API 与事件等大类收敛。本轮以该明确要求为实施依据，替代上一轮「每技术类型一个节点」的呈现设计。

主图最多五个节点：命名空间与项目配置（包含项目自身、日志、配置、项目整体额度）、服务与算力、存储、网络、平台 API 与事件。资源条目和技术类型增加均不增加图上节点；类型仅作为权限弹窗中的筛选。管理员继续在单项弹窗直接管理，负责人申请，开发者只读。

验收：两端和窄屏一致；真实跨类有向关系保留，同类内部关系在单项详情保留；独立配额不相加；历史分类／类型／单项链接可用；大量成员仍只有五类以内且图高有界。
