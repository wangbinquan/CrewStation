# RFC-004｜管理员配置 Agent 运行环境，租户按档位使用

> Draft · 2026-09-14。作者已明确职责归属；本三件套与 ADR-0004 是待审方案，尚未进入生产代码实现。

## 背景与依据

RFC-001 已确立算力归平台，但现有管理员表单只包含名称、驱动、模型和说明：[ComputeProfileForm.tsx:17](../../../apps/console/src/features/admin/components/ComputeProfileForm.tsx#L17)。运行凭据仍靠安装配置 `CS_AGENT_ENV_SECRET`，Runner 创建时读一次环境文件：[platformSettings.ts:63](../../../packages/settings/platformSettings.ts#L63)、[runner.ts:85](../../../runtimes/task/src/runner.ts#L85)。

2026-09-14 的 RFC-003 实机验收中，新的任务镜像已正确运行；`rfc003-verify-workbench` 中原生 Claude Code 启动后进入登录选择页。只读核对该 Pod 未设置 `CS_AGENT_ENV_FILE`，也没有 `agent-env` 挂载。作者要求改用 OpenCode，并明确：“运行配置肯定是要由管理员来做的，并且租户使用”。

因此，完成驱动／模型登记不等于完成运行环境配置。租户点击启动以后应直接得到可用 Agent；配置不完整时应提示平台配置未就绪和管理员处理入口。

## 产品方案

平台管理的“算力与 Agent”保留两个页签，租户开发页仍只选择算力档位。

| 页签 | 管理员维护 | 租户得到的行为 |
|---|---|---|
| 运行配置 | Claude Code／OpenCode、模型供应方与协议、网关地址、认证、运行参数、版本、验证结果 | 启动时自动装载选中配置，无需在每个容器重复登录 |
| 算力档位 | 名称、用途、运行配置、该配置下的模型、启用状态 | 选择“日常开发”“复杂分析”等业务档位后逐个启动 CLI |

同一种 CLI 可以有多份运行配置，例如“OpenCode 公司网关”“Claude Code 公司网关”；多个档位可以引用同一份配置，但选择不同模型。配置粒度以 Agent 进程为准，同一开发容器可同时运行来自不同配置的 CLI。

### 运行配置编辑

使用紧凑表格与编辑面板。列表展示名称、CLI、启用版本、检查结果、引用档位数和修改人／时间；草稿、检查通过、检查失败、已启用和已停用分别显示。

编辑分为四组：

1. 基本信息：名称、说明、CLI 类型；当前安装版本来自实际 Runner 能力，不由管理员随意填写可执行文件路径。
2. 模型连接：供应方／协议、Base URL、API Key／Bearer Token／无需认证、模型目录；密钥显示“已设置”及更新时间，修改使用保留／替换／清除明确操作。
3. 运行选项：驱动支持的超时、重试、推理选项与环境变量；高级区域可编辑经当前驱动版本校验的原生 JSON 配置。可预览最终配置及各字段来源，凭据只显示引用。
4. 检查与启用：保存草稿 → 检查格式 → 在目标运行环境检查连接与一次最小模型调用 → 启用此版本。检查显示具体阶段、镜像／CLI 版本、耗时和脱敏错误；模型目录读取成功不代表推理成功。

检查调用使用平台生成的固定测试内容，不带项目源码或业务数据。依赖网络出口、认证或模型权限失败时，管理员在原位置修正；失败草稿保留。检查产生的费用／用量在发起前展示已知信息，未知时不编造价格。

### 生效规则

- 保存草稿不改变已启用版本。编辑采用版本比较，冲突保留草稿并显示当前版本。
- 启用后，下一次新启动的 CLI／Agent 使用新版本，包括已存在开发容器中新增的 CLI。
- 已运行的 Agent 固定原版本，继续执行；页面分别显示“配置已启用”和“此 Agent 使用版本”。
- 对已有 Agent 使用新配置，须通过现有结束／新建流程显式操作，不把后台更新伪装为已经加载，也不批量结束租户会话。
- 停用只阻止新的托管启动，已接受的执行继续按固定快照运行；回退是启用之前仍可用的配置版本。
- 业务子任务与原生 CLI、历史对话的 headless Agent 使用同一个配置解析规则。发布记录冻结的 Manifest 仍引用算力档位，实际执行另记运行配置版本。

## 管理与租户边界

管理员拥有运行配置、认证、启用／停用、检查和档位绑定权限。租户只获得档位名称、说明、是否可用以及自身 Agent 的配置版本／加载结果；管理字段和密钥不放入租户表单、项目配置、仓库、动态事件或导出日志。

项目中的业务说明、代码规则和既有工具权限继续保留。平台负责驱动、模型连接、认证与运行版本；会话负责当前任务、工作目录和已授权的工具范围。原生配置冲突必须按字段显示来源与结果，不能静默覆盖平台用于 MCP 身份和轮次观测的配置。

本次先提供企业 API／网关接入和无需认证的供应方。个人订阅网页登录、跨租户共享 OAuth 账号及其自动续期不作为默认接入方案；如果需要，再明确服务账号与续期流程。这不删除现有 CLI 的原生登录能力。

## 兼容与能力影响

| 既有能力 | 本方案处理 |
|---|---|
| 租户以 `compute` 名称启动 | 保持；不要求租户填写厂商、模型或运行 JSON |
| 已有仅 driver／model 的档位 | 保持兼容路径，并在管理页标识“部署配置模式”；管理员显式绑定运行配置后切到托管模式 |
| 已有 `CS_AGENT_ENV_SECRET` | 仅供未迁移档位继续使用；不自动读取并写回界面，也不把全部旧凭据混入已托管 Agent |
| 原生 CLI／headless／业务子任务 | 全部接入同一解析入口，不只修原生 CLI |
| 正在执行的会话与进程 | 保持当前配置，新增 Agent 可使用新版本 |
| 失效的托管配置 | 启动前报可恢复错误，不悄悄改用其他模型或转入租户登录流程 |

托管模式中的启动前拒绝、停用后的新启动拒绝，以及平台字段优先级，是本次新增的行为约束，需随本 RFC 一并确认与测试。旧模式保持原行为，不以本次迁移擅自删除能力。

## 验收

管理员在 UI 配置 Claude Code 和 OpenCode，各完成一次真实运行环境检查并启用；普通租户只选档位即可使用。双 CLI、业务子任务、已有容器中新建 Agent、配置失败恢复、修改冲突、停用、回退、旧 Runner／旧档位兼容均需有实际证据。细项见 [plan.md](plan.md)。

RFC-003 继续保留完整 UX 验收范围；本 RFC 负责其中暴露的运行配置缺口，不将 RFC-003 提前标记 Done。
