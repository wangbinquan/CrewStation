## 1. 来源与确认

作者 2026-09-23 在本机实机连报四件事（「运行与诊断」拆页签、拓扑里的开发会话、重新部署报内部错误、关掉的 CLI 又出现），前三件的缺陷已按「先修，RFC 另立」当天修复并部署（cc99553d、70801d23、8e5b022d，见 STATE.md 同日一节）。随后作者两句话提出本 RFC：

1. 「整个系统的资源分配、资源启动控制、流量控制要有统一的公共能力来承载起来，防止现在我说的这些问题再次出现」
2. 「也就是整个系统要有一个统一的资源管理中心，来管理资源分配、释放、流量等等与 pod、容器、服务相关的生命周期管理，界面回显信息也是基于这个系统标准输出来的」

按开发规则 §8，先做了只读盘点（[audit.md](./audit.md)，含本机实查），再经四轮问答定下 §4 的十三项裁定。§10 是按作者「由你设计」写下的取舍，§11 是还要作者确认的点。

## 2. 今天的情况

逐条出处见 [audit.md](./audit.md)，这里只列与目标直接相关的事实。

**同一个资源的状态散在多处，界面再各自拼。**

- 一个 CLI 有五处状态：`task_runtime.environments`（`state`＋`native.state`）、`dev_session.native_terminal_starts.record.lifecycle`、执行 Pod 里 Runner 的名册、个人布局的 `hiddenTerminalIds`、页面内存（audit §1.3）。「停止中」只是一句文案 `正在结束此 CLI`，契约里没有这个状态（`modules/dev-session/application/nativeExecution.ts:73-79`）。
- 一个服务槽有四种表示：`release.service_slots`、`observability` 每次请求实时读 Deployment、`cluster-management` 30 秒快照、`gateway.routes`（audit §1.6）。
- 拓扑由盘点、开发会话、槽、数据资源四个来源在前端拼（`apps/console/src/shared/topology/projectTopology.ts:24-80`）；开发页由名册、布局、页面内存拼；概览卡的「N 个 CLI」直接数全部记录，把已结束、失败的都算进去（已于 8e5b022d 修）。
- 全系统至少 17 套状态词汇（audit §3），同一个「运行中」在各页含义不同。

**分配与释放各走各的路，释放之后没人收尾。**

- 额度是一个计数器，六条路径各自加减，没有按记录重算的自愈（audit §1.5）。
- 工作区判失败后只退额度，Pod、PVC、预览 Service 与路由都留着；15 秒一轮的对账只判失败、从不删除（audit §1.1）。
- 本机实查到的遗留：rfc006-verify 的僵尸 Pod 连同 PVC 与路由（自 09-20）；3 个项目 09-21 04:18:35 同一秒批量失败后留下的 PVC 与路由；rfc022 两个失败会话的 PVC；3 个已释放持久卷业务任务的 PVC；demo、workbench 各 2–3 个重建后没删的旧 Runner Secret；demo、workbench 各两条同 Host 的开发预览路由（RFC-013 改名后旧名没删）；Pod 身份索引 695 行里 666 行是从未清理的墓碑（audit §1.1、§1.2、§1.4、§1.8）。

**启动控制没有统一的预检，流量没有统一的控制。**

- 重新部署直接拿发布记录里存的 Manifest 做预检，旧写法在途中抛错成 500（已于 cc99553d 修；audit §5a）。
- 待命槽没有工作负载时，待验证主机的路由仍在，指向没有端点的 Service，访问得到 503（RFC-021 为此开了 `allowEmptyServices`，audit §1.8）。
- 网关上没有任何限流；服务端只有零散的节流补丁；一次布局保存在旧驱动的 cs-api 里挂了 490 秒，没有任何机制兜住（audit §1.9）。

**界面没有资源推送。** 唯一的推送是 cs-session 按任务的 Runner 事件流；Pod 被删、槽变化、发布状态、路由变化都靠 1–30 秒的轮询加 30 秒的全局缓存（audit §2）。

## 3. 目标与非目标

**目标**

1. 平台里与 Pod、容器、服务相关的每一个资源，在一个地方有一条**标准记录**：归属、用途、期望、实况（阶段、原因、条件、子对象）、可做的操作、时间。所有界面、命令行、MCP 与集群管理只读这一份。
2. **声明式**：各业务模块只写期望（要不要这个资源、要什么规格），资源中心负责分配、启动、释放的执行，并记录实况；调和器让集群与台账一致，按种类回收遗留对象。
3. **统一的启动控制**：任何「让一个工作负载起来」的请求先过统一预检，失败给出标准原因（阶段、原因码、说明与出路），不在执行途中崩掉。
4. **统一的流量控制**：路由随资源生命周期挂上与摘除；网关对平台接口、用户域访问数字人、服务域调用限流，超额给出明确结果。
5. **推送**：界面订阅项目的资源变化，页面不轮询、不在内存里记状态、不自行推断「在运行」。

**非目标**

- 不改变资源的业务语义：一项目一开发会话、空闲只提醒不自动释放（不变量 14、D50）、两槽与切流（D45）、额度超额一律拒绝（D31）都不变。
- 不引入 Kubernetes 自定义资源（CRD）与 Operator 框架：台账在平台自己的 PostgreSQL 里，调和器是平台进程里的 worker（§10 B6）。
- 不做多集群；规模与 HA 仍在 M6 一次验证（接受的风险不变）。
- 开发预览主机不限流（D11）。

## 5. 统一资源模型

### 5.1 一条标准记录

每个资源一条记录，字段分三组（契约见设计 §4）：

- **身份与归属**：资源 ID（UUIDv7）、种类、所属项目（系统资源没有）、所属对象（哪个模块的哪个对象，例如开发会话、发布、网关路由表）、上级资源（CLI 的上级是会话工作区）、用途（沿用 RFC-010 的 Pod 用途分类）。
- **期望**（spec）：由所属模块写，只有所属模块能改；带代数（generation），每次改动加一。界面不解读期望的内部结构。
- **实况**（status）：只有资源中心写。阶段、原因（原因码＋说明＋出路）、条件列表（每条有类型、真假、原因、起始时间）、子对象（种类、名字、UID、各自的阶段与就绪）、启动进度（沿用 RFC-022 的 `StartupRecord`）、已观测代数、时间（进入当前阶段、空闲起点、保留到期）。
- **可做的操作**：按阶段算出的生命周期操作（释放、重试、重启、删除工作卷等），每项带「能不能做、为什么不能」；再按当前用户的角色裁掉无权的。界面据此显示按钮，不自己判断。

### 5.2 八个标准阶段

| 阶段 | 含义 | 占额度 |
|---|---|---|
| 排队中 `pending` | 已受理，等额度或调度 | 是 |
| 分配中 `provisioning` | 正在建子对象（卷、凭据、Pod、Deployment、路由……） | 是 |
| 启动中 `starting` | 子对象已建，未就绪；细节是 RFC-022 的启动进度 | 是 |
| 运行中 `ready` | 就绪、可用 | 是 |
| 降级 `degraded` | 部分就绪、反复重启或观测不到（例如 Runner 断开） | 是 |
| 结束中 `stopping` | 已受理释放，正在回收子对象；**受理的那一刻就进入**，所有界面同时看到 | 是 |
| 已结束 `stopped` | 子对象已回收；记录作为历史保留（期限见 Q5）；保留下来的工作卷另有自己的记录 | 否 |
| 失败 `failed` | 平台判定失败；原因写明；按种类有保留期（开发会话 72 小时，D9） | 否 |

待命槽没有工作负载时是「已结束」，原因写明「已下线（时间、原因）」或「尚未部署」。旧的 17 套词汇逐一映射到这八个阶段加条件（设计 §4.3），领域细节（例如 CLI 的「CLI 初始化」、槽的「保留计时」）作为条件或启动进度保留，不另起阶段。

### 5.3 视图与推送

- 每个项目一份资源视图：快照（带游标）加推送流（增量）；断线按游标续上，游标过旧时重新给快照。
- 管理员有全平台视图，集群管理与拓扑的系统层读它。
- 视图里的计数（例如「0 个 CLI 在运行」「2 个需要关注」）由服务端按阶段算好，页面不再自己数。

## 6. 各类资源在中心里的形态

| 种类 | 所属模块写期望 | 子对象 | 备注 |
|---|---|---|---|
| 命名空间 `namespace` | provisioning | Namespace、ResourceQuota | 项目归档才删；调和器补回被改动的额度 |
| 网络策略 `network-policy-set` | provisioning | 四条 NetworkPolicy（D54、D60） | 被删或被改时调和器补回 |
| 开发会话工作区 `dev-workspace` | dev-session | Pod、Runner Secret、预览 Service、工作卷（`volume`）、开发预览路由（`route`） | 一项目至多一个非终态；失败保留 72 小时 |
| Agent 执行 `agent-execution` | dev-session、business-task | Pod、Secret | 用途：CLI、headless Agent、业务子任务；上级是工作区或业务任务 |
| 业务任务工作区 `business-workspace` | business-task | Pod、工作卷 | 持久卷任务可暂停、恢复（不变量 14） |
| 工作卷 `volume` | 随上级 | PVC | 上级结束后按 D8：跟随容器的直接删；持久卷与孤儿卷进入「待回收」 |
| 服务槽 `service-slot` | release | Deployment、Service | 期望里是版本、镜像、副本（含运维覆盖）、配置版本 |
| 构建 `build-job`、迁移 `migration-job` | release | Job | Kubernetes TTL 之外，台账记录结果 |
| 路由 `route` | gateway（槽、服务域、`/api/<proxy>`）、dev-session（开发预览） | IngressRoute、Middleware | 一个 Host 同一时刻只有一个生效的路由（§8.1） |
| 限流策略 `rate-limit-policy` | gateway | Middleware（rateLimit、inFlightReq） | §8.2 |
| 数据库 `database` | data | 数据面上的库与角色 | 生产库、开发库 |
| 数据访问绑定 `data-binding` | data | 数据面上的授权 | 三种模式与审批仍归 data（领域规则） |

Pod 身份索引与放行表仍是网关的领域数据；身份索引改为读中心对 Pod 的观测，不再另开一条 watch（设计 §7.4）。

## 7. 回收规则

按种类（D8、D9）：

| 情形 | 处理 |
|---|---|
| 资源进入「结束中」 | 调和器按 UID 删除它的 Pod、Secret、Service、路由；删完进入「已结束」 |
| 跟随容器的工作卷，上级已结束 | 删除 |
| 持久卷（业务任务），上级已结束 | 不删；工作卷记录进入「已结束」，条件「待回收」，集群管理里列出，管理员输入确认词后删除 |
| 开发会话失败 | 保留 72 小时（Pod、路由、日志都在，可以重试）；到期回收 Pod、Secret、Service、路由，工作卷进入「待回收」 |
| 失败期间又开始了新会话 | 新会话照常开始（与今天一致）；旧会话的开发预览路由立即摘除，保证一个 Host 只有一条路由；旧会话其余对象仍按 72 小时保留 |
| 集群里有、台账里没有的受管对象（孤儿） | Pod、Secret、Service、IngressRoute、Middleware 自动删（UID 前置条件）；PVC 建一条工作卷记录，条件「孤儿・待回收」，等管理员处理 |
| 台账里有、集群里没有的子对象 | 资源进入「降级」或「失败」（按种类的规则），原因写明「子对象不在」 |
| 命名空间、网络策略、额度被改动或删除 | 调和器按期望补回 |

不自动删除的：命名空间（只随项目归档）、PVC（只经管理员确认）、`crewstation-system` 里的平台组件（不在本 RFC 范围）。

## 8. 流量：路由的生命周期与网关限流

### 8.1 路由

- 路由是资源，随上级的阶段挂上与摘除：服务槽「运行中」时指向它的 Service；槽「已结束」（已下线、尚未部署）时，待验证主机指向平台的**说明页**（D13）。正式主机在首次上线之前同样给说明页（「尚未上线」）。
- 说明页写明：这个主机当前没有在运行的版本、原因（某时由谁下线、到期自动下线、尚未部署）、成员可以去「发布与上线」重新部署；非成员照今天的规则看不到这个项目。浏览器请求得到页面，接口请求得到 503 与 JSON 原因（B8）。
- 一个 Host 同一时刻只有一个生效的路由；冲突时按上级的阶段取舍（运行中的优先），被压下的那条立即摘除并在台账里写明原因。今天 demo、workbench 各两条同 Host 的开发预览路由就是这样收掉。
- 切流仍是 release 的领域动作（D45）：切流改的是期望里的「哪个槽是正式」，路由由调和器随之改写。

### 8.2 网关限流（D10–D12）

- **范围**：平台接口（`/v1/*`，工作台与命令行）、用户域访问数字人（正式与待验证主机）、服务域调用（`/api/<proxy>/`、数字人互调、事件推送）。开发预览不限；推送流与终端的长连接不计入并发上限。
- **维度**：两级。第一级按调用方（登录用户；服务域为来源服务，由网关按源 Pod IP 认出）；第二级按目标项目合计，防止一个项目被众人同时打满。平台接口另有每个用户的并发上限。
- **超额**：返回 429 并带 `Retry-After`（秒）。工作台的读请求按 `Retry-After` 自动重读并写明「请求过于频繁，N 秒后自动重试」；写请求不自动重发，写明原因让人再点。数字人收到的 429 由业务自己处理，能力说明 MCP 写明这一约定。
- **配置**：默认值在平台设置里，由管理员修改；管理员可以给单个项目设覆盖值；改完无需重启，调和器随即改写网关的中间件。初始默认值见 Q4。

## 9. 界面与旅程

- **拓扑**（运行与诊断、概览、集群管理）：只读资源视图，按记录画节点与横带，不再拼四个来源。开发会话横带写明「会话工作区 · 运行中 · 空闲 N 分钟 · 0 个 CLI 在运行」，并给出「释放会话」（来自记录的可做操作）；这样「关掉的是 CLI、会话容器还在」一眼能看出。失败保留中的会话写明「失败 · 保留至某时」。
- **开发页 CLI 标签**：标签的状态就是 CLI 记录的阶段。点 × 之后该 CLI 立即是「结束中」（× 置灰、写明「结束中」），推送一到所有窗口同时变化；变成「已结束」后标签按个人布局的已关闭列表收起。个人布局只存显示偏好，不再参与判断在不在运行。
- **概览三张卡、发布页两张槽卡、健康状态**：阶段、原因、可做操作都来自记录；槽卡的「部署版本…」在预检不通过时直接写明原因（例如旧写法的 Manifest）。
- **集群管理**：清单与拓扑读全平台视图；新增「待回收的工作卷」筛选，删除要输入确认词；运维操作（重启、扩缩、删除）经台账执行，结果回到同一份记录。
- **说明页**：§8.1。
- **限流提示**：§8.2。

## 10. 本 RFC 自己的取舍

作者对 D4、D7、D12 说了「由你设计」，下面是我的设计选择，批准三件套即视为接受；不同意的逐条指出即可。

| 编号 | 取舍 | 理由 |
|---|---|---|
| B1 | 记录分两层：平台资源一条（会话工作区、CLI、槽、路由……），Kubernetes 对象作为它的子对象列在记录里，不给每个 Kubernetes 对象单独一条平台记录 | 界面与领域都以平台资源为单位；子对象保留 UID 与各自状态，排障所需信息不丢 |
| B2 | 实况＝中心对集群的观测＋所属模块经端口上报的领域条件（例如 Runner 已连接、CLI 界面已就绪）；阶段由中心按种类的规则统一算出 | 领域信号只有领域模块知道，但「怎么算阶段」只在一处 |
| B3 | 额度按台账推导：受理时在同一事务里数该项目占额度的资源，超额拒绝；去掉计数器 | 计数器没有自愈（audit §1.5）；推导出的数天然一致 |
| B4 | 统一预检＝领域预检（所属模块，例如 Manifest 与档位）＋平台预检（额度、套餐上限、Kubernetes 服务端 dry-run）；任何一项不过都不受理，记录不进台账，返回标准原因 | 「启动控制」的统一出口；与今天 cc99553d 的修法一致但覆盖所有种类 |
| B5 | 推送用 SSE：cs-api 提供按项目（与管理员全平台）的资源流，先给快照再推增量，断线凭 `Last-Event-ID` 续传；与 cs-session 的终端 WebSocket 分开 | 资源变化是单向的、低频的，SSE 经网关与 ForwardAuth 最简单；终端流的负载与生命周期完全不同 |
| B6 | 台账在平台 PostgreSQL，调和器是 cs-controller 里的 worker，多副本以租约分工；不用 CRD／Operator | 与现有持久化、迁移、HA 方式一致，不引入第二套状态存储 |
| B7 | 孤儿判定只针对带 `app.kubernetes.io/managed-by=crewstation` 标签、位于项目命名空间里的对象；按 UID 前置条件删除 | 不误伤别人的对象；删除前再核对一次 |
| B8 | 说明页由 cs-api 渲染（路由把待验证主机指向平台的说明页服务）；浏览器请求给 HTML，接口请求给 503＋JSON 原因 | 说明里要读台账里的下线原因与时间 |
| B9 | 限流用 Traefik 的 `rateLimit` 与 `inFlightReq` 中间件，按 ForwardAuth 注入的身份头计；多副本网关的全局计数用 Traefik 的分布式后端（是否可用在 T2 验证，不可用时按副本数折算并写明） | 限流只在网关（D10）；计数键要在认证之后才有 |
| B10 | 迁移分期：先任务类容器（今天两件事的根源），再服务槽与构建、路由与限流、命名空间与网络策略、数据资源；每期旧接口由台账推导、契约不变 | 一次性切换风险太大；分期能在本机逐期实机验收 |
| B11 | 旧形状对象由中心收编：按 UID 认领，标准记录只用 UUID，旧的 `rel_…`／`tsk_…` 作为别名可查；可改的标签改成新标签，不可改的（PVC 名字）保留别名 | RFC-013 之后的遗留靠别名匹配仍在（audit §1.6），收编后只剩一处 |

## 12. 能力影响清单

按开发规则 §5.5，以下是本 RFC 关闭、收缩或改变的既有能力，请作者逐项确认：

| 编号 | 变化 | 受影响的形态 |
|---|---|---|
| C1 | 失败的开发会话不再无限期保留：72 小时后回收容器与路由（D9） | 失败会话的诊断窗口从「一直」变为 72 小时；工作卷不自动删 |
| C2 | 释放或失败后遗留的 Pod、Secret、Service、路由由调和器自动删除（D8） | 今天这些对象会一直留着，手动 `kubectl` 查看的人会发现它们消失 |
| C3 | 持久卷与孤儿卷不再静默保留：列入「待回收」，由管理员确认后删除 | 集群管理多出一类待处理项；不确认就一直留着 |
| C4 | 待验证主机（与首次上线前的正式主机）没有工作负载时，不再返回 503，而是说明页／503＋JSON（D13） | 依赖 503 判断「未部署」的脚本需要看 JSON 原因 |
| C5 | 平台接口、用户域访问数字人、服务域调用开始限流，超额 429（D10–D12） | 以前不限；突发的自动化脚本与数字人互调可能收到 429 |
| C6 | Design D53 修订：原模块保留期望，生命周期实况归资源中心（D5）；集群管理的运维操作改为经台账执行 | ADR-0006 与 RFC-010 的所有权描述随之修订；集群管理不再直接改集群对象 |
| C7 | 额度计数器去掉，改为按台账推导（B3） | 直接改 `task_runtime.admissions` 的运维手法失效 |
| C8 | 一个 Host 只保留一条生效路由（§8.1） | 同 Host 的旧路由会被摘除 |

## 13. 验收标准

| 编号 | 内容 |
|---|---|
| RC-01 | 一个资源一条标准记录：拓扑、概览、开发页、发布页、健康状态、集群管理对同一资源显示同一阶段与原因（逐页与视图接口对照） |
| RC-02 | 结束 CLI：受理即「结束中」，已打开的所有窗口在推送到达后同时变化；离开再回来、刷新、另一名成员看到的一致；不会被再结束一次 |
| RC-03 | 推送：断网后恢复按游标补齐；游标过旧时重新给快照；成员被移出项目后，他的资源流被断开 |
| RC-04 | 开发会话失败后保留 72 小时（验收用缩短的保留期或可调时钟）：期间可看日志、重试；到期回收容器与路由，工作卷进入「待回收」 |
| RC-05 | 按种类回收：人为制造的孤儿 Pod、Secret、Service、路由被自动删除；孤儿 PVC 只标注，管理员输入确认词后删除 |
| RC-06 | 本机现存的遗留对象（audit 实查清单）按 RC-05 的规则处理完，逐项核对 |
| RC-07 | 统一预检：旧写法 Manifest、档位被删、套餐被收回、额度已满，各自给出标准原因，不出 500，记录不进台账 |
| RC-08 | 待验证槽下线后访问待验证主机：浏览器看到说明页（原因、时间、怎么重新部署），接口请求得到 503＋JSON；重新部署就绪后恢复为服务；同 Host 只剩一条生效路由 |
| RC-09 | 限流：平台接口、用户域、服务域各用突发脚本打到上限，得到 429 与 `Retry-After`；工作台读请求按 `Retry-After` 自动重读并写明，写请求不自动重发；推送流与终端连接不受并发上限影响 |
| RC-10 | 限流配置：管理员改平台默认值与项目覆盖后无需重启即生效 |
| RC-11 | 额度由台账推导：并发超额一律拒绝并写明原因；删掉资源后额度立即回来 |
| RC-12 | 命名空间、额度、网络策略、数据库、数据访问绑定都有标准记录；人为删掉一条网络策略后被补回 |
| RC-13 | 两个 cs-controller 副本同时运行时，同一资源不会被两边同时调和；杀掉持有租约的副本，另一副本接手 |
| RC-14 | 集群管理的清单、拓扑与运维操作经台账，结果与各页一致；`tools/arch` 规则体现新的依赖方向 |
| RC-15 | 旧形状对象被收编：标准记录只用 UUID，`rel_…`／`tsk_…` 可作为别名查到 |
| RC-16 | 本地 gate、改动行防护通过，精确 SHA 的 CI 六项成功 |
