# RFC-001 · 算力由平台统一提供｜Proposal

- 状态：Draft
- 日期：2026-09-12
- 作者裁定：2026-09-12 四选一确认「选管理员定义的档位名」＋「驱动也归平台，含在档位里」

## 1. 背景

用户 2026-09-12 指出：**所有 Agent 的算力资源都应该由平台统一提供，业务使用的时候不应该还要填算力来源。**

现状与这句话不符的地方，逐条对着源码：

| 面 | 现状 | 位置 |
|---|---|---|
| 模型凭据 | **已经是平台统一提供的**：平台级 Secret 挂进每个任务容器的 `/etc/crewstation/agent.env`，业务碰不到 | `modules/task-runtime/application/containerEnv.ts:38` |
| Manifest 的 Agent 档案 | 业务必须写 `driver` 与 `model`（`<provider>/<model>`） | `packages/contracts/manifest/tasks.ts:9-17` |
| 开发会话启动 Agent | 请求体必须带 `driver` 与 `model` | `packages/contracts/api/devSession.ts:49-56` |
| 工作台 | 「新建 Agent」是驱动下拉 ＋ **模型自由文本框** | `apps/console/src/features/dev-session/` |
| 平台侧的算力对象 | **不存在**。没有任何「模型目录」「算力档位」之类的平台对象 | 全仓 grep 无 |

对照 CPU 与内存：它们走的是管理员定义的 `ServicePlan` / `TaskProfile`，业务只在 Manifest 里引用一个**名字**（Design §1.2 `ServicePlan` / `TaskProfile` 行，「管理员定义的服务资源套餐与任务容器规格；Manifest 引用」）。算力没有对应物，是这套设计里唯一一处「资源规格由业务直接写具体值」的例外。

后果：

- 业务开发者必须知道厂商与模型标识符才能起一个 Agent，而这是平台的采购与成本决策，不是业务决策。
- 平台换模型、调供应商、按成本分档，要改每一个业务仓库的 Manifest。
- 工作台上那个自由文本框没有任何校验面——写错了要等 Agent 起来才报错（实现时那个 Agent 明确说过：平台没定义模型清单，所以只能给自由文本）。

## 2. 目标与非目标

### 目标

1. 业务在 Manifest 与开发会话里**不再出现任何厂商、模型标识符或驱动名**。
2. 平台新增一类管理员维护的对象：**算力档位（ComputeProfile）**，与 `ServicePlan` / `TaskProfile` 同构——管理员定义，业务按名字引用。
3. 档位封装「用哪个驱动、哪个模型」这一整件事；业务只表达**要多强的算力**，不表达**用谁的算力**。
4. 平台换模型或换供应商时，只改管理员那一份目录，不动任何业务仓库。

### 非目标

- **不做按项目的档位白名单**：首版所有已定义档位对所有项目可用。若将来要按项目限制，另立 RFC。
- **不做用量计量与成本归集**：Design §10 已明确首版只有「每数字人并发任务数」一种预算，没有时长与模型用量预算。本 RFC 不改这条。
- **不动模型凭据的下发方式**：仍是平台级 Secret 经环境变量进容器（Design §10 记录在案的残余风险），本 RFC 不碰。
- **不改 TaskRunner 协议里的 `driver` / `model`**：容器里要跑的是具体驱动与具体模型，解析发生在平台侧。任务容器镜像与 `packages/agent-drivers` **零改动**。

## 3. 用户故事

**业务开发者**：我在 `crewstation.yaml` 里给业务 Agent 档案写 `compute: balanced`，不需要知道背后是哪家的哪个模型。在开发会话里起 Agent 时，我从一个下拉里选档位，下拉里是「快速 / 均衡 / 深度」这样的名字加一句说明。

**平台管理员**：我在平台管理里维护算力档位表，每一档写清用哪个驱动、哪个模型、一句给业务看的说明。公司换供应商时我只改这张表，业务侧无感。

**接手的运维**：我在工作台看到某个 Agent 跑在 `balanced` 档上；要知道那具体是什么，去平台管理的算力档位页查这一行。

## 4. 验收标准

1. `crewstation.yaml` 的 `tasks.agentProfiles[]` 里**没有** `driver` 与 `model` 字段，只有 `compute`；写了 `driver` 或 `model` 的 Manifest 在发布时被拒绝并说明原因。
2. `POST /v1/tasks/:taskId/agents` 的请求体**没有** `driver` 与 `model`；`compute` 可省略，省略时用平台默认档位。
3. 引用了不存在档位的发布被拒绝，错误信息列出当前可用的档位名——与 `ServicePlan` 引用不存在时的行为一致。
4. 工作台「新建 Agent」是**档位下拉**，选项来自平台目录，没有任何自由文本的模型输入。
5. 平台管理里有算力档位的增删改页，与服务套餐、任务容器套餐并列。
6. 最小示例模板与两个接入容器改用档位名，本机开通链与 `/chat` 业务子任务链照常跑通。
7. 租户面的 Agent 列表显示**档位名**，不显示厂商与模型标识符。

## 5. 能力影响清单

本 RFC 关闭了一项既有能力，按开发规则 §5.5 逐项列出：

| 被关闭的能力 | 影响 | 处置 |
|---|---|---|
| 业务可以在 Manifest 里指定任意 `<provider>/<model>` | 业务不能再自选模型；平台没提供的模型用不了 | **这正是本 RFC 的目的**，用户 2026-09-12 明确要求 |
| 业务可以在 Manifest 里指定 `driver` | 业务不能再按驱动的工具生态偏好选 claude-code 或 opencode | 用户 2026-09-12 选定「驱动也归平台，含在档位里」；如某业务确有偏好，由管理员为其加一个档位 |
| 开发会话可以临时试任意模型 | 开发者不能再临时换一个平台目录外的模型做对比 | 管理员加档位即可；平台目录是唯一的算力来源，这是本 RFC 的前提 |

**没有兼容期**：本仓尚无外部使用者，全部 Manifest 与调用方都在本仓内，一次性改完。被拒绝的旧写法有明确报错，不静默忽略。
