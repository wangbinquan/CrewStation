## 1. 来源与范围

作者于 2026-09-21 明确提出：

1. 存储管理给出存储的申请数量和使用数量。
2. Pod 给出申请的容器、每个容器对应的资源申请量、部署节点。
3. 整体给出总节点数、总资源量、已消耗资源量及实时 CPU、存储、网络等关键资源信息。

RFC-010 已完成资源目录与管理动作；其设计 §2、§4 只覆盖节点名称及 requests／limits，没有实时指标。本 RFC 增加容量和观测，不改变已有重启、扩缩、删除与领域生命周期。

**建议范围**：全局容量面板覆盖整个 Kubernetes 集群，包括基础组件与其他工作负载的总体占用；同时单列 CrewStation 管理的项目及平台组件用量。可操作资源清单继续只纳入 CrewStation 对象。节点只有只读详情，不新增节点或 PV 的删除、驱逐、维护操作。

作者随后明确选择“同时保留最近 7 天趋势”。本轮同时交付实时观测和七天历史，使用独立指标存储；不新增告警通知、计费或 Grafana 页面。

## 2. 页面与指标

入口仍为 `/admin/cluster`。第一屏先回答“总共有多少资源、申请了多少、实际用了多少、还剩多少”，再进入资源目录。

### 2.1 全局概览与节点

全局区域明确标注“整个集群”，不随下面的项目筛选悄悄改变口径。CrewStation 分项及资源目录明确标注当前项目／平台系统范围。

| 区域 | 必须展示 |
|---|---|
| 节点 | 总数、Ready／NotReady／Unknown、可调度／已禁止调度；节点名、角色、Kubernetes 版本与压力状态 |
| CPU | 总核心数、可分配核心数、已调度 Pod 有效申请量、已设置的限制合计、实际消耗核心数／总容量占比；未设置限制的容器数量另列 |
| 内存 | 总量、可分配量、有效申请量、已设置限制合计、实际工作集、使用比例；不把缓存或申请量伪装为实际消耗 |
| 临时存储 | 可分配量、Pod 申请／限制、Pod 实际临时存储用量；与持久卷分开 |
| 节点磁盘 | 节点文件系统容量、实际占用、可用空间、inode 使用／可用数；镜像与容器文件系统按来源分项 |
| 持久卷 | PVC 总数、Bound／Pending、申请总量、已绑定声明容量、已观测使用量、统计覆盖数量与最后观测时间 |
| 网络 | 节点接收／发送字节速率与错误速率；展示采样窗口和选用网卡，不把累计字节数当每秒速率 |
| 磁盘 I/O | 节点设备读取／写入字节速率、读／写操作速率；按设备展示来源与覆盖范围 |
| Pod 容量 | 节点支持的 Pod 数、当前已调度活跃 Pod 数、未调度 Pending 数；CrewStation Pod 数单列 |
| 扩展资源 | 节点实际声明的 GPU／其他扩展资源容量、可分配量、申请量；没有设备利用率来源时明确说明 |

新增“节点”页签。每行可展开容量、用量、压力、设备／网卡与该节点上的 CrewStation Pod。节点详情不能把全节点消耗全部算给这些受管 Pod。

### 2.2 Pod 与容器

Pod 列表直接显示节点、容器数量、CPU／内存有效申请与实际使用量，保留项目、用途、状态和重启信息。窄屏在表格自身滚动，详情保留完整数据。

容器页签改成结构化表格：名称、普通／初始化／常驻 sidecar／临时调试类型、镜像、状态、CPU 申请／限制／实际、内存申请／限制／实际、临时存储申请／限制／实际，扩展资源按存在的键展开。申请为空显示“未设置”，限制为空显示“未限制”；初始化完成或已结束的容器不冒充有实时用量。

Pod 概要显示有效申请总量、Pod 级资源约束、overhead、QoS、节点及挂载卷。未调度显示“未调度”与调度原因。Pod 的网络用量只在 Pod 层展示，不复制成每个容器各自的网络用量。

### 2.3 存储

“存储与配置”中提供存储摘要和 PVC 专用列：申请、已绑定容量、已使用、使用／声明容量比例、StorageClass、访问模式、挂载 Pod／节点、采集时间与来源状态。ConfigMap、Secret 等行不显示无意义的容量列。

PVC 详情同时给出关联 PV、挂载关系与观测来源。未挂载但仍保留的本地卷也要显示真实占用。本地目录型存储明确标注“声明容量，非硬配额”；实际超过申请量可超过 100%，不能截断成 100%。

不把 `ResourceQuota.status.used` 命名为磁盘实际已用；它单列为配额已申请／已占额度。

### 2.4 最近七天趋势

总览、节点、Pod／容器、PVC 均能查看最近 1 小时、6 小时、24 小时、7 天，也可在七天内选择自定义范围。CPU／内存、节点磁盘／PVC 用量、网络收发和磁盘读写按对应对象提供；申请／限制／容量线可与实际用量对照。

长时间范围按显示粒度归并，标出平均值与峰值，不用平均值掩盖短时峰值。图表给出单位、时区、采样时间、显示粒度与覆盖情况；悬停和键盘可读具体值。

采集断档留空并显示原因，不补零或画线跨过缺口。同名重建按不同 UID 分开；已删除的资源在历史目录中仍可查询七天内的记录，标记“已删除／已结束”，不提供管理动作。

部署之前的历史无法追溯，新装明确显示“从开始采集时间起有数据”；真实积累满七天后滚动保留。控制面或指标服务重启后保留已有历史。

## 3. 统计口径

- 总容量、可分配容量、已申请、限制与实际消耗分别展示，单位一致。CPU 用核／m，内存与存储用 IEC 单位，网络和 I/O 用 B/s；百分比注明分母。
- 全集群节点 CPU／内存用量包含系统进程，CrewStation 分项来自受管 Pod；两者不是可直接相减得到“其他业务”的同口径集合。
- 已调度有效申请按 Kubernetes 的普通容器、init、常驻 sidecar、Pod overhead、Pod 级资源和原地调整规则计算；不能简单把所有容器相加。终态 Pod 不占当前申请合计，未调度申请另列。
- “可分配减已调度申请”称为“账面未申请量”，不承诺某 Pod 一定可调度；亲和性、污点、扩展资源和节点状态另有约束。超额申请不隐藏负余量。
- PVC 按 UID 去重。一个卷被多个 Pod／节点挂载只算一次。PVC 声明容量、卷实际占用、节点磁盘容量是不同维度，不能相加。
- 节点镜像／容器文件系统可能共享磁盘，不相加冒充总盘量；节点总览按明确的 node filesystem 口径汇总，额外挂载点单列。不声称它是外置 SAN／云存储池的物理总容量。
- 网络节点总量只统计选定的对外接口，同一份默认接口和接口列表不重复累加，不再加上 Pod 或 veth 流量。跨节点通信会在两端计量，标题为节点接口流量合计，不声称公司出口流量。
- 指标值 0、未设置、未采集、首次等待速率样本、过期、不支持、采集失败必须可区分；残缺集合显示“已观测合计”及覆盖率，不称完整总量。

## 4. 数据采集与体验

建议容量／声明随资源快照采集；CPU、内存、网络、I/O 每 15 秒采样，PVC 目录用量每 60 秒后台测量。数值均显示源时间和速率窗口；这是拟定默认值，不是已测性能承诺。

优先读取 Kubernetes Node／Pod／PVC／PV 和 kubelet 统计。实机的 local-path PVC 没有 kubelet 卷统计，因此增加只读存储采集器，按白名单根目录扫描平台受管卷的文件元数据，返回大小，不读取或返回文件内容。CSI 已上报卷指标时无需目录扫描。

采集在后台运行，用户打开页面只读取共享结果。卷扫描、指标采样、目录扫描、管理动作各有独立执行容量；慢盘不应卡住 Pod 列表或管理操作。

建议随平台部署内部 Prometheus，持久化保留至少最近七天的可查询样本，前端通过平台受控查询接口读取。它与采集器一起纳入系统内置资源；安装前核对指标卷及其底层磁盘实际余量，不以 PVC 申请成功代表已经获得物理空间。

加载、缺少能力、单节点失败与过期值有各自状态；刷新不清除用户正在填写的操作表单。中英文、浅深色、键盘与 1280／390／320px 均验收。

## 5. 验收标准

1. PVC 申请／绑定／实际占用可与独立 Kubernetes 查询和专用测试卷文件系统测量对账；本机现有 local-path 形态不以全部“暂无数据”交付。
2. Pod 容器、资源申请／限制、实际使用与节点在列表和详情一致，初始化和 sidecar 的有效申请计算正确。
3. 总节点和各资源容量、申请、实际值有明确范围和单位，真实 0 与缺失不混淆。
4. 网络／I/O 是两次有效样本间的速率；重启、计数回退、迟到、同名新 UID 不产生负值或串数据。
5. 共享卷、镜像文件系统和网络接口不重复计数；部分覆盖不会呈现为完整总量。
6. 原有管理动作、来源状态、UID 保护、项目归属和用途分类的测试与实机路径保持通过。
7. 七天范围、短期峰值、缺口、删除对象、同名替换、重启后历史保留及到期回收可验证；新装不伪造过去七天的数据。

逐项验收编号和发布要求见 [plan.md](./plan.md)。
