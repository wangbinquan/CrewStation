# RFC-029：以任务列表为入口的业务恢复

状态：In Progress · 2026-09-27。任务列表、失败置顶与不再填写内部身份来自作者本次明确反馈；作者已明确批准下述新的恢复执行契约，进入实施。RFC-027／028的原验收继续。

## 问题

现有 `/admin/business-execution` 让管理员填写 `project/service`，实际仅检查旧协议执行票据并停止环境／解除阻塞。它既不是任务列表，也不提供 v3 任务恢复，却以“业务执行恢复”命名，造成错误预期。源码见 `AdminBusinessRecoveryPage.tsx`、`business-task/application/legacyRecovery.ts`。

作者要求：直接显示任务，失败任务置顶，点击具体任务恢复。不能将上述旧票据操作换个按钮名充当任务恢复。

## 产品行为

1. 进入页面直接读取真实任务列表，默认覆盖管理员可查看的项目；失败／状态待确认优先，其次暂停／恢复中，再是其他状态。同组按更新时间倒序，服务端先排序再分页。
2. 显示项目名称、任务名称或已有请求说明、状态、失败原因、更新时间；未提供名称时明确显示任务编号，不凭空编造业务名称。支持项目与状态筛选，保留条件与选中任务。
3. 点击任务进入详情：父任务与失败子任务、日志／失败信息、运行镜像、保留工作区与恢复条件。旧票据排障位于相关任务详情，不能占据首页。
4. “恢复任务”展示本次具体动作、保留的数据、会重新执行的范围及副作用提示。正常恢复和从头重试分清；平台不能确认旧执行已停止时，先处理状态确认，不自动重复执行。
5. 确认后返回持久操作编号并显示等待接收、恢复中、已恢复或失败。浏览器断线、刷新和平台重启不产生第二次恢复。

## 推荐执行边界

**由所属业务应用的当前执行控制器执行恢复请求。** 管理员提交持久恢复意图；平台保存请求、验证权限和旧执行状态、展示进度。业务服务仍通过 RFC-027 的执行权与幂等接口发起恢复，平台不冒用服务身份或当前 fence。

应用通过明确能力声明接入。尚未接入、没有在线执行控制器、工作区丢失、镜像不兼容或原执行未确认结束时，界面说明具体原因，不能以“已恢复”结束。CrewStation 的 v3 示例应用必须实现请求接收与恢复，才能证明按钮可用；不修改只读外部 agent-workflow 仓库。

旧协议已有管理员恢复操作仅按真实支持范围开放，不将它直接用于 v3。服务整体恢复与发布交接仍使用 release 的原流程。

## 与已批准范围的关系

任务枚举和按状态排序是此次页面可用性修复，补入 RFC-027 的只读工作台；不会扩大执行权限。持久恢复请求、应用能力声明及新的失败工作区恢复语义属于本 RFC 的新契约，须在批准后实施。RFC-028 的镜像快照规则不变：恢复不借机替换默认镜像、档位、初始化或会话材料。

## 已批准决策

R1（2026-09-27 作者明确批准）：采用上述“平台提交恢复请求，所属应用执行”的边界。管理员直接绕过应用重新执行任务不在本方案中；若作者需要该能力，必须另行定义业务状态同步、执行权与重复副作用责任。
