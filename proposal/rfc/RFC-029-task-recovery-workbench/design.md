# RFC-029 技术设计

状态：Done · 2026-09-28，作者批准的R1方案已实现、部署并验收，见acceptance首节。

## 只读任务投影

business-task L5拥有任务列表投影，合并 legacy tasks 和 v3 execution_operations／生命周期投影。管理员入口分页并支持项目／状态过滤；不借用 worker 的 claim／observe 接口读取，查询不得更新租约、准入、投影游标或环境。失败排序在存储侧执行，未知状态独立呈现。项目名称由 project 公开能力取得，禁止跨模块读表。

返回父任务身份、项目／服务、协议、状态、时间、错误摘要与失败子任务概览，不返回 prompt、凭据、文件内容或完整执行材料。详情按管理员权限逐次校验；分页游标包含排序位置，重复或变动状态允许重读校正，但不得永久跳过失败任务。

## 恢复评估与请求

新增只读评估端点，服务端根据父任务／子任务、旧执行停止证据、持久卷、原镜像／档位快照和当前应用能力给出可执行动作与禁用原因。客户端不能决定能否恢复。

管理员提交 `requestKey`、目标父／子任务、期望 generation／attempt、选择动作与评估材料摘要。恢复请求保存操作者、所属服务、原材料指纹、不可变目标、创建时间和审计；同键同内容返回原请求，同键不同内容409。受理时重新验证权限与当前状态，未知执行或已变化快照412，禁止读取 latest 默认值替换历史选择。

状态：`pending` → `claimed` → `running` → `succeeded | failed | rejected`。`pending`表示等待应用接收，不表示资源正在恢复；拒绝和失败均给出可读原因。状态不明时保留请求，不能自动 mint 新 requestKey。

## 执行权与应用接收

服务通过现有认证与有效 fence 读取并认领本服务请求。认领绑定当前 holder／epoch和有界租约；交接后旧 epoch不能提交动作，新 holder可接续同一请求。应用在自己的持久事务中记录意图，再用固定幂等键调用原恢复／重试契约，防止崩溃重复派发。

真正的任务变更请求携带 `recoveryRequestId`，平台校验其服务、目标、动作、原 generation／attempt及材料指纹，记录产生的 operation／attempt。进度由平台实际操作与资源观测推进，不能仅接受应用一句 success。业务应用仍负责业务数据库的状态一致性，平台不得假造它的数据库屏障。

## 各恢复类型

- 暂停的持久父任务：通过原 resume 恢复同一卷和镜像，实际连接就绪才成功。
- 已停止的失败／取消子任务：应用明确选择原生会话续跑或新 attempt；只有具备兼容会话材料才可续跑。新 attempt保留原镜像与执行材料，展示重新执行的副作用范围。
- 失败的持久父工作区：须增加显式恢复状态机，先确认旧容器及活动子执行停止、验证原卷 UID／目录所有权和原镜像，才重建原工作区。无停止证明或卷已丢失拒绝，不能创建空卷冒充恢复。
- 无法保留原工作区：只有业务应用显式支持“从头新建任务”时允许另一种动作；生成关联的新任务，不能把旧失败任务写成恢复成功。
- 状态未知：先对账或明确停止旧执行，确认前禁止重试。旧协议票据使用原 stop/reconcile 墓碑规则。

## 工作台

页面不再出现要求手填内部身份的表单。任务列表／筛选常驻，详情与恢复确认使用 shared Card、DataTable、FormDialog／ConfirmationDialog。恢复期间重复按钮禁用，刷新恢复原操作进度；切换任务不沿用旧任务的确认材料。

中文／英文均使用业务可理解的动作与原因。主按钮仅在有真实可执行动作时出现；未接入恢复能力时显示原因与所属应用入口，不能放一个必然失败的“恢复”按钮。失败任务置顶和可用动作从服务端状态驱动。

## 落位与迁移

contracts/api/business 增加恢复DTO；business-task/domain/application/ports/adapters 管理评估、请求表与事务；api-client公开工作台与服务端接口；v3示例客户端和controller接入；console的任务列表、详情与恢复交互位于业务任务feature。无跨模块表写入。新增迁移与契约金样按仓库门禁更新；保留既有接口与旧应用行为。

## 实现细节（2026-09-27）

- 能力声明为 `tasks.recovery.actions`，动作分别为 `resume-task`、`rebuild-workspace`、`retry-subtask`、`resume-subtask`、`restart-task`；必须配合 fenced 执行控制。缺少声明不会自动开放。
- 请求以 `(serviceId, requestKey)` 唯一；同一父任务或子执行的未结束恢复互斥。恢复任务变更携带 `recovery: { recoveryRequestId, claimId }`，实际操作固定幂等键 `recovery:<requestId>`。认领 token 更新不改变真实 retry 参数摘要。
- 请求关联 operation／新 attempt 与实际准入使用同一服务级事务；在持久派发前完成关联。终态重放只读取已绑定结果，不重置请求为 running。
- `recovery_requests` 保存非敏感目标、操作者与审计关联；`recovery_audit` 逐项追加请求、认领、运行与结果。评估／列表不改变执行权。内部结果投影使用独立 `observed_at` 排队，长期未结束请求不会挡住后面的结果，也不伪造用户看到的更新时间。
- 资源停止、原卷身份、原镜像／会话兼容等事实须从所属模块取得。纯评估函数只接受这些事实；未知值不得作为可恢复证明。新 HTTP 入口接通前，持久仓储不是面向用户的恢复入口。

### 管理员入口与只读证明（2026-09-28）

管理员评估／提交使用 `/v1/admin/business-execution/tasks/:taskId/recovery`，原请求列表使用子路径 `/requests`。可选 subtaskId 来自所选任务详情，所属服务从平台持久任务反查。认领令牌和应用 fence 不进入管理员接口。幂等回执检查先于当前评估；检查资源期间发生并发相同提交时再次读取原回执，避免把成功请求误报为评估过期。展示优先未结束请求，动作互斥使用独立有界 EXISTS 查询，不能从最近100条历史推断。

task-runtime 的公开内部只读能力 `inspectBusinessRecovery` 返回原卷验证、父执行停止和子环境存在事实；持久记录变化、集群读失败均不提供肯定证明。runtime-environment 的 `inspectReference` 核对原 owner 和不可变快照／用途验证，不取 latest，不修改引用。business-task 在自己的 application/recovery 组合这些公开能力与本模块停止投影／加密计划／会话，再调用纯评估；无跨模块表访问或写入。两个 HTTP 路由文件分别属于工作台管理员和业务 Pod，不混合身份。

### 失败工作区重建与关联新任务（2026-09-28）

- `POST /v3/business-tasks/:taskId/rebuild` 必须携带恢复认领；与原恢复请求同事务登记生命周期。运行时只接受失败的独立持久业务工作区，核对原 PVC／旧 Pod 消失／子环境停止。持久操作编号和世代随原 render 保存，重复调用不增加启动次数或配额，旧世代不能重启后续失败。沿用原镜像和资源，新 Runner 实际连接后才完成。
- `POST /v3/business-tasks/:taskId/restart` 为显式的重新执行入口，要求当前 fenced 控制权和 restart-task 认领。复制原任务契约、发布材料、镜像快照和资源配置，生成独立任务 ID；新准入意图保存 restartOf，原请求同事务绑定 operationId／resultTaskId。原任务保持失败；客户端不能提交新的镜像或档位覆盖历史材料。当前应用不接受原契约版本则拒绝。
- 重新执行的 runtime 准入只在原卷不能保留且旧父／子进程确认停止时进行。新任务使用独立 PVC、Pod、Runner 令牌和初始化状态；原环境与原卷不修改。持久镜像引用从原 owner 复制，同键并发落败的候选释放自己的引用。项目锁中复核源环境没有变化，再扣额度登记新环境。
- 重新执行的额度拒绝保留原新任务 ID；丢回执先按固定 ID 对账。恢复请求不会因创建资源的准入成功而完成，需观测新任务运行；新任务启动失败或关闭则记录失败。应用不提供成功上报接口。v3 示例显式支持五项动作，先持久化意图，沿原键重放；不自动重放旧子任务外部副作用。

### 管理员任务详情与恢复交互（2026-09-28）

- `GET /v1/admin/business-execution/tasks/:taskId` 返回当前任务和子执行 DTO，不返回加密执行计划；与评估、请求读取一样每次检查管理员权限。列表支持失败／状态未知／暂停／运行／关闭筛选，筛选在服务端分页之前执行；游标绑定项目和状态，失败子执行使父任务进入失败优先队列。
- 详情使用既有共享 Dialog，父任务与命名子执行在弹窗中选择；动作先显示后果及固定材料，再通过 ConfirmationDialog 提交。嵌套 Esc 只关闭最上层，关闭详情返回列表原按钮、筛选和滚动位置，关联的新任务仍在同一详情弹窗打开。
- 根据服务端评估展示可用动作及不可用原因；状态或评估材料变化使旧确认失效。读取失败／撤权／已有未完成恢复禁止重复提交。请求历史区分 pending、claimed、running、succeeded、failed、rejected，显示关联新任务／attempt和可读失败原因，不把受理视为成功。
- 同一确认有同步防双击保护；请求键按 taskId＋assessmentDigest 暂存于 sessionStorage。丢回执后关闭重开沿用原键，不自动重发；平台回读结果或原键重放决定结果。已结束记录之后明确再次请求才使用新键。
- 文案位于独立 `features/business-recovery/i18n`，生产动态目录与测试显式目录均加载中英文；任务自身环境错误和子执行错误直接展示，机器失败码另有可读解释与原始详情。
