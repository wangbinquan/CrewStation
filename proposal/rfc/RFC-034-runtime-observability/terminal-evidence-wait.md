# 未启动执行的终态证据等待

2026-10-11 本机实际回收观察到两个原验证执行反复失败：未启动的执行因 Pod 未就绪先进入业务失败，原 owner 已保存 `closeReason=error`，但没有 Session 绑定或实际模型终态回执。当前调用仍向结束仓提交 `reason=error`，触发“完成或错误请求需要对应实际终态回执”；部署后的 28 分钟内每个执行出现 702 次相同重试。该业务失败不能作为模型已错误退出、Token 为零或物理回收完成的证明。

本修复在原请求桥接中等待缺失的实际 completed/error 回执；没有回执时不创建结束 job，也不修改原 owner、绑定、首个原因、费用或任何数值。原正常取消仍创建独立等待 job。实际回执到达后原恢复路径可以继续；结果不匹配仍由原严格合同拒绝。Selected 原生执行在业务结束时不写物理 `endedAt`，只有原执行环境真正结束后才按已有持久收尾路径保存时间；legacy 结束逻辑保持。

使用原真实 PostgreSQL producer 夹具验证未绑定失败、重建生命周期的幂等等待、迟到正常完成，以及 completed 回执不能冒充 error。保留原断言、时间预算和源绑定检查，完成 handoff 的异常期待改为明确等待；未运行的测试不会记为通过。当前两个旧执行的缺口与既有 endedAt 记录不回写，不以本修复宣称旧 Pod 已回收。

发布门为本候选一次原始 `bun run check`、该提交精确六项 hosted CI，以及部署后原失败日志和实际 Session／Pod 证据核对。未知与未绑定状态仍不授权物理删除，不重建旧运行时，不放宽终态、ACK、完整性或原生清理条件。
