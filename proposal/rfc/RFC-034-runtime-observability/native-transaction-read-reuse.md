# RFC-034｜原任务事务内的用量读取复用

## 原始检查与测量

修复磁盘后原完整 `bun run check` 为 6,580 pass／4 fail／153 skip；四项原超时保留。10 月 11 日 Docker 又满，原三个文件的定向检查出现明确 ENOSPC。用户批准精确清理后，三个原文件的全部 32 例、286 断言通过，原 211 步、100／200／211 的进度、全部原 EOF 与 60 秒预算均未改。定向成功不替代或豁免完整检查。

原 `retainNumeric` 对每个实际步骤读取原投影，`project` 再读同一投影，写入后再读一次。所有工作已运行在原 task-head 事务中。重复 SQL 增加真实数据库往返，在完整检查与实际采集负载下放大用量投影时间。

## 设计

仅在 `drizzleUsageLedger.transaction` 的一次事务对象内，按完整 meter key 复用已经读出的投影。保留真实 task-head 锁、原来源、证据读取至 EOF、原模型资格、原修订引用、原投影计算、原两项投影／变化写入和 owner 归属验证。

首次 `current` 必须读取原数据库；未知也只在此事务中保留。`project` 从相同事务的已读投影取得 previous，仍执行原 repair／native model／projection 逻辑，原写入完成后只保存实际计算并持久化的 document，不把 incoming value 冒充最终 document。返回值使用独立副本，保留原数据库读取的值语义；缓存写入采用原 JSON 存储语义。`capture`、`developmentCapture`、`advance` 会更新关联投影，进入和完成这些操作时清空事务缓存；异常路径也清空，不沿用先前结果。

事务结束即丢弃缓存，下一次事务重新读原数据库。无跨请求、跨事务、跨任务快照缓存；无人口上限、无新增跳过、无原 budget 调整。100 是原调度批次，仍逐批读取全部人口至实际 EOF。

## 原验证要求

原真实 PG 回归必须验证：同事务先读未知再写入可读；调用者改变读出对象不会改后续读数；原 repair 与 late capture／advance 更新后不复用旧值；新事务读到真实持久结果。继续执行原 native ledger／211-step pipeline、归属桥接和断线恢复测试，保留原全部断言。限定独立设计门与实现门后，对真正变更后的候选执行一次原完整 `bun run check`，按终态决定发布与本机部署。旧失败、环境清理材料与定向通过分别保留。
