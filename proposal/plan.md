## 0. 计划依据与执行规则

本计划依据 Proposal v0.3.0 与 Design v0.3.0。需求基线为 R01–R49，其中 R06、R20 已删除，R10–R13 已作废并由 R44–R46 替代；设计决策为 D01–D37，待决项为 Q01–Q19。技术选型全部待重评，M0 的 T0.10 产出 `proposal/tech-evaluation.md` 并由用户确认后才冻结，本计划不预设任何组件。

角色命名沿用 Proposal：**意图创建与修改 Agent** 由开发者在开发会话中启动；**业务执行 Agent** 由业务服务经子任务契约层提交。平台不定义 Agent 角色，也没有主 Agent。M3 交付开发会话所需的任务容器与 TaskRunner 底座，M5 在同一底座上交付业务子任务契约层；不能把任务容器能力推迟到 M5。

### 0.1 本版范围与编号

任务编号 `Tn.m` 对应里程碑 `Mn`，只用于追踪。v0.3.0 保留全部旧编号：被删除或作废的任务保留行并标注“已删除”或“已作废，由 Tx.y 替代”，新任务在各阶段末尾追加编号。验收编号 `AT-xx` 同理：AT-20 标已删除，AT-03 等按新模型改写，新增 AT-36–AT-43。所有任务初始状态为未执行。

里程碑名称随范围调整：M2 改为“有状态应用与标签发布”，M3 改为“开发会话、TaskRunner 与工作台”，M4 改为“内部 API 接入、开放策略与事件中心”，M5 改为“业务执行契约层、配额、可靠性与最小样例验收”，M6 改为“一键发行、控制面 HA、分层升级与恢复”。

不按未经估算的日历天数承诺交付。以可运行结果、依赖关系和验收门槛推进；每阶段给出当前源码版本、锁定依赖与证据，不能仅以界面截图或 Agent 自述“完成”结项。数百数字人并发、数百节点是设计目标，压测按该档位报告，不在报告之外承诺数字。

## 1. 实施原则与交付档位

### 1.1 先打通一条真实路径，再扩展适配

先做一个最小样例模板（实现语言随 T0.10 确定）、一个任务容器镜像（TaskRunner 加 OpenCode 与 Claude Code 两个驱动）、一种公司 GitLab 兼容接入（本机复用已运行的测试 GitLab）、PostgreSQL 与 S3 数据资源、一个内置 GitLab 格式 EventProducer。双驱动是首版必需，不因“先打通一条路径”而只接一个。

安全与数据隔离从基础阶段进入。正式公司接入可晚于模拟接口，但不能把模拟登录、模拟放行的结果表述为公司已经授权。

### 1.2 两个明确交付档位

| 档位 | 应具备什么 | 不应宣称什么 |
|---|---|---|
| **开发／体验版** | 本机 kind 集群；建仓、最小样例、开发会话与并行多 Agent、标签发布到 preview、晋级、业务任务契约层、GitLab 事件；控制面副本数可为 1，但 HA 配置项与多副本能力必须存在并在多节点测试集群验证过 | 不宣称公司身份、公司 GitLab Group 与真实数据访问已获授权；不宣称生产隔离；单节点不能代表故障切换已验证 |
| **组织试点／正式候选版** | 真实身份、真实托管 Group、真实上游连接；控制面多副本与元数据库高可用实测；目标档位压测报告；安装升级恢复证据 | 公司审批与未验证模式显式阻塞；不承诺未测规模和任意无损回退 |

“正式候选”不是自动生产批准；公司环境与安全审核是外部前置条件。

**目标：先验证最容易导致返工的接合处，并冻结选型，不以完整 UI 作为起点。**

| 任务 | 内容与边界 | 产出／完成条件 |
|---|---|---|
| T0.1 | 评审 R01–R49、D01–D37、Q01–Q19；明确项目、服务、开发会话、业务任务、接入容器、放行表与数据的身份边界 | 决策记录；旧的主 Agent、执行槽、检查点、自动入库规则不再有效 |
| T0.2 | 建立 monorepo、CI、格式与类型校验、测试入口、依赖锁与许可证核验 | 依赖 T0.10；基础流水线实际通过 |

| T0.4 | 原型：一个任务容器镜像内常驻 TaskRunner，同时运行 OpenCode 与 Claude Code 两个 Agent、一个终端、一个命令；会话恢复；取消与进程树清理 | 双驱动并行可用；清理可验证；驱动对 agent-workflow 后端的依赖已反转（Q03、Q13） |
| T0.5 | 原型：网关鉴权前置、身份头与签名令牌注入、外部同名头剥离、工作负载身份识别、按服务环境的方法加路径放行表 | 业务服务收到身份；伪造头被拒；未开放操作被拒（Q16、Q18） |

| T0.7 | 建立公司身份、上游连接与 API 接入清单，区分实际材料、模拟实现和审批依赖 | 身份映射草案、上游连接主体；缺少的条件显式登记（Q01） |

**关联**：Design §1–§5、§7–§8、§9.4、§10；优先关闭 Q02–Q05、Q11、Q13、Q16、Q18，识别 Q01、Q06、Q10、Q12、Q14、Q15、Q17、Q19。

**限制必须显示**：首版支持的模板与构建 profile、单写卷维护窗口、共享数据库额度是硬限制还是监控阈值。

### 10.1 自动化测试分层

- **契约测试**：三种 Manifest、平台 API、事件、放行表、TaskRunner 接口、状态迁移；示例与 Schema 一致。
- **单元测试**：操作匹配、开放策略、放行表生成、幂等、版本条件、迁移判断、删除保护、配额准入。
- **组件集成测试**：数据库、S3、任务容器、双驱动、网关、GitLab 的实际版本适配；模拟上游与真实上游分别标识。
- **端到端测试**：创建、开发会话、发布、晋级、接口、事件、数据与恢复全过程。
- **故障与升级测试**：副本被杀、元数据库切换、超时、失联、重投、部分供给失败、CRD 变更。
- **安全测试**：不可信代码、租户边界、出站路径、身份伪造、缓存泄露。
- **规模测试**：目标档位下的并发、吞吐与连接数。

外部推送、标签、部署、迁移等副作用必须使用专属测试资源和唯一幂等标识；清理只针对测试新建且可销毁的资源。

### 10.2 业务任务最小验收脚本规范

以下为待编写的测试步骤，不是本次已经执行的结果。

1. 业务服务以工作负载身份创建业务任务，默认 follow-container；记录 taskId 与 traceId。
2. 同时提交分析 Agent 子任务与一个命令子任务；断言两者并发运行，互不阻塞。
3. 分析子任务结束，TaskRunner 校验输出契约；业务程序经文件接口读取报告并核对摘要。
4. 提交编码 Agent 子任务；结束后运行测试命令；核对 cwd、退出码、输出。
5. 提交审核 Agent 子任务；发现问题应为 `Succeeded, businessOutcome=findings`。
6. 注入一次半写失败；重试生成新 attempt，不覆盖失败证据。
7. 取消一个子任务，确认其进程树停止、其他子任务与文件不受影响；清理不确定时该子任务标 Failed。
8. 以 persistent 模式重复 1–4，暂停后恢复，核对卷内容与授权重验；关闭任务后卷与配额释放，仓库与业务数据保留。
9. 用 traceId 索引出全部 sessionId、子任务、命令与产物引用。

### 10.3 开发会话与标签发布完整验收脚本规范

1. 在获准测试 Group 新建项目，确认唯一远端 Project、初始提交、最小样例在 preview 可访问并显示当前用户。
2. 开启开发会话，选择默认分支；核对显示的部署 SHA 与落后提交数；第二个会话被拒。
3. 容器就绪，预览自动启动；同时启动一个 OpenCode Agent 与一个 Claude Code Agent，打开终端与编辑器；各自修改文件，预览实时更新。
4. 在 Swagger 调试页试调一个默认开放接口与一个未开放接口；前者成功，后者被网关拒绝；申请定向接口，管理员审批后可调。
5. 申请只读诊断数据访问，负责人审批后连接成功；未审批的生产变更被拒。
6. 点发布：存在未提交内容时提示；提交后再发布，平台代推、打标签、构建、部署 preview；手工推送一个 v 标签，确认不触发。
7. 负责人晋级 prod；开发者尝试晋级被拒；核对 prod 路由与迁移记录。
8. 释放会话，核对未推送提示、Pod 与卷删除、配额释放；再次开启会话，容器重建并从所选分支检出。
9. 触发一条 GitLab 事件，确认经 EventProducer 与 cs-events 推送到样例服务处理路径。

### 12.3 完成定义

功能完成必须同时满足：代码和协议实现；正常与失败路径测试；权限和数据影响明确；用户可见状态与错误；运维与恢复说明；精确版本验证记录。性能或可用性承诺只在有对应实测条件时写入发行说明。

## 13. 延后项目与触发条件

| 延后能力 | 何时再做 |
|---|---|
| 更多 Agent 驱动 | 双驱动稳定后按需求扩展 |
| 多集群调度、跨区域灾备 | 单集群目标档位稳定后 |
| 业务服务发布自定义事件 | 有明确跨数字人协作需求 |
| 平台定时触发 | 业务自实现方案不足以支撑时 |
| agent-workflow 作为业务应用接入 | 其 OIDC 登录改为网关身份的改造完成后 |
| 开发会话暂停或持久卷 | 一项目一会话与释放即回收不满足需求时 |
| 同一项目多个并行开发会话 | 单会话串行开发成为瓶颈且冲突策略明确 |
| 知识提取与召回 | 追溯链稳定后按价值决定 |
| 资源级接口授权 | 上游或业务把关不足且能在目录标注资源语义 |
| 任务时长与模型用量预算 | 并发配额不足以控制成本时 |
| 通用 DAG 与平台侧编排 | 明确违背“平台不编排开发过程”原则，需重新评审 |
| Knative、Istio、OPA、Temporal、Buildpacks | 与 v0.2.0 相同的触发条件 |

延后不意味着忽略安全与数据；不能因为某组件可选就延后生产隔离门槛。

## 14. 启动项目时的第一组行动

从 M0 开始，先完成选型重评（T0.10）并冻结三种 Manifest 与放行表契约，然后做三条原型：

1. 一个任务容器镜像内常驻 TaskRunner，同时运行 OpenCode 与 Claude Code 两个 Agent、一个终端与一个命令，会话可恢复、进程可清理。
2. 网关鉴权前置、身份头与签名令牌注入、工作负载身份识别、按服务环境的方法加路径放行。
3. 在本机测试 GitLab 的获准 Group 自动建仓、推送、以平台身份创建保护标签；两种任务持久卷模式的释放与暂停恢复。

随后 M1 建好项目、身份、路由与最小样例，M2 打通数据与标签发布到 preview 与晋级 prod，M3 交付开发会话与工作台，M4 交付接入容器、开放策略与事件中心，M5 交付业务契约层、配额与最小样例验收，M6 验证 HA、一键发行、分层升级与恢复。

**整套计划最终验证的是：业务团队在一个常驻 TaskRunner 的开发容器里，用自己的方式和自己的 Agent 开发数字人；发布只是一个平台创建的标签；业务服务不写登录代码就拿到身份、按开放策略调用内部接口、接收公司事件、经契约层运行业务执行 Agent；平台在数百服务的规模下以高可用形态独立升级公共能力。**
