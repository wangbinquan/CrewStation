## 0. 计划依据与执行规则

本计划依据本次对话汇总后的 Proposal 和 Design。需求基线为 R01–R37，包含用户明确要求与标明的建议实现；技术选型与具体协议仍需验证，Design 的 Q01–Q15 是待决项。这里不重新做技术调研，也不把对话中提到的第三方能力视为已经在项目中验证。

角色命名沿用 Proposal：**意图创建与修改 Agent** 根据用户意图创建和修改数字人应用；**业务执行 Agent** 由业务服务调用，完成具体业务任务。M3 验证前者，M5 验证后者；底层运行能力可以复用，但工作对象、会话和授权分开。

主、分析、编码、审核是任务内职责，与上述用途正交。M3 先交付共用 TaskEnvironment／SubtaskRun 底座和意图场景，M5 复用它完成业务场景，不能把任务级能力推迟到 M5，导致 M3 仍实现一次 Agent 一个临时环境。

### 0.1 本版范围与编号

本版从 v0.1.1 继续更新原有阶段与任务：R05、T0.4、T3.1、T5.1、AT-08 等旧表述同步替换为任务级模型，不保留互相冲突的验收。新增 R29–R37、D16–D22、Q11–Q15、相关实施任务和 AT-25–AT-35。

自动建仓进入 M1；源码入库与自动发布进入 M2；长周期任务、已运行应用的意图修改和 TaskDataBinding 进入 M3；M6 做真实公司托管与整条恢复再修改链路验证。任务编号只用于追踪，不等同于严格执行先后；阶段内按明确依赖推进。

任务编号 `Tn.m` 对应里程碑 `Mn`。验收编号 `AT-xx` 是本项目要实现的可复现测试，不表示这些测试当前已存在或已经通过。所有任务初始状态为未执行。

不按未经估算的日历天数承诺交付。以可运行结果、依赖关系和验收门槛推进；每阶段都应给出当前源码版本、锁定依赖与证据，不能仅以界面截图或 Agent 自述“完成”结项。

## 1. 实施原则与交付档位

### 1.1 先打通一条真实路径，再扩展适配

先做一个 React＋Fastify 数字人模板、一种 Agent Adapter、一种任务运行后端、一种公司 GitLab 兼容托管接入和 PostgreSQL／S3 数据资源。同一引擎可切换分析、编码、审核配置，首版必须支持这些角色的顺序执行及命令，不因“单适配器”而删掉多步骤要求。暂不追求所有语言或共享工作区并行执行。

安全与数据隔离从基础阶段进入，不是最后单独补一轮。正式公司接入可晚于模拟接口，但不能把模拟登录、模拟权限通过的结果表述为公司已经授权。

### 1.2 两个明确交付档位

| 档位 | 应具备什么 | 不应宣称什么 |
|---|---|---|
| **开发／体验版** | 本地或测试 K8s 建仓模型、Demo、串行 Agent／命令、意图修改、源码入库与发布；独立测试数据 | 托管 Mock／测试服务单独标记，不宣称公司建仓和真实数据访问已获授权；不宣称 HA 或生产隔离 |
| **组织试点／正式候选版** | 实际身份、接口和托管 Group 接入，任务环境、受控数据连接、自动入库部署、环境回收再修改，以及安装升级恢复证据 | 公司审批与未验证模式显式阻塞；不承诺未测规模和任意无损回退 |

“正式候选”不是自动生产批准；公司环境与安全审核是外部前置条件，计划要显示等待状态。

## 2. 里程碑与依赖

| 阶段 | 核心结果 | 进入条件 |
|---|---|---|
| **M0：约束和关键原型** | 协议、托管兼容范围、任务内顺序执行和多仓工具、路由／数据原型 | 文档评审与获准测试环境 |
| **M1：平台最小可运行基础** | 创建服务自动建仓与源码初始化；稳定地址、真实 Demo、身份与状态 | M0 的关键不确定性可控；托管测试接入可用 |
| **M2：有状态入库发布** | ZIP／工作区代码入库、数据库／文件绑定、最终 SHA 发布与失败保留旧版 | M1 仓库绑定与工作区基础 |
| **M3：持续意图创建与修改** | 共用 TaskEnvironment 与串行子任务；新建／已运行应用按需修改、数据连接、预览及自动入库部署 | M1 托管基础、M2 数据及发布接口；先完成 T3.8 执行器 |
| **M4：公司接口权限与事件** | 服务身份、代理、权限化 Swagger、调试和 Webhook | M1 身份边界；真实公司接入按条件推进 |
| **M5：业务执行、可靠性与知识** | 业务服务复用任务环境执行分析／编码／命令／审核；资源池、恢复和知识验证 | M2–M4，共用执行底座已在 M3 验证 |
| **M6：完整发行包与运行验证** | 空集群安装、离线、分级升级、单项目恢复与生产候选验收 | 前面各阶段功能通过；发行包骨架从 M1 建起 |

M3 与 M4 在接口冻结后可部分并行，但组织试点必须同时通过。M6 不是到最后才做安装：M1 先有简化安装与预检，M2–M5 持续纳入组件，M6 关闭完整性和恢复验证。

新增能力的关键依赖：`T0.9 → T1.9/T1.10 → T2.9/T2.10 → T3.9/T3.12`；`T0.4 → T3.1/T3.8 → T3.2/T3.3/T3.11 → T5.1`；`T2.2/T2.3/T2.4 → T3.10 → T3.9`。这些依赖先于同一阶段内的编号顺序。公司生产数据授权可以晚于开发数据验证，但未获批不得标为真实数据接入通过。

建议职责按工作领域分配：平台契约／控制面、前端与开发体验、执行底座、企业接入安全、数据与发行工程。小团队可以由同一人承担多个角色，不预设真实人员或团队规模。

**目标：先验证最容易导致返工的接合处，不以完整 UI 作为起点。**

| T0.2 | 建立 monorepo、基础 CI、格式与类型校验、测试入口、依赖锁和许可证核验 | `apps/`、`packages/contracts/`、`tests/`；基础流水线实际通过 |

| T0.4 | 锁定 K8s、网关、OpenSandbox、Agent 候选；一个长任务关联两个代码环境，顺序跑分析／编码／命令／审核 | 步骤间复用文件；新 Agent 会话独立；主协调读真实文件且不占被等待的执行槽 |

| T0.7 | 建立公司身份与 API 接入清单，区分实际材料、模拟实现和审批依赖 | 身份映射草案、上游授权主体、接口归属规则；缺少的条件显式登记 |
| T0.8 | 验证非特权构建、运行时隔离、网络出口和秘密传递；选定首个受支持 profile | 威胁模型和测试结果；未通过只能进入受信体验环境 |

**门槛 G0**：证明一个长任务可顺序运行两个 Agent 角色和命令、主协调可读两个代码环境的实际文件；网关直达预览、业务数据跨项目拒绝；至少在明确标记的兼容测试服务完成建仓初始化。真实公司权限未知时登记阻塞项，不放宽授权或隔离来宣称原型通过。

**关联**：Design §1–5、§7、§9–10、§13；优先关闭 Q02–Q05、Q11、Q13，识别 Q01、Q06、Q10、Q12、Q14、Q15。

## 4. M1：项目、身份、路由和真实 Demo

**目标：先不依赖模型生成，创建出来的项目就具有可用源码和页面。**

| 任务 | 内容与边界 | 产出／完成条件 |
|---|---|---|
| T1.1 | 实现 Project、ServiceEnvironment、ServiceAccount、Operation 与基本授权表 | 事务与对象级授权测试；跨团队项目 ID 不能越权 |
| T1.2 | 建立五个自研服务启动边界、健康检查与内部通信；提供体验部署和安装预检骨架 | cs-api 不执行用户代码；各服务权限与日志独立配置 |
| T1.3 | 实现从初始化远端提交准备模板 Workspace、写租约、检查点和就绪状态 | 依赖 T1.9/T1.10；Demo 对应公司托管源码，重试不覆盖已编辑文件 |
| T1.4 | 实现用户认证、服务身份框架、预览／正式身份分离和环境访问规则 | 体验身份显式标记；真实身份 Adapter 可按 Q01 接入 |
| T1.5 | 实现 ServiceHost／SandboxProvider 最小调用与稳定 URL、HTTPRoute 管理 | 重建环境后地址不变；用户不能发布指向其他团队的路由 |
| T1.6 | 实现项目页面、独立预览、准备状态、日志和恢复入口 | URL 分配与 Demo Ready 分开；iframe 显示真实应用 |
| T1.7 | 实现入口鉴权与大文件地址申请骨架、日志脱敏和基础配额 | 不把所有正文转发鉴权；直接对象上传流程有受限授权 |
| T1.8 | 集成创建、仓库初始化、停止恢复、控制面重启和孤儿检查 | AT-01、10、22、25 基础场景留证；远端仓库不是临时容器附属资源 |
| T1.9 | 实现 SourceControlProvider 自动建仓、稳定服务路径、远端 ID 归属、幂等核对 | 指定 Group 下建一个项目；冲突不接管；失败续接不删除已存在数据 |
| T1.10 | 实现 SourceRepositoryBinding、模板／ZIP 初始提交、远端确认和仓库状态 UI | 每逻辑服务唯一绑定，preview/prod／扩容不重复建仓；Demo 来源可核对 |

**门槛 G1**：创建服务返回稳定 URL，并在获准测试 Group 自动创建唯一 Project、初始化源码；Demo 对应该提交的工作区，文件修改立即影响预览；环境失败重试不新建仓库；重启管理 API 不重建已运行应用；未授权不能访问仓库或预览。

**本阶段不算完成的能力**：模型尚可不接；兼容托管模拟与真实公司接入分开标记；完整业务发布和数据绑定由 M2 补齐。代码托管不是后续可选项。

## 5. M2：有状态应用、ZIP 导入和统一发布

**目标：用户上传源码包，就能在已授权范围内得到独立、持久、可更新的业务服务。**

| 任务 | 内容与边界 | 产出／完成条件 |
|---|---|---|
| T2.1 | 实现 Manifest Schema、源码类型识别、上传会话、原包摘要与安全解压 | ZIP 越界、链接、炸弹、重复文件、入口冲突均有拒绝测试 |
| T2.2 | 实现 DataResource／DataBinding／套餐与供给状态机 | 配额检查、幂等分配、失败续接；已有数据不自动补偿删除 |
| T2.3 | 实现 PostgreSQL Provider：独立库、运行／迁移账号、凭据注入与验证 | 业务账号不能读平台库或其他项目；preview/prod 分开 |
| T2.4 | 实现 S3 Provider 与受限 PVC Provider；记录访问模式和保留策略 | 存储侧权限测试；不支持 RWX 或单写条件时拒绝申请／发布 |
| T2.5 | 实现从已确认最终 SHA 构建、短期私有依赖访问、镜像摘要和检查 | 构建输入不漂移、不从开发进程直接打包；版本和权限可追查 |
| T2.6 | 实现 Release／Deployment、最终提交验证、健康检查、稳定路由与旧版保留 | 服务副本和源码保存分开，失败不切换正式版本；发布检查对应最终 SHA |
| T2.7 | 实现独立迁移 Job、迁移锁、兼容性声明、破坏性变更批准与维护模式 | 迁移失败可定位；独占卷不能被两个新旧副本错误并行写入 |
| T2.8 | ZIP／工作区检查点统一进入托管修改分支、远端确认提交与发布链 | 回退、暂停和删旧版不删仓库或业务数据；AT-03、12、13、14、21、24 |
| T2.9 | 实现工作区检查点、修改分支、受控 commit/push、最终合入与自动发布策略 | 保存不等于上线；秘密不入库；拒绝／结果未知有状态；审批后自动续行 |
| T2.10 | 实现目标分支与 Active Release 版本条件、发布租约、Git／CI／主动发布事件去重 | 两修改会话不覆盖对方；最终验证匹配最终 SHA；迟到发布不能覆盖较新上线 |

**门槛 G2**：ZIP 和工作区修改先进入绑定仓库，平台自动保存／推送并按策略发布最终 SHA，分支与发布冲突有明确状态；独立数据库和文件跨升级保留；远端推送失败不算入库，部署失败不覆盖旧版，回退不恢复整库或旧权限。

**限制必须显示**：首版支持的模板与构建 profile、单写卷维护窗口、共享数据库额度是硬限制还是监控阈值，以及尚未批准的接口需求。

## 6. M3：意图创建与修改 Agent 与在线工作台

**目标：用户在前端对话修改的是真实项目，不是只获得一段代码。**

| 任务 | 内容与边界 | 产出／完成条件 |
|---|---|---|
| T3.1 | 实现 DevSession create/modify、TaskEnvironment、TaskWorkspaceBinding 及准备协调 | 环境归任务，AgentRun 归子任务；仓库／数据／预览／步骤状态分别可见 |
| T3.2 | 实现 task 文件／diff／日志工具、绑定鉴权与版本检查 | 主 Agent 和子步骤读写实际工作区，路径／环境不能越界；实时与快照来源明确 |
| T3.3 | 接入 Agent Adapter 和 CommandAdapter，同一运行时顺序选择角色／会话并清理进程 | 单引擎多角色可用；任务不重建所有环境；本地工具和仓库配置不能绕过授权 |
| T3.4 | 实现消息幂等、步骤尝试、事件游标、流式重连、步骤取消与任务暂停关闭 | 断线不重复指令；取消一个步骤不清空环境；主协调等待无队列自锁 |
| T3.5 | 完成意图对话、任务时间线、步骤差异、仓库／数据模式、预览和发布状态展示 | 主对象是应用与任务；RemoteSaved、检查成功和 Active 分开，不伪报进展 |
| T3.6 | SDK／CLI／MCP 接入创建、修改现有应用、任务工具、保存和完成发布 | 同一后端授权与发布逻辑；自动策略不要求手工 Git，但不能由文本自行扩权 |
| T3.7 | 实现空闲休眠、检查点、分支恢复、旧写入者隔离和运行时迁移 | 全部开发计算回收后可恢复；不只恢复已提交文件；重新授权不复活生产权限 |
| T3.8 | 实现 TaskRunner 前台串行槽、SubtaskRun、AgentRun／CommandRun、尝试和输出契约 | 同环境依次分析／编码／命令／审核，步骤结束文件保留；依赖 T3.1，先于完整 Agent UI |
| T3.9 | 实现运行中应用的意图修改入口与环境重建：读取实际发布 SHA、分支、配置和数据绑定 | 独立环境 clone/fetch，正式版不被编辑；回收后可重新创建并恢复未提交现场 |
| T3.10 | 实现 TaskDataBinding：开发、获批只读诊断、受控生产变更；数据连接及预览副作用控制 | 真实连接可验证；权限／到期检查不只发新 token；无默认生产写权，后台消费隔离 |
| T3.11 | 实现主 Agent 任务工具发现、现场读取、检查点 diff、步骤调度与结果查看 | 跨仓文件真实读取、分页和来源完整；主协调不占子任务槽；访问他人环境被拒绝 |
| T3.12 | 贯通意图完成到自动保存／入库／最终验证／部署，与 M2 共用发布模块 | 新建与已运行应用都可完成；无须手工 Git，越权或检查失败阻塞，旧版数据保留 |

**门槛 G3**：对新建和已经运行的应用，都可准备独立意图任务环境、拉取准确基线并连接该应用获授权数据。一个任务顺序运行分析、编码、测试命令和审核，主 Agent 可读取真实报告与 diff。完成后自动入库并按规则部署最终提交；清空开发计算后再次发起修改仍可恢复代码、数据访问和预览，原正式应用不被直接编辑。

必须验证：步骤取消不关闭任务、会话重连不重复指令、独立分支冲突可见、生产副作用隔离、未获授权模式被拒绝。既要有固定桩驱动的可复现状态测试，也要有首个真实 Agent 适配器的实际行为证据，不能用模型一次成功替代平台契约测试。

**关联**：R02–R06、R14、R23、R25、R27、R29–R37；AT-02、08、11、21、22、26–34。公司接口使用 M4 的权限化能力，M3 的模拟工具不得扩大为正式默认授权。

### 10.1 自动化测试分层

- **契约测试**：Manifest、OpenAPI、事件、状态迁移和授权接口；生成示例与实际 Schema 一致。
- **单元测试**：操作匹配、资源范围、策略裁剪、幂等、版本条件、迁移判断、删除保护。
- **组件集成测试**：数据库／S3／沙箱／Agent／网关的实际版本适配；模拟上游与真实上游分别标识。
- **端到端测试**：用户创建、开发、发布、接口、事件、数据与恢复全过程。
- **故障与升级测试**：重启、超时、失联、重投、部分供给失败、CRD 变更、资源不足与恢复。
- **安全与容量测试**：不可信代码、租户边界、出站路径、缓存泄露、身份伪造，以及不同流量的容量测量。

自动化可以并行运行，但外部 MR、发布、数据迁移等副作用必须使用专属测试资源和唯一幂等标识。测试结束的清理只针对该测试新建且可销毁的资源。

### 10.2 新执行模型的最小验收脚本规范

以下为待编写的测试步骤，不是本次已经执行的结果。

1. 创建一个任务环境，准备后端和前端两个测试仓库及一个任务产物目录；记录环境／工作区 ID。
2. 运行分析 Agent，生成分析文件；断言该步骤结束后任务仍 Ready，原代码环境未被回收。
3. 主 Agent 读取该文件和指定代码片段，检查内容与真实文件摘要一致，再提交编码子任务。
4. 编码产生变更后运行明确命令；核对 cwd、退出码、标准输出、测试报告和前后检查点。
5. 用独立会话运行审核 Agent；发现问题应为执行成功＋findings，不得当成审核通过，也不等于执行异常。
6. 继续修复，注入一次半写失败；分别测试当前现场续做与检查点恢复，留下独立 attempt 记录。
7. 取消一个步骤，确认其子进程停止、其他持久文件仍在；残留不确定时阻塞队列。
8. 暂停任务，回收计算，再恢复；核对未提交源码、分支、产物和当前授权。关闭整个任务后检查资源与数据保留策略。

主 Agent 协调不能占住唯一执行槽；直接由业务程序提交同样序列也应通过。即使模型输出不同，状态和权限断言仍可复现。

### 10.3 持续意图修改的完整验收脚本规范

1. 在获准公司测试 Group 新建应用，确认只有一个远端 Project、初始提交与服务绑定，真实 Demo 可用。
2. 分配开发／正式数据资源，在正式应用中写入一条测试业务记录及一个附件，记录数据与资源 ID。
3. 首轮意图开发后自动保存、推送并发布；核对最终 SHA、镜像摘要、部署与验证记录。
4. 回收所有意图开发计算，不关闭正式服务；源码、数据、发布记录仍存在。
5. 再次发起意图修改，默认从当前正式 SHA 创建独立分支和任务环境，拉取应用仓库并建立获授权数据访问。
6. 使用多个 Agent 与命令完成一个功能修改，主 Agent 可读文件；右侧预览真实更新，正式版不被提前修改。
7. 对开发数据执行写入，对获批真实数据做只读诊断；未经批准的生产写入和事件消费必须拒绝。
8. 完成后自动入库并发布最终版本；验证原业务记录和附件仍可用。再注入推送失败／部署失败，分别检查保存状态和旧版可访问性。
9. 并发启动两个修改会话并模拟目标分支或正式版本变化，验证冲突处理和发布协调，不允许迟到覆盖。
10. 卸载或升级控制服务、归档项目等操作按独立测试计划验证；仓库／数据销毁必须显式授权，测试清理不触碰未知资源。

这两条脚本规范分别是 AT-26–28、34 和 AT-25、29–33、35 的组合入口，不代替各 AT 的异常与权限测试。

## 12. 发行验收与证据目录

### 12.1 每个阶段都需要的记录

记录源码精确提交、文档／契约版本、镜像摘要、组件锁定版本、集群与存储条件、测试数据范围、实际执行命令、结果和失败项。不得把其他提交或更早版本的测试结论当成本次版本通过。

建议证据组织方式：

```text
evidence/<release-or-commit>/
├─ versions/            # 精确源码、镜像、依赖与契约版本
├─ environment/         # 测试拓扑、存储、网络、身份模式
├─ contracts/
├─ install/
├─ development/
├─ source-hosting/      # 建仓、Git 操作、最终 SHA 与发布关联
├─ task-runtime/        # 串行 Agent／命令、主 Agent 文件访问与恢复
├─ task-data/           # 任务数据库模式、预览副作用与撤权
├─ intent-modify/       # 回收后再次修改的完整链路

├─ stateful-release/
├─ upgrade/
├─ restore/
├─ isolation/
```

目录只是拟议交付规范，本次文档生成不创建虚假的测试报告。敏感凭据、真实业务正文和个人数据不得放入公开证据。

### 12.3 完成定义

功能完成必须同时满足：代码和协议实现；正常与失败路径测试；权限和数据影响明确；用户可见状态与错误；运维／恢复说明；精确版本验证记录。性能或可用性承诺只在有对应实测条件时写入发行说明。

## 13. 延后项目与触发条件

| 延后能力 | 何时再做 |
|---|---|
| 多引擎／多语言适配器全面覆盖 | 首个引擎多角色顺序执行稳定后再扩展；同任务顺序多 Agent 和命令不是延后能力 |
| Knative 缩容到零 | HTTP 服务语义、冷启动与数据外置已验证，确实需要按需托管 |
| Istio／更复杂服务网格 | 有独立的服务间治理需求且现有网关与网络边界不足 |
| OPA／复杂策略中心 | 固定操作＋资源规则无法清楚表达实际授权时 |
| Temporal／复杂业务持久工作流 | 大量跨天等待、人工审批与恢复需求证明必要时；不强制所有应用采用 |
| Buildpacks 全语言自动构建 | 已有源码协议稳定，能够维护多语言测试矩阵 |
| 多人实时同写一个工作区 | 单写租约／独立工作区不能满足协作，再引入明确冲突处理 |
| 通用 DAG／共享工作区并行子任务 | 首版串行和独立分支满足不了实际需求后再做；不能因此延后主 Agent 文件访问和步骤恢复 |
| 独立向量库和自动自进化 | 已有知识验证、来源与撤回机制证明价值与容量需要 |
| 多集群调度、跨区域灾备 | 单集群运行、备份恢复与租户隔离稳定后按需求扩展 |

延后不意味着忽略安全与数据。不能因为某安全组件是“可选”就把生产隔离门槛也延后。

## 14. 启动项目时的第一组行动

从 M0 开始，先冻结新对象关系和三条原型：

1. 一个长周期 TaskEnvironment，两个代码环境，顺序执行分析／编码／命令／审核，主 Agent 读取实际文件。
2. 一个逻辑业务服务，在批准 Group 自动建仓并提交模板；重复创建可恢复，不误接他人仓库。
3. 一个可独立运行的 Demo，具有路由、业务数据库和文件空间；任务可按批准模式访问数据，不能越权。

随后 M1 建好真实托管项目，M2 打通数据及最终 SHA 发布，M3 共用任务执行器并完成新建与运行中应用的意图修改；M4 提供公司接口与事件授权，M5 复用同一任务底座交付业务数字人，M6 验证公司接入、一键发行、回收再修改和升级恢复。

**整套计划最终验证的是：应用有长期托管源码和业务数据，任务环境可以随时重新准备；主 Agent 或业务程序在一个持续任务内安排工作，平台自动完成受控入库和部署，团队不必反复协调所有基础设施。**
