# 0003. 新增 provisioning 与 platform 两个模块

- 状态：已接受
- 日期：2026-09-12

## 背景

`docs/engineering/repository-structure.md` §5 定了 16 个模块。第一轮实现把整条链在本机集群上跑通后，出现两件确实没有归属的事：

**项目开通链**。管理员建项目之后，平台要依次做：建命名空间与配额与网络策略、建仓并写入模板、开通生产数据、算路由、从首个标签发一次版，任一步失败要留下原因并可重跑。这条链横跨 `project`、`scm`、`data`、`gateway`、`release` 五个模块，按现有分层放进其中任何一个都会让那个模块反向依赖比它高的层。

**装配**。18 个模块之间是端口注入，谁给谁提供什么必须有一处唯一的答案；五个 `cs-*` 进程又各自只启用其中一部分路由与后台。散在各进程入口里写，等于每个进程各有一份装配逻辑，正是本文 §0 要避免的堆叠。

## 决策

新增两个模块：

| 层 | 模块 | 拥有的对象与职责 | 依赖的模块 |
|---|---|---|---|
| L6 | `provisioning` | 项目开通编排：命名空间→仓库→数据→路由→首个标签发布→active；失败留原因可重跑，由 `project.created` 事件入队、队列重试 | project、scm、data、gateway、release（都只经各自的公开 API） |
| L7 | `platform` | 组合根：按端口装配全部模块，按进程角色挑选 http 路由、后台工作器与事件订阅 | 全部模块 |

`platform` 单独占 L7，因为它按定义依赖所有模块；它不含任何领域逻辑，只有装配。`provisioning` 放 L6 而不是更低层，因为它依赖 L5 的 `release`。

## 后果

- 模块总数 16 → 18，`tools/arch` 的分层表同步更新，依赖方向规则照常生效（实测无违规）。
- 开通链的每一步都必须幂等：整条链会因任一步失败而整体重跑。
- `platform/wiring.ts` 会随模块增加而变长；它已经拆成 `composeCore`／`composeDelivery`／`composeRuntime`／`composeAggregates` 四个函数守住 80 行的函数上限，再增长时继续按这个方式拆，而不是放宽上限。
- 跨层回填用 `late` 机制（低层声明端口，组合根在高层装配后回填），例如 `project` 的配额占用数取自 `task-runtime` 的准入计数器。这是唯一允许的反向取数方式，且必须经端口。
