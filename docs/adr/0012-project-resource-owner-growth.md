# 0012. 项目资源所有者的增长与拆分方案

- 状态：提议；拆分尚未实施，没有新增模块、layer 或结构规则例外
- 日期：2026-10-01
- 关联：[RFC-037](../../proposal/rfc/RFC-037-project-creation-and-deletion/design.md)、[ADR-0009](0009-resource-center.md)

## 背景

仓库结构 §11 要求模块超过 40 个源码文件或 6000 行时，先用 ADR 提出拆分方案。永久删除必须沿所有者边界逐一封写、排空、回收和复盘，不能把这些工作都塞入 platform，也不能用更深目录绕开规模限制。完整 RFC-037 已获准按现有模块实施；本提议用于记录后续拆分边界，实际增加／转移模块与 schema 前仍须批准结构方案。

## 提议的拆分顺序

先按现有对象概念合并零散端口、纯映射与持久表声明，减少重复 imports 与一对象多文件碎片，不合并不同状态机来隐藏规模，也不增设转发 facade。scm 的正式删除协议优先采用这种方式，保持在 40 个生产文件内；data-control 的原生删除与来源协议维持 ADR-0009 已接受的 L2 职责。

resources 先在现有删除 inventory 中提供完整保留台账和显式历史缺口，不为一个查询再增加 facade 或子模块。后续拆分候选为台账／声明与视图、工作区准入／消费者、原实例及原卷清理三个已有对象簇；它们的共同项目屏障、原身份和 schema 归属仍须保持单一所有者。实际拆分需完整依赖和迁移方案后批准，本提议不授予文件规模例外。

data 拆分候选为：保留 data L3 的数据库资源、访问绑定／审批和项目授权；对象空间、文件、上传／读取／验证、配额与引用形成 object-storage L3；归档计划、终结意图、归档绑定与恢复形成 archive-storage L4。原生数据库 DDL 和 S3 字节协议仍归 data-control L2，不移动到领域模块。具体新模块、表归属、依赖图与迁移兼容方案须在实施拆分前补齐并批准。

task-runtime 先沿原生执行与实例／卷分组，business-task 沿业务协调与终结归档分组；dev-session 保留父任务／恢复的单一所有者，原生执行经 task-runtime 端口提供。拆分不能把一个任务状态机复制到两个模块；消费者和持久意图仍由原 owner 负责。session 沿会话状态与原生桥接、release 沿发布状态与构建／迁移执行、runtime-environment 沿目录修订与验证执行分别盘点，优先合并同概念小文件，仍超界时再提出有独立状态和数据的模块。

observability 的数值汇总与原始执行内容按不同保留／清理语义拆分；cluster-management 的清单与持久运维操作分别盘点。platform 只保留装配与跨 owner 的公开端口回填：物理资源能力落既有 control owner 的适配器，不能移出模块再建一个横跨全部 schema 的“删除服务”。涉及层或拥有对象转移的实际决定均需后续批准，不能由本提议默默执行。

## 兼容与当前工作

拆分必须保持公开 REST 合同、原 UUID、资源身份、已确认删除范围与最小回执，不按当前 slug 重新认领历史资源。schema 所有权转移要有完整旧库迁移和升级／回放用例，不能共享读取彼此内部表、改已入锁迁移或留下两套写入者。部署期间同一原资源只能有一个实际写入所有者。

本次结构记录不改变已经批准的永久删除语义，不调整 40／6000 或 600／20／80 上限，不授予 imports／新增代码防护例外，不实施新模块与 schema 转移。RFC-037 继续按现有 owner 接口完成已授权的关闭／排空协议；涉及真正的新模块或层转移时以具体方案另行确认，不借静态检查绿灯省略结构决策。
